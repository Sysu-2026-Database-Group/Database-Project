# 第一阶段总结报告：可运行数据库原型 v0.1

## 1. 报告范围与材料

本报告总结第 1—4 周形成的拾光书店数据库原型。它对应 `docs/task-v0.1.md` 的阶段报告要求，具体规则、字段和 SQL 仍以正式文档和脚本为准。

本阶段交付 19 张表、47 个外键、77 行基线样例，以及建库、样例、CRUD、查询、视图、约束和角色脚本。当前机器复现使用 SQL Server，完整命令和脚本顺序见 `db/README.md`；结果与截图索引见 `docs/evidence-v0.1.md`。

## 2. 经营场景与业务流程

拾光书店是单门店、线下销售并支持线上预订到店取货的书店。商品分为图书和文创，图书用 ISBN 识别，文创用内部编码识别；库存按商品种类的数量管理，不追踪到单件。

店内角色为店长、收银员和库存管理员，顾客是外部主体。主流程是：库存管理员建档并上报报价，店长定价上架；库存管理员提交采购申请，店长审批并付款，库存管理员按正常申请数量收货入库；顾客可以直接购买，也可以线上预订后到店由收银员核验、结算和交付；退货由收银员受理退款、库存管理员回收入库。查询、资金登记和盈亏查询分别由业务流程自动留痕或按角色完成。

预订只增加已订量，不冻结价格、折扣或积分；到期或取消释放已订量，取货时按当时的售价和会员档位结算。销售单、预订单、采购申请单和退货单都是业务记录，销售单由结算动作产生，不另设“订单”业务。

## 3. 数据边界及理由

进入数据库的内容包括商品及当前库存计数、图书和文创识别信息、供应商及当前报价、采购 / 销售 / 预订 / 退货单据与明细、会员与当前卡档位、积分流水、资金流水和员工留痕。这些信息分别支撑库存、结算、退货、会员权益、资金对账、权限和追责。

可售量、是否可售和经营盈亏不单独保存，因为它们可以由在架总量、已订量或资金流水计算，另存会产生不一致。退货理由、顾客姓名、支付渠道、封面图、货架位置、单件编号、会计成本、门店档案和会员卡参数变更历史不进入当前数据库，因为它们不参与本阶段的业务判定，或已被场景边界排除。会员卡当前费用和折扣率保留在 `card_type`，历史成交通过销售快照保留。

## 4. 表与码的设计理由

数据库按五个数据域组织 19 张表：商品与库存、单据与流转、会员与积分、资金、主体。`goods` 统一保存两类商品的名称、上架状态和库存计数，`book` / `toy` 保存各自识别与展示信息；这样商品销售和库存流水只需引用一个商品主表。

默认使用自增 `id` 作为内部标识，采购、销售、预订和退货单另外设置唯一业务编号。ISBN、文创内部编码、会员手机号、员工手机号和卡档位本身具有稳定业务含义，因此分别作为对应表的主键；单号和预定码作为唯一约束而不是内部外键主键，避免把可能调整的编号生成规则扩散到表关系。

单据使用单头与明细分离。一张销售单可有多条销售明细，单头保存折扣、积分抵扣、实付金额和成交快照；退货明细引用原销售明细，才能支持部分退货并核对库存、资金和积分。库存变动和资金流水保留来源外键与操作人，使三本账可以回溯到业务单据。

## 5. 完整性约束和角色权限正反例

Week 3 的基础约束包括主键、唯一约束、外键、非空、默认值和单行 `CHECK`，拒绝重复单号、不存在的外键、非法数量、错误金额、无来源库存流水和不完整留痕。`verify.sql` 实际保留了 16 个非法数据反例及错误码，并验证库存、积分、销售、退货、采购和资金的跨表对账。

Week 4 用触发器补充银卡 / 金卡的跨行关系：金卡费用必须高于银卡，金卡折扣率不能高于银卡；非法修改返回 `51025` 并回滚。查询、视图和约束脚本的输出见 `db/results/`。

角色遵循最小权限：店长维护价格、卡档位和全店账；收银员处理顾客、销售、预订和退货；库存管理员处理商品、报价、采购和库存；顾客不建立员工式数据库账号，由业务层使用手机号、预订码等凭证验证归属。每个店内角色都有正常操作成功和越权操作失败的结果，越权测试返回 `229`，没有授予 `db_owner`、`CONTROL` 或 `ALTER`。

## 6. 实验过程、问题与修正

第一阶段先由 Week 1—2 确定场景、角色、业务、边界和数据字典，再由 Week 3 落成 SQL Server 表结构和基线样例，最后由 Week 4 补充查询、视图、跨行约束和角色权限。样例数据固定为 2026-09-20 收盘截面，方便多轮复现比较。

实际执行中遇到并修正了以下问题：

1. 初次样例装载的 ISO 日期时间缺少秒数，SQL Server 转换失败；改为完整 `YYYY-MM-DDTHH:MM:SS` 后重新执行。
2. 结构校验最初错误预期 `DECIMAL(3,2)` 的内部长度，实际 SQL Server 存储长度为 5 字节；修正验证脚本预期，字段定义不变。
3. Week 4 查询中 Q3 的变量跨越 `GO` 后失效，按 SQL Server 批次作用域重新声明；视图脚本中 `CREATE VIEW` 也调整为批次第一条语句。
4. 人工 SSMS 对账最初把有效预订条件写在 `LEFT JOIN ... ON` 中，导致已取 / 已取消记录没有被正确过滤；改为 `WHERE` 或条件聚合后，商品 1 的有效已订量恢复为 6。
5. 命名实例和 ODBC Driver 18 的加密要求导致复现命令调整为 `localhost\SQLEXPRESS` 和 `-C`；PowerShell 变量大小写不敏感造成的变量覆盖也已修正。

## 7. 实验总结与当前边界

本阶段已经形成可从空库装配的数据库原型：SQLCMD 九步复现退出码均为 0，Week 3 基线复现前后保持一致，SSMS 对象、行数、三本账和权限对象已有人工作证据。现有结果能证明脚本可运行、基础约束生效、查询和视图结果可复算、角色越权被拒绝。

仍需由非作者组员补充或确认的事项包括：按 README 独立复现的记录归档、八类结果证据的 SSMS 截图补齐、现场讲解（如课程要求变更）、以及后续阶段的复杂业务事务、并发、自动过期和重复请求幂等。当前报告不把尚未产生的截图或人工验收写成已通过。
