# AI 使用记录

> 本文记录当周实际工作与当时设计数字。第 1—2 周记载的旧业务编号、表数和外键数属于历史记录；当前实现口径见 `spec-businesses.md` 与 `spec-data-dictionary.md`。

> **性质**：过程留痕（官方第一周任务要求「记录下使用 AI 协助与人工修改」）。
> **记法**：按周记录 —— ① AI 协助了什么；② 人改了什么、由谁裁定。
> **原则**：**AI 只做起草与自查，所有口径由组员裁定**；组员须能解释每条结论的来历。

---

## 第 1 周

### 1 AI 协助的范围

| 环节 | AI 做了什么 |
|---|---|
| 任务拆解 | 从官方任务原文提炼五条子任务的实质要求与硬性约束（→ `task-week-1.md`） |
| 场景 | 起草场景说明：门店档案、经营范围、经营方式、业务规则、边界声明、六类核心对象落点 |
| 角色 | 起草角色与职能清单：4 个主体，每人「能做 / 不能做 / 能看 / 不能看」+ 五条横切约束 |
| 业务 | 起草 15 条业务与 R-1 ~ R-30 规定，并把「业务」与「规定」分开 |
| 数据边界 | 遍历 16 条业务逐条问「这一步动了什么」，得候选信息后判进库 / 不进库并写理由 |
| 自查 | 两轮一致性审查、两轮对照复核、取消盘点后的残留清扫（AI 执行，结果交组员裁定） |
| 规范 | 起草物料结构、命名与去重约定（→ `project-conventions.md`） |

### 2 人工修改与裁定（举例）

| AI 的原稿 | 人工怎么改 |
|---|---|
| 会员分三级、按累计消费评定 | 改为**买卡制**：只有**银卡 / 金卡**两档、一年有效、**不做升级降级** |
| 积分基数表述含混 | 定为**实付金额**；保留**单笔最多抵小计 20%** 的上限 |
| 退货时积分怎么处理未定 | 定：**只退实付，原单用掉的积分不退** |
| 单据没有对外编号 | 增设**单号**；**退货凭单号认单**（非会员同样能退） |
| 保留了「库存盘点」业务 | **取消** —— 数据是虚拟的，账实核对没有对象 |
| 保留了「日常费用登记」 | **取消** —— 店长只能投钱 / 取钱 |
| README 里写了业务范围与设计细节 | 删掉 —— README 只做对外速览，具体内容归 `docs/` |
| 数据边界清单写到字段级 | **打回** —— 本周只到「要记哪些信息」这一层 |
| 文档里带版本记录 / 方法说明 / 证据表 | 删掉 —— `docs/` 只留口径 |
| 同一规则在多份文档各写一遍 | 删去旧出处，只留最新那版（去重原则） |

### 3 结论

- AI 承担**起草、走查与自查**；**每一条口径都由组员裁定**（上表即为裁定记录）。
- 组员能解释任意一条结论的来历：它对应哪条业务 / 规定，以及为什么这样定。
- **未使用 AI 直接生成表结构或 SQL** —— 本周不写 SQL、不建表、不定字段类型。

## 第 2 周

> 本周产出：`docs/spec-data-dictionary.md`（数据字典：19 张表、字段与域、码、样例元组）。
> 过程稿：`drafts/plan-week-2.md`（四个子任务，逐条经 Owner 审定后才迁入 `docs/`）。

### 1 AI 协助的范围

| 环节 | AI 做了什么 |
|---|---|
| 方案 | 按官方四个子任务起草 `drafts/plan-week-2.md`：判断规则、表清单、字段定义、标码、样例策略 |
| 对照 | 把表清单与 `spec-data-boundary.md` 的进库 / 不进库清单**逐条对照**（查漏 / 查多），并回核 `spec-businesses.md` 的 R-1~R-30 状态机与 §4 留痕清单 |
| 字段 | 19 张表逐张铺开：字段名、类型（长度 / 精度）、键、空、默认、**域**、含义 |
| 标码 | 主键判据与 19 张一览、**候选码一览**（逐表说明为何不当 PK）、39 条外键清单（逐条一句话业务含义） |
| 样例 | 一条贯穿故事线的 19 张表样例元组（约 70 行），并做三本账对账（库存累加、积分流水、资金链） |
| 自查 | 全文一致性审查：编号连续、交叉引用无悬空、字段与样例列名逐表比对、死引用清扫 |

### 2 人工修改与裁定（举例）

| AI 的原稿 | 人工怎么改 |
|---|---|
| 主键一律用代理键 `id` | **改用业务键做主键**：`book.isbn`、`toy.inner_code`、`member.phone`、`employee.phone`（账号即手机号）；**单据的单号 / 预定码不做主键** |
| `book` / `toy` 用 `id` 兼外键指向 `goods` | **方向反过来**：`goods` 引用细节表（`book_isbn` / `toy_code` 两个可空外键），细节表用 ISBN / 内部编码做主键 |
| 折扣与金额记在销售单的**行**上 | **钱记在单头**：`subtotal_amount` 原始总额、`discount_rate` 折扣率、`point_deduction_amount` 积分抵扣、`paid_amount` 成交金额；**行只记商品 + 数量 + 成交价** |
| 积分抵扣上限 = **折扣前小计**的 20% | 更正为 **折扣后金额**的 20%（先打折再算上限） |
| 获得积分 = 实付 × 1，未说取整 | 定为 **向下取整**（退货回滚同样向下取整） |
| 预订有效期未定 | 定为 **3 天** |
| 资金流水的"事由"用单号弱引用 / 三个外键（含 `reservation_id`） | 定：**三个可空外键** —— `sale_id` / `request_id` / **`member_phone`**（办卡费挂会员；预订不收款，故不用 `reservation_id`）；注资 / 提现时全空 |
| 库存变动的来源记"类别 + 单号" | 改为**三个可空外键**（`request_id` / `sale_id` / `return_id`），**报损时三者全空**；类别与外键一一对应，原"来源类别"列删除 |
| 商品带封面图（`cover`） | **不做** —— 移入不进库清单 B19（不参与任何判定） |
| §1.2 写成"实体清单" | **打回**：语义不限于实体 —— 先改为"内容清单（待建表的全部内容）"，后按 Owner 要求**整节取消**，改为"**边界清单逐条定性**（哪条建表、哪条做属性）" |
| 子任务 4 做成"完整数据链路演算" | **纠偏**：官方只要"**每张表补几行真实数据看效果**"；链路演算降为**备查**（它只是让样例互相对得上，满足验收第 9 条） |

### 3 结论

- AI 承担**起草、对照、自查**；**每一条口径（主键怎么选、钱记在哪、事由怎么挂、取整与有效期）都由组员裁定**（上表即裁定记录）。
- 组员能解释任意一条结论的来历：它对应哪条业务 / 规定，以及为什么这样定。
- **仍未使用 AI 直接生成表结构或 SQL** —— 本周只到"关系模式 + 样例元组"，建库是第 3 周的事。
