# 后续开发与验收操作指南

本文把已有 review 的未闭环事项转成执行步骤，供接下来逐步开发使用。状态依据仓库当前源码及已保存的验收材料；本次编写指南没有执行数据库操作，也没有重新运行应用测试。

**建议先完成步骤1的 runner 建库完整性，再扩展业务。** 员工登录与门店销售已有实现，应在现有结构上继续，不需要重新搭建认证或重写销售。

当前可以演示：员工登录、退出、身份查询，收银员查询销售商品、预览结算、确认销售、查看本人销售凭证。店长和库管可以登录，但尚无对应业务工作台；顾客端和自动过期任务尚未实现。

已有实现采用“Flask验证员工身份 → 业务层 → 唯一DAO → 受限数据库账号调用过程”。四个服务账号用于后端分工，不是四名员工的个人登录。历史 `db/role.sql` 用于课程授权演示，不应直接作为应用运行账号授权方案。

最近部署记录为22张用户表、52个外码、10个 `api` 过程；其中业务实体仍为19个，其余包含迁移、认证及请求技术对象。后续增加技术对象时另记部署结构，不能机械地把技术表塞进业务ER，也不能继续把这些数量作为永远不变的验收值。

本指南中的开发顺序是建议；尚需选择的实现细节列在第5节，不能将其记成用户已确认的新规则。

## 2 review问题与当前状态对照

为避免与业务编号混淆，下表使用“复核B1”等表示历史工具问题；“业务B1”等表示正式业务。

| 问题 | 当前核对结果 | 接下来如何闭环 |
|---|---|---|
| A1 重复请求无幂等 | **销售已覆盖，其余写入待做**。已有 `api.sale_request` 和销售重试测试 | 每个新写入动作约定请求键、内容一致性、原结果回读；按步骤4—7分别补齐 |
| A2 无自动过期及释放 | **待实现**。手工执行SQL不等于自动任务 | 步骤5实现过期事务、实际调度、失败重试和竞争测试 |
| A3 并发超卖 | **销售内部已覆盖，跨业务待做** | 新增预订、取货、报损等入口前统一锁顺序；验证不同业务抢同一库存或积分 |
| A4 无统一业务入口 | **认证和销售已覆盖，其余业务待做** | 沿用按动作封装的过程及受限授权。`run.ps1` 是工程入口，不能替代业务入口 |
| A5 积分可超额抵扣 | **门店销售已覆盖**，包括负余额、到期及舍入 | 保留现有回归；步骤5到店取货沿用R-7结算规则，不能另造一套算法 |
| A6 非法状态迁移 | **销售创建/重放已有控制，完整状态机待做** | 采购、预订、退款分别列允许迁移；相同请求重试回原结果，不同请求操作非法终态应拒绝 |
| A7 会员入口及收费快照缺失 | **待实现** | 步骤6先落实办理历史结构，再实现开卡、续费、升级及费用/有效期事务 |
| A8 岗位与操作人不匹配 | **登录和销售已覆盖，其他动作待做** | 操作人取自会话，数据库复核岗位/会话版本；不得由表单冒填审批人、收货人等 |
| A9 顾客展示边界缺失 | **待实现**。收银员内部商品接口不是顾客接口 | 步骤5增加顾客专用读取过程/字段清单，仅展示上架商品并验证越权 |
| 复核B1 原Week6入口依赖PS7/默认实例 | **新入口已改善，兼容性验收未完成** | 新runner已在PS5.1、默认实例、ODBC17实测；步骤8补队友电脑、命名实例、ODBC18。不能据此声称旧Week6外壳原样通过 |
| 复核B2 审计器纳入自身清单 | **待处理** | 步骤8明确校验器版本与被校验材料的关系；保留审核时清单，不为消除差异重写历史指纹 |
| 复核B3 变异测试重复且强度不同 | **待处理** | 步骤8对照断言，形成当前维护的共用测试来源；历史实际执行副本继续留档 |
| 复核B4 视图未进入建库验收链 | **仍存在，并影响新runner的空库准备** | 步骤1补安装及对象检查，避免依赖某台电脑源库中恰好已有的对象 |

另外登记当前实现核对发现的三项：

| 新问题 | 证据与影响 | 对应步骤 |
|---|---|---|
| N1 新runner遗漏跨行约束触发器 | `scripts/project_runner.py` 的 `prepare_source()` 清单没有 `constraint.sql`；`dbo.tr_card_type_cross_row` 仅在该脚本创建。新基线不能因数据快照一致就认定约束齐全 | 步骤1 |
| N2 请求日志及错误分类不完整 | 现有基础日志不足以覆盖请求号、时间、动作、用户岗位、错误码和结果；部分约束错误落入通用服务不可用，API默认404/405也需统一 | 步骤3 |
| N3 角色动作和课程CRUD尚未形成完整映射 | 登录页面和销售闭环不等于多角色完整应用；订单/明细的修改、删除与事实不可变规则需要明确对应 | 步骤2、步骤8 |

这里的“销售已覆盖”仅指已保存的销售范围测试，不意味着所有业务已解决。第六周在声明范围内已验收；这些条目用于后续阶段补齐，不把整个第六周改写成未通过。

## 3 分步操作

### 步骤1：补齐runner从零建库的数据库对象

**操作**

1. 对照 `db/README.md`、`schema.sql`、`migration.sql`、`constraint.sql`、`view.sql`，列出当前应用基线必需的表、索引、触发器、视图及后续过程/授权。
2. 调整新阶段准备链，纳入跨行约束触发器及三个历史视图的安装。`constraint.sql` 同时含DDL和回滚测试，`view.sql` 同时含定义和查询；先确认可执行顺序及样例依赖，必要时增加当前阶段专用安装脚本。不要对已经经营的运行库直接套用固定样例测试。
3. 给空库准备增加对象检查：`tr_card_type_cross_row` 存在且启用，`v_sale_detail`、`v_goods_sales_summary`、`v_inventory_status` 存在且可查询，迁移要求的筛选索引齐全，运行过程及授权满足当前清单。
4. 在独立新库运行规则反例，确认金卡费用不高于银卡、金卡折扣率高于银卡均被正确拒绝；不能只检查触发器名称。
5. 同时让准备/诊断明确报告缺失对象，避免旧库恰好完整而新库漏装。

**验收**：从仓库创建的新基线及其新运行副本通过对象和规则检查；缺少必要对象应失败；正反例结束后业务数据恢复。既有运行库是否缺对象需另行只读核对，不能由脚本清单推断所有现有库的实际状态。

**证据**：保存脚本版本、安装顺序、对象清单、合法/非法配置输出、数据恢复结果和runner报告到新的Week7结果目录。58项旧测试通过的历史记录保留，但不作为本项已完成证据。

**推进范围**：复核B4、N1。此步不新增采购、顾客等页面。

### 步骤2：先把角色动作与页面清单落到当前设计

**操作**

1. 以第4节为起点，将每个动作对应到角色、页面/按钮、输入、结果、读取范围、失败情形、后端入口、验收证据。
2. 按收银、库管、店长、顾客组织页面；一个工作台可以承载多个相关动作，无需每表一个页面。
3. 对照课程商品、库存、订单和明细CRUD要求，明确各自对应的业务动作。库存修改通过业务流水；已成交单据通过退货处理，不能开放任意改金额或删除事实。
4. 将“允许编辑/删除的未提交草稿”与“保留的已发生事实”区分。若现行口径没有定案，先记录待决策项，不能用采购草稿删除自动冒充课程销售订单删除要求已满足。

**验收**：每个业务动作都有实现状态和证据位置；每项课程CRUD都有明确映射或待确认差距，不用一个笼统的“已支持增删改查”代替。

**产出**：当前操作覆盖表及页面草图，可并入现有设计；复用已确定的Flask、员工认证和DAO方案。桌面《Web构建契约列表.md》可作为检查索引，其旧路径、旧ER版本和未决标签应先核对，不能作为优先于正式业务文档的新规则。

### 步骤3：补错误处理、请求日志和工作台公共能力

**操作**

1. 在现有分层中统一输入、未登录、无权限、不存在、业务规则、数据库连接、约束和事务错误。分别确定页面提示及API状态/错误码，补齐API 404/405处理。
2. 后端记录请求号、时间、动作、员工/角色或顾客凭证的非敏感标识、错误码、结果；客户端可用请求号反馈问题。口令、完整预定码、连接串、SQL正文和调用栈不进入客户端响应。
3. 建立店长、库管和顾客入口的导航与后端边界；尚未实现的动作不能用可点击按钮伪装成功。
4. 保持运行SQL集中在DAO并参数化；页面校验改善提示，数据库在事务内完成最终规则判定。单一业务口径不排斥各层承担不同校验职责。

**验收**：正常请求、越权、找不到对象、约束冲突和连接故障均返回约定结果；日志能按请求号定位，响应不泄露内部信息；现有销售及会话失效回归保持通过。

**产出**：错误映射表、日志示例、关键边界验证结果。闭环N2，并为A4、A8的扩展提供基础。

### 步骤4：打通货线——建档、采购、收货与报损

**操作顺序**

1. 业务B11商品与库存查询、B12库存变动查询：先让员工看到角色允许的数据及单据来源。
2. 业务B1商品建档、定价与上下架：库管建档/报当前供应商报价，店长定价、上架、调价、下架。售价留空的新商品不可成交；不增加定价申请业务。
3. 业务B2商品采购：草稿和明细 → 提交 → 店长审批 → 店长一次付款 → 库管一次足量收货。取消只按R-5允许的阶段执行，审批后不能取消。
4. 业务B3商品报损：必填文字原因，只扣未被预订占用的数量，写入库存变动。
5. 每个写入动作同时接入请求幂等、状态判定、可信操作人和事务。资金余额链、库存计数的锁顺序须与既有销售兼容。

**验收**：库管建商品、店长上架和付款、库管收货、收银员销售形成完整闭环；重复付款/收货只记一次；未付款收货、审批后取消、越权定价、报损占用库存均拒绝；失败后单据、资金、库存及请求结果不留半笔。

**证据**：三岗位操作路径、正常/错误结果、付款及入库对账、中途故障回滚、收货/报损与销售相关竞争结果。推进A1、A3、A4、A6、A8及N3。

### 步骤5：打通顾客预订、取消、取货和自动过期

**操作顺序**

1. 顾客商品列表只显示上架商品和公开字段；无可售量显示暂时无货。不要直接暴露内部库存接口的全部字段。
2. 业务B5线上预订与取消：创建预订、生成预定码、凭手机号和预定码查单/取消；收银员代取消单独验证岗位。预订和取消不产生资金流水。
3. 业务B6到店取货：只支持整单；按取货时售价和权益结算，复用既有销售结算规则；预订终态、销售、已订量释放、库存、积分、资金在同一事务内完成。
4. 实现过期处理过程，并接入能实际运行的调度。按机器条件选择Windows任务计划或其他明确维护的worker；不能假定Express一定有SQL Server Agent。
5. 明确调度账号最小权限、执行间隔、失败记录、重试和停用方法。并发时过期、取消、取货只能有一个合法终态，重复运行不会重复释放。

**验收**：顾客完成浏览→预订→查询；收银员完成取货结算。另有取消和实际调度过期路径；验证临界时间、竞争、相同请求重试和不同请求终态拒绝。库存总量、已订量和有效预订明细对账，取消/过期没有资金/积分流水。

**特别处理**：历史样例中有刻意保留的“过期但仍有效”边界数据。先为应用测试准备相对日期样例和可控制的测试时钟；自动任务只运行于明确选定的当前应用库，不触碰Week6历史证据或基线来源库。用过的运行库不能继续要求业务行数永远等于历史样例。

**证据**：顾客字段边界、预订凭证校验、结算快照、真实调度配置/日志及多连接竞争输出。闭环A2、A9，扩展A1、A3—A6、A8。

### 步骤6：补会员办理与档位配置

**操作顺序**

1. 先确定办理历史的存储：应能复核办理动作、办理时档位/费用、实收、前后有效期、操作人及资金来源关系；评估新增历史表或扩展结构的迁移方案。
2. 业务B8会员办理：依次实现开卡、同档重买/续费、有效银卡升级、过期后重买；计算依据R-17、R-18、R-24，收费和权益更新同事务。
3. 业务B9会员卡档位配置：店长维护当前两档参数，跨行约束继续有效；不回改过去的办理记录和销售快照。
4. 补会员归属验证后的销售/积分自助查询；归属验证方式见第5节，不能仅输入手机号就认为身份可信。

**验收**：闰日、到期当天、过期、负积分、升级差价、续期起算、重试和并发办理符合正式规则；店长改当前参数后历史收费仍能解释；非本人数据不可查询。

**证据**：结构变更及恢复方案、日期和费用案例、历史快照对照、资金/权益事务测试。闭环A7，并扩展A1、A5、A8。

### 步骤7：补退货、员工管理、资金和盈亏

**操作顺序**

1. 业务B7商品退货：先落实收银退款与库管实物回收的交接设计，再实现按原单/原行的部分退货、累计数量限额、退款与积分回滚、库存回收。各阶段的事务边界和失败恢复必须说明。
2. 退货使用R-25累计比例算法；全退累计金额和回滚积分准确归零到原单目标，不返还已抵扣积分，不生成零额资金/积分流水。不能用修改原销售单金额代替退货。
3. 业务B10员工与账号管理：提供店长业务入口；角色变更、停用和重置口令使旧会话失效。已有凭据管理CLI可保留，不能视为店长页面已经完成。
4. 业务B14资金收付登记：核对采购、销售/取货、退货、办卡自动收付；店长独立操作仅注资/提现。
5. 业务B15盈亏查询：分别展示经营盈亏与现金余额，并能回溯来源；沿用R-15/R-16，不增加未确认的日常费用或会计毛利业务。

**验收**：两人同时退同一原行不会超退；重复退款和回收入库不会多记；伪造库管操作人被拒；负积分规则正确。店长改岗/停用后旧会话不可继续操作；资金自动记录齐全，两项指标能逐笔核对。

**证据**：跨岗位交接、部分/全退及舍入案例、并发和故障恢复、会话失效、资金汇总及明细对账。推进A1、A3、A4、A6、A8，完成其余角色动作。

### 步骤8：收尾工具问题，做队友换机与课程交付验收

## 6 每完成一步怎样验证与留证

### 6.1 日常命令

在仓库根目录执行，当前已有环境不需要反复setup：

```powershell
.\run.ps1 doctor
.\run.ps1 test -Unit
.\run.ps1 test
.\run.ps1 start
```

保持start终端开启，在另一终端执行：

```powershell
.\run.ps1 verify -Http
```

执行策略阻止脚本时，对单次命令使用以下方式，其余命令同理：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\run.ps1 doctor
```

端口已有服务时先确定它属于哪个配置，避免重复启动。使用临时端口时start与verify必须一致。首次换机准备、命名实例和独立配置参数见[统一入口说明](unified-entry.md)。这些命令的通过范围取决于已纳入的检查，新增功能必须补相应检查，不能靠旧58项测试替代。

### 6.2 写入动作的验收清单

- 正常路径：页面可完成动作，单据、库存/已订量、积分、资金、操作人及时间相互对得上。
- 输入与权限：非法数量/金额、未登录、错误岗位、他人数据、失效会话得到对应拒绝，客户端无内部信息泄露。
- 状态与幂等：同键同内容返回原结果，同键不同内容拒绝，不同请求不能越过允许的状态迁移。
- 事务：在关键写入之间注入故障，单头、明细、流水、计数和成功请求结果不残留半笔。
- 竞争：按动作选择真正相关的多连接场景，如销售与预订抢末件、取消与取货竞争、重复收货、累计退款竞争；不能只串行调用两次冒充并发。
- 清理与隔离：测试只用专用库/账号；业务数据恢复，临时凭据和故障对象清理，运行配置不变，历史来源不被写入。

只读页面重点验证字段、过滤、归属、岗位和错误响应，不需要套用全部写入测试。低风险文档/布局调整也无需机械增加业务测试。

### 6.3 证据与状态更新

每次保留以下内容：实际执行者、源码版本/指纹、环境和目标库、步骤命令、预期/实际、原始输出、清理结果及未验证范围。新增结果放 `db/results/week-7/` 下能识别本次事项的目录，`.runner/` 中选择必要的无秘密报告归档；不要提交本地口令或连接秘密。

测试新增后项数可以变化，报告应写本次实际计数。对象检查与业务指纹是两类证据，不能互相替代。预期故障日志中的异常也不能直接判为整轮失败，应核对断言和退出码。

旧Week6结果、清单、执行元数据及已归档测试保持其历史含义。源码变化应说明审核时版本与当前版本，不通过刷新旧清单掩盖差异。保留库/备份的资源名和用途，后续维护按明确资源清单处理，不在runner里加入隐式覆盖或删库。

只有“实现完成 + 对应验证通过 + 证据归档”才更新问题状态；AI执行与人工签收分别记录。指南提出的任务本身不是实现或验收证据。
