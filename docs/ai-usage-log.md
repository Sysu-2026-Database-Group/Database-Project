# AI 使用记录

**性质**：过程留痕（官方要求「记录下使用 AI 协助与人工修改」）—— 只记录**当周实际发生**的工作。
**记法**：按周记三件事 —— ① AI 协助了什么；② 人改了什么、由谁裁定；③ 怎么验证的。
**原则**：AI 可按授权起草、修改、执行测试及整理材料；业务口径由组员裁定，执行归属与未验证范围如实记录，组员须能解释结论依据。

> 第 1—2 周记的是**当时**的业务编号与设计数字（如 R-1 ~ R-30、39 条外键、约 70 行样例）；
> 现行口径见 `docs/specs/spec-businesses.md` 与 `docs/specs/spec-data-dictionary.md`（现为 R-1 ~ R-26、47 条外键、77 行样例）。

## 第 1 周

本周产出：`spec-scenario.md`（场景）· `spec-roles.md`（角色与职能）· `spec-businesses.md`（业务与规定）·
`spec-data-boundary.md`（数据边界），以及 `task-week-1.md`（任务说明）与 `project-conventions.md`（物料与命名规范）。
按官方要求，**本周不写 SQL、不建表**。

### 1 AI 协助的范围

| 环节 | AI 做了什么 |
|---|---|
| 任务拆解 | 从官方任务原文提炼五个子任务的实质要求与硬性约束（→ `task-week-1.md`） |
| 场景 | 起草场景说明：门店档案、经营范围、经营方式、业务规则、边界声明、六类核心对象落点 |
| 角色 | 起草角色与职能清单：4 个主体，逐个写「能做 / 不能做 / 能看 / 不能看」，另立五条横切约束 |
| 业务 | 起草 15 条业务与规定，并把「业务」（一串动作）与「规定」（口径约束）分开（当时编号 R-1 ~ R-30） |
| 数据边界 | 遍历当时的 16 条业务，逐条问「这一步动了什么」，得到候选信息后判进库 / 不进库并写明理由 |
| 规范 | 起草物料结构、命名与去重约定（→ `project-conventions.md`） |
| 自查 | 两轮一致性审查、两轮对照复核，以及取消「库存盘点」后的残留清扫；AI 执行，结果交组员裁定 |

### 2 人工修改与裁定

| AI 的原稿 | 组员怎么改 |
|---|---|
| 会员分三级、按累计消费评定 | 改为**买卡制**：只有**银卡 / 金卡**两档、一年有效、**不做升级降级** |
| 积分基数表述含混 | 定为**实付金额**，并保留**单笔最多抵小计 20%** 的上限 |
| 退货时积分怎么处理未定 | 定为**只退实付，原单用掉的积分不退** |
| 单据没有对外编号 | 增设**单号**；**退货凭单号认单**（非会员同样能退） |
| 保留了「库存盘点」业务 | **取消** —— 数据是虚拟的，账实核对没有对象 |
| 保留了「日常费用登记」 | **取消** —— 店长只能投钱 / 取钱 |
| README 里写了业务范围与设计细节 | 删掉 —— README 只做对外速览，具体内容归 `docs/` |
| 数据边界清单写到字段级 | **打回** —— 本周只到「要记哪些信息」这一层 |
| 文档里带版本记录 / 方法说明 / 证据表 | 删掉 —— `docs/` 只留口径 |
| 同一规则在多份文档各写一遍 | 删去旧出处，只留最新那版（去重原则） |

### 3 验证与结论

- **AI 做了什么**：起草上述四份口径文档与两份规范，并做走查与自查。
- **人改了什么**：上表即裁定记录 —— 每一条口径都由组员定案（含两处业务被取消、一处清单被打回）。
- **怎么验证的**：AI 的**两轮一致性审查 + 两轮对照复核**结果交组员逐条核对，核对通过的稿件才标注「已敲定」；
  组员能解释任意一条结论的来历 —— 它对应哪条业务 / 规定、为什么这样定。
- **本周边界**：未写 SQL、未建表、未定字段类型（字段类型属第 2 周）。

### 2 人工修改与裁定

| AI 的原稿 | 组员怎么改 |
|---|---|
| 主键一律用代理键 `id` | **改用业务键做主键**：`book.isbn`、`toy.inner_code`、`member.phone`、`employee.phone`（账号即手机号）；**单据的单号 / 预定码不做主键** |
| `book` / `toy` 用 `id` 兼外键指向 `goods` | **方向反过来**：`goods` 引用细节表（`book_isbn` / `toy_code` 两个可空外键），细节表用 ISBN / 内部编码做主键 |
| 折扣与金额记在销售单的**行**上 | **钱记在单头**：`subtotal_amount` 原始总额、`discount_rate` 折扣率、`point_deduction_amount` 积分抵扣、`paid_amount` 成交金额；**行只记商品 + 数量 + 成交价** |
| 积分抵扣上限 = **折扣前小计**的 20% | 更正为 **折扣后金额**的 20%（先打折再算上限） |
| 获得积分 = 实付 × 1，未说取整 | 定为 **向下取整**（退货回滚同样向下取整） |
| 预订有效期未定 | 定为 **3 天** |
| 资金流水的「事由」用单号弱引用 / 三个外键（含 `reservation_id`） | 定：**三个可空外键** —— `sale_id` / `request_id` / **`member_phone`**（办卡费挂会员；预订不收款，故不用 `reservation_id`）；注资 / 提现时全空 |
| 库存变动的来源记「类别 + 单号」 | 改为**三个可空外键**（`request_id` / `sale_id` / `return_id`），**报损时三者全空**；类别与外键一一对应，原「来源类别」列删除 |
| 商品带封面图（`cover`） | **不做** —— 移入不进库清单 B19（不参与任何判定） |
| §1.2 写成「实体清单」 | **打回**：语义不限于实体 —— 先改为「内容清单（待建表的全部内容）」，后按组员要求**整节取消**，改为「**边界清单逐条定性**（哪条建表、哪条做属性）」 |
| 子任务 4 做成「完整数据链路演算」 | **纠偏**：官方只要「**每张表补几行真实数据看效果**」；链路演算降为**备查**（它只是让样例互相对得上，满足「样例自洽」这一条） |

### 3 验证与结论

- **AI 做了什么**：起草方案、铺字段、标码、写样例，并做全文一致性审查。
- **人改了什么**：上表即裁定记录 —— 关键口径（**主键怎么选、钱记在哪、事由怎么挂、取整与有效期**）都由组员定案。
- **怎么验证的**：把表清单与上游边界清单**逐条对照**（查漏 / 查多），并把发现的不一致**回填上游文档**；
  样例按三本账自洽（在架 = 变动累加 · 积分 = 流水之和 · 资金首尾相接）之后，才随字典一并迁入 `docs/`。
- **本周边界**：交付的是**设计**（关系模式 + 样例元组），**没有生成 SQL、没有建库**；
  表结构由 AI 起草，但**逐条经组员审定**（上表即审定记录）后才落进字典 —— 建库与执行在第 3 周。
