# Web 验收标准（v1.0）

- 日期：2026-11-06
- 适用范围：第 7—9 周 Web 构建的审查、修复验收与阶段交付
- 依据：`homework/第7-9周任务讲解.md`、项目冻结口径、用户已确认决策
- 用法：每条问题/每批修复/每次发布，都按本文件判定，不以"改好了"作为结论

## 一、标准来源（三层）

| 层 | 来源 | 作用 |
|---|---|---|
| 权威层 | 课程任务书（目标、任务 1–7、阶段作业、展示重点） | 判断"该做的有没有做" |
| 项目层 | DB 冻结口径：21 实体、受限账户、DAO 唯一 SQL 出口、不改历史迁移、不新增触发器 | 判断"是否越界、是否破坏基线" |
| 决策层 | 用户确认：三无商品可删、成交后冻结、跨机已完成、O4–O7 不修 | 把争议项变成已裁定项 |

## 二、三轴标准

### A. 内容全面性（12 条）

| 编号 | 标准 | 判定方式 |
|---|---|---|
| A1 | 四层结构（页面→业务→数据访问→数据库） | 能指出各层文件，调用链单向 |
| A2 | 数据访问层是唯一 SQL 入口 | 路由/业务层无 `cursor.execute`、`pyodbc.connect` |
| A3 | 登录、商品、库存、订单四类功能 | 功能入口存在且可用 |
| A4 | 四类对象查询/新增/修改/必要删除 | 逐对象核对，删除口径见决策层 |
| A5 | 至少店员与顾客两类角色 | 角色入口与权限矩阵存在 |
| A6 | 五类失败：参数、未登录、无权限、连接失败、约束冲突 | 逐类实测，有状态码与友好提示 |
| A7 | 权限三层一致（页面、后端、数据库账户） | 越权请求被后端拒绝，账户非 dbo |
| A8 | 统一异常与日志 | 错误分类、统一响应、请求编号、日志字段齐全 |
| A9 | 沿用 v1.0 数据库 | 迁移/表/主外键/样例与冻结版本一致 |
| A10 | 交付物清单 | 代码、脚本、结果、报告、ai_log、分工齐全 |
| A11 | 空环境可复现 | 新库 setup→doctor→test→start→verify 通过 |
| A12 | 展示重点 | 登录+CRUD 可演示、无拼接 SQL、异常可控、角色差异 |

### B. 任务完成度（6 条）

| 编号 | 标准 | 判定方式 |
|---|---|---|
| B1 | 完成定义明确 | 每项有退出条件，不用页面壳/规划冒充完成 |
| B2 | 动作落真实库 | 全流程经 SQL Server，不用 mock 替代 |
| B3 | 缺口登记规范 | 缺口有记录与影响；**登记 ≠ 满足** |
| B4 | 里程碑不降低门槛 | P0–P6 阶段产物不等于最终完成 |
| B5 | 依赖闭合 | 付款依赖注资、取货依赖预订等链不断 |
| B6 | 实现-测试-证据同源 | 含源码指纹，旧测试不能替代新功能验收 |

### C. 质量与严谨性（10 条）

| 编号 | 标准 | 判定方式 |
|---|---|---|
| C1 | 架构质量 | 单一 SQL 出口、依赖单向、规则不重复实现 |
| C2 | 一致性与并发 | 原子性、幂等、余额链、锁顺序、任务真实运行 |
| C3 | 数据语义 | Decimal、快照不回写、枚举不外露、尾差防御 |
| C4 | 安全 | 全参数化、最小权限、秘密不入日志/URL、404 防枚举 |
| C5 | 错误与可观测 | 统一分类、用户可见边界、requestId 可定位 |
| C6 | 测试质量 | 真实库、多连接、边界值、预期值外部可查 |
| C7 | 可维护与复现 | 模块化、配置外置、文档与代码一致 |
| C8 | 交付质量 | 手册可操作、报告如实、证据六要素 |
| C9 | 技术对象不写死 | 表数/外码数/索引数以当次部署为准 |
| C10 | 动库纪律 | 增量迁移 + ER/字典同步，不改历史迁移含义 |

## 三、验收层级

| 层级 | 判据 | 出口 |
|---|---|---|
| 条目验收 | 判据 + 验证方式 + 预期值 + 证据 + 回归不退化 | 单项 PASS |
| 批次验收 | 该批条目全部 PASS，无新增 FAIL | 里程碑通过 |
| 发布验收 | 新库 setup、全量测试、HTTP 验证、关键页截图、文档一致、打标签 | 可交付 |

## 四、判定规则

| 判定 | 含义 |
|---|---|
| PASS | 判据全部满足，且回归（119 项）不退化 |
| FAIL | 有复现步骤与证据，登记为问题，不修不得判过 |
| BLOCKED | 无法安全构造（如 500），写明原因与所需条件，不冒充通过 |
| 登记 ≠ 满足 | 记录缺口不等于完成；必需项有差距只能标"带差距交付" |

## 五、证据模型（六要素）

```text
执行者 / 环境（库、端口、版本）
命令或操作步骤
预期值（外部可查）
实际输出
原始证据（截图、日志、结果 JSON）
未测范围（如实列出）
```

证据落位约定：

```text
结构化结果   .runner/<运行>/summary.json、results.json
截图         drafts/assets/<批次>/
结果归档     db/results/week-7/<批次>/
追溯         git log <基线>..HEAD
```

## 七、使用方式

1. **开项**：先把问题写成"判据 + 验证方式 + 预期值"，再动手；
2. **验收**：按条目→批次→发布逐层判，不跳层；
3. **例外**：无法验证的写 BLOCKED 并注明条件，不写"应该没问题"；
4. **复核**：任何 PASS 必须能由第二人按证据独立重跑。
