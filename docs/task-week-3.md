## 1. 任务原文

> 第三周任务 ch3 DDL与数据修改
> ==================
>
> 1\. 本周目标
> --------
>
> 使用SQL脚本从空数据库开始创建商品、库存、订单和订单明细等业务对象，完成基础数据的新增、修改、删除和查询
>
> 2\. 任务
> ------
>
> 1.  创建数据库与数据表：创建数据库，根据第二周的数据字典，为商品、库存、订单等先前设计的核心对象选择合适的数据类型并创建表。
> 2.  定义表结构：按照第二周为每张表确定字段名、数据类型、长度或精度、是否允许为空、默认值及字段含义。设置数据约束，定义主键、候选码、外键、非空约束、默认值和检查约束，保证商品、库存和订单之间的数据关系正确。
> 3.  添加样例数据：把第二周编写的样例元组转换为 INSERT 语句，使各表都有能够支持后续查询和测试的数据。
> 4.  完成增删改查：至少对商品、库存和订单相关数据分别完成插入、查询、修改和删除操作。
> 5.  验证脚本可复现：在空数据库中按说明重新执行脚本，确认能够得到相同的表结构和样例数据。
>
> 3\. 本周作业
> --------
>
> *   建库与建表脚本：包括数据库创建、核心数据表创建以及必要的数据类型说明。
> *   插入样例数据脚本：为核心表插入能够体现业务联系的样例数据。
> *   CRUD 脚本与结果：展示典型的新增、查询、修改、删除操作及执行前后的结果。
> *   复现说明：写明脚本执行顺序和从空数据库开始运行的方法。
>
> 4\. 提示与常见问题
> -----------
>
> *   先创建被外码引用的表，再创建引用它的表；删除时通常按相反顺序处理。
> *   字符串、日期和数值要使用合适的数据类型，不要把所有字段都定义成字符型。
> *   插入的样例数据尽量多一些，以便之后的实验。
> *   DELETE 和 UPDATE 必须先确认 WHERE 条件，建议先用相同条件执行 SELECT 检查目标行。
> *   样例数据要能够体现表之间的联系，不要让订单明细引用不存在的订单或商品。
> *   AI 可以协助生成候选 SQL，但必须逐句检查表名、字段名、数据类型和执行结果，并记录人工修改。

## 2. 本组任务与交付

| 任务 | 要完成的内容 | 交付位置 |
|---|---|---|
| 建库建表 | 按 `spec-data-dictionary.md` 建立 19 张表；商品与库存计数同在 `goods`，退货为单头与明细；字段类型、空值、默认值、主码、候选码和外码与数据字典一致。店长维护的当前档位参数建 `card_type` 表；积分换算规则不建表 | `db/schema.sql` |
| 样例数据 | 将数据字典的样例元组转为可重复插入的 SQL，保留原主键对应关系，并核对库存、积分和资金三条账 | `db/sample-data.sql` |
| CRUD 演示 | 商品、库存相关记录、订单各展示新增、查询、修改、删除；修改和删除前先用同条件查询目标，演示在事务中执行并回滚，避免破坏样例基线 | `db/crud.sql`，实际结果记在 `db/results/week-3.md` |
| 复现 | 写环境、版本、空库起点、脚本顺序、执行方式、每步预期结果、校验 SQL 与常见失败处理；让非作者组员按文档独立复现 | `db/README.md` |
| AI 使用留痕 | 若使用 AI 生成候选 SQL，写明候选范围、人工核对和修改；只记录真实发生的工作 | `docs/ai-usage-log.md` 的 Week 3 条目 |

**约束安排**：官方 Week 3 已要求主键、候选码、外键、默认值和检查约束，应在 `schema.sql` 中实现基础约束。Week 4 的 `constraint.sql` 用于补充跨表或业务层验证、非法数据反例及复核，不应重复建立同名约束。跨行汇总、累计退货上限与流水对账不能只靠普通 `CHECK` 实现，需明确写出事务逻辑或验证查询。

**复现说明采用 Markdown 文档**：放在 `db/README.md`，因为它紧邻脚本且是进入 `db/` 的入口。执行截图或输出记录放 `db/results/week-3.md`；记录未产生前不得把计划写成通过结果。

## 3. 验收标准

以下为本组的检查清单。只有实际执行并保留结果后才能标记通过；尚未编写或尚未运行的脚本保持“待验证”。

| # | 检查项 | 通过证据 |
|---|---|---|
| 1 | 交付完整 | `db/schema.sql`、`db/sample-data.sql`、`db/crud.sql`、`db/README.md` 和实际 CRUD 结果均在仓库中；文件之间的执行顺序一致 |
| 2 | 表结构与数据字典一致 | 实际建成 19 张表；逐表核对名称、字段、类型、可空、默认值、主码、候选码和外码；`goods` 保存商品与库存计数，退货有单头和明细，`card_type` 保存当前档位参数 |
| 3 | 约束生效 | 主码、候选码、外码、非空、默认值和可在单行判断的域约束实际生效；用合法与非法插入验证。跨表或跨行规则另用事务逻辑和校验查询验证，不能声称 `CHECK` 已覆盖 |
| 4 | 样例数据可装载 | 所有表的样例元组能插入，主键和外键指向与数据字典对应；退货单总额等于明细之和，退款与积分回滚指向本次退货，库存、积分、资金三条账可复核 |
| 5 | 商品、库存、订单 CRUD | 三类对象各有 INSERT、SELECT、UPDATE、DELETE 的演示和执行前后结果；UPDATE/DELETE 前用同一条件 SELECT 确认目标；不回改历史成交与流水，不手调库存或积分余额 |
| 6 | 从空库复现 | 非作者组员按 `db/README.md` 从空库顺序执行，记录环境、命令、结果和遇到的问题；重新从空库再执行一次，结果一致。未实际执行不得填写通过 |
| 7 | 现场说明与 AI 留痕 | 能解释每段 SQL 对应的业务和约束；若用了 AI，留有候选 SQL 的范围、人工修改及验证记录 |
