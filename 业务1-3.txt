★ 本次敲定（2026-09-15，业务 1-3 封板）
【总则】
1. 供应商为字符串，不做实体
2. 采购：审批通过 -> 付款 -> 立即入库（秒送到，无收货差异、无独立收货单）
3. 报损：业务 1-3 不做
4. 审计：不做 —— 不记任何操作人（申请人 / 审批人 / 收银员）
5. 销售订单 / 销售历史：不做（归业务四）
6. 会员系统：细节归业务六，本次只留动作接口「查询会员信息」
7. 库存只维护两个计数：在库 = 架上总量（盘点基准）；可售 = 在库 - 预定（派生，不存列）
8. 库存变动记录：不做（归业务七）
【库存定式】入库 在库+N / 预订 预定+N（在库不变）/ 取货 在库-N、预定-N / 销售 在库-N
【资金变动原因取值】采购付款 / 销售收款 / 会员卡费
【另行归属】销售历史 -> 业务四；会员细节 -> 业务六；库存变动记录、报损 -> 业务七；退款 / 注资 / 提现 / 日常费用 -> 业务四、八
说明：下文凡以「→ 敲定：」开头的行为本次追加，原句一律保留未动。

业务一：商品采购
逻辑链路：库管申请->店长审批->资金计算->货物入库
涉及实体：
1. 申请BuyRequest
2. 资金BankAccount
3. 商品信息数据库GoodsDataset
4. 商品Goods，包括如下5、6点
5. 书Book
6. 文创Toy
角色&操作：
1. 库管（查询、申请）
2. 店长（同意/拒绝申请）
注：
1. 采购商不作实体，仅以string形式出现
2. 假设采购在付款后秒送到，可瞬间入库
具体实体数据结构：
1. BuyRequest：单号id，供应商producer，是否通过is_accepted，申请时间apply_time，[商品(Book/Toy)，数量，价格] x N
→ 敲定：is_accepted 为空 = 未审批（保持布尔，不加三态、不加审批人/时间）；行内「商品」引用 ISBN 或 Toy 内部编码
2. BankAccount：总金额数money_count、盈亏历史[金额变动、原因、时间、变动前后金额]
→ 敲定：该历史记录的是资金变动；原因取值 = 采购付款 / 销售收款 / 会员卡费（「经营盈亏」按口径另行计算）
3. GoodsDataset：[商品，在库数量，预定数量，当前售价]
→ 敲定：在库 = 架上总量（盘点基准）；可售量 = 在库 - 预定（派生，不存列）；入库前提是该商品已在此有行
注：不做损坏商品相关问题
4. Goods：Book + Toy，不做真实实体，仅成为概念逻辑
5. Book：名字name，作者author，出版社publisher，初版年份publish_year，ISBN
6. Toy：名字name，品牌brand，生产日期produce_time，内部编码goods_code（选做：款式，SN码）
→ 敲定：内部编码为本次新增，与 ISBN 并列作为被引用的商品编码

业务二：商品线下销售
逻辑链路：顾客选择->收银员结算->会员积分、库存、资金更新
→ 敲定：结算落三件事 —— 库存 在库-N；资金 +实收（原因=销售收款）；积分走接口（细节归业务六）。买会员卡：资金 +卡费（原因=会员卡费）。不生成订单（归业务四）
涉及实体：
1. Book
2. Toy
3. 会员系统MemberSystem
4. GoodsDataset
5. BankAccount
角色&操作：
1. 顾客（查询，选择并购买，买会员卡，查询会员积分和有效期）
注：成为会员需要购买会员卡，一年有效。不再是根据累计消费金额评定
2. 收银员（结算）
具体实体数据结构：（部分内容需要与业务一一致）
1. Book：名字name，作者author，出版社publisher，初版年份publish_year，ISBN
2. Toy：名字name，品牌brand，生产日期produce_time，内部编码goods_code（选做：款式，SN码）
3. MemberSystem：会员信息[会员id，会员等级，姓名，生日，电话号码，会员卡有效期，会员积分]
→ 敲定：本次不定（归业务六）；业务二 / 三仅留动作接口「查询会员信息」
4. GoodsDataset：[商品，在库数量，预定数量，当前售价]
5. BankAccount：总金额数money_count、盈亏历史[金额变动、原因、时间、变动前后金额]

业务三：商品线下取货
逻辑链路：顾客请求->收银员确认->收银员结算（同业务二）
→ 敲定：取货 = 在库-N、预定-N（书离店）；资金 +实收（原因=销售收款）；积分走接口；核销前先查预定状态，已取 / 已过期 / 已取消一律拒绝
涉及实体：
1. 预定系统（至少包含唯一预定码和手机号）具体由后续业务涉及，本处仅作对最低要求
2. 同业务二
角色&操作：
1. 顾客（提交预定码和手机号，购买）
2. 收银员（查询并核对预定系统，结算）
具体实体数据结构：（仅列举新增数据结构，已有定义且无冲突的不再列举）
1. 预定系统：预定码lock_id，手机号phone_number，姓名member_name，预定码有效期lock_ddl，状态status（有效/已取/已过期/已取消），[商品(Book/Toy)，数量] x N
→ 敲定：状态为本次新增，用于拒绝重复核销与过期核销
