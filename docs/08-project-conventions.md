# 08 · 项目规范（物料结构与协作约定）

> 本文档规定**物料放哪儿、怎么命名、怎么流转**。
> 项目速览见根目录 `README.md`，业务与设计口径见 `spec-scenario.md` / `spec-roles.md` / `spec-businesses.md`。

---

## 1. 物料结构

```text
Database-Project/
├─ README.md       项目速览（对外展示的唯一入口）
├─ docs/           正式文档 —— 已经被敲定的口径
├─ drafts/         草稿 —— 讨论稿 / 对照表 / 评审稿
├─ homework/       课程官方材料 —— 每周底线任务（原文件）
└─ db/             建库脚本 —— 可直接在 SQL Server 执行的 SQL
```

| 目录 | 装什么 | 准入标准（能不能放进去） |
|---|---|---|
| `docs/` | 正式文档 | 内容**已经被敲定**，可作为项目当前口径 |
| `drafts/` | 草稿 | 还在讨论、还没拍板的一切草稿 |
| `homework/` | 课程材料 | **课程官方原文件**，不做二次加工 |
| `db/` | 建库脚本 | **能直接执行**的真实 DDL，不放过期草稿 |

> 「敲定」= 当前统一的判断标准，**不是冻结**；后续仍可修订，修订痕迹写进文首的版本说明。

---

## 2. 各目录规则

### 2.1 `docs/` —— 正式文档

- 命名 `NN-<主题>.md`（两位编号，见 §3）。
- **例外**：按周整理的文档命名为 `task-week-N.md` / `plan-week-N.md`（N = 1…17），
  不带编号前缀，也不占 §3 的编号。
  - `task-week-N.md` = **任务说明**：只保留四块 —— 官方任务原文 · 任务拆解 · 任务说明 · 验收标准。
    **不记录完成情况** —— 成果沉淀到正式文档，讨论过程留在 `drafts/`。
  - `plan-week-N.md` = **本组的预设草案**：我们打算怎么做（执行步骤、待决问题、分工等），草案性质。
- **只留最新版**：`docs/` 里的文档**只写当前口径** —— 修订时**直接改正文**，
  **不留版本记录、不写改动摘要、不保留旧说法**。
  （"为什么变成现在这样"去 `drafts/` 看，过程留在那里。）
- 这里是**唯一可以被 `db/` 脚本与测试用例引用的口径来源**。

### 2.2 `drafts/` —— 草稿

- 命名不限：`<主题>.txt` / `<主题>.md`。
- 收录：讨论稿、数据结构对照表、评审意见、原始需求摘录，
  以及**尚未通过审查的旧稿**（如 `00-overview.md` / `01-scenario.md` / `07-test-plan.md`）。
- **双向流转**：
  - 草稿被敲定 → 迁入 `docs/`（自成一份，或并入既有正式文档）；
  - `docs/` 里的文档若需重修 → 退回 `drafts/` 逐份审查，通过后再迁回。
- 原稿一律留在 `drafts/`，便于回溯讨论过程。
- 铁律：`drafts/` 里的任何结论都**不是当前口径**，不得作为 `db/` 与测试的依据。

### 2.3 `homework/` —— 课程官方材料

- 只放课程下发的**原文件**：不改名、不分拆、不转格式（保留原始 `docx`）。
- 命名 `第N周-<原名>`（当前 `第一周任务讲解.docx` 等已符合）。
- 从材料里提炼出的结论**不写在这里** —— 先落到 `drafts/`，敲定后再进 `docs/`。

### 2.4 `db/` —— 建库脚本

- **一个实体一个文件**，文件名与实体名一致、首字母大写：
  `Book.sql` / `Toy.sql` / `GoodsDataset.sql` / `BuyRequest.sql` / `BankAccount.sql` / `Reservation.sql`。
- 每个文件自包含，按固定顺序排布：
  `DROP` → `CREATE` → 约束与注释 → 样例数据 → 验证查询。
- 建库顺序（依赖关系）：

  `Book`（自带 `publisher`）→ `Toy` → `GoodsDataset` → `BuyRequest` → `BankAccount` → `Reservation`

- 视图 / 触发器 / 存储过程 / 种子数据等增量脚本**暂不拆子目录**，先平铺；
  数量增长后再在 `db/` 下分层。

## 4. 提交前自检

1. 新增内容落在**正确的目录**（未敲定 → `drafts/`；已敲定 → `docs/`；可执行 → `db/`）。
2. 改动了 `docs/` 的结论时，**直接改正文** —— `docs/` **不留版本记录 / 改动摘要**（见 §2.1）。
3. **写新规则前先搜一遍**：这条规则是不是已经在别处定过了？（见 §5）
4. `.codebuddy/`、`课堂练习/` 不进版本控制（见 `.gitignore`）。

---

## 5. 去重原则

**同一规则只在一处定案。** 发现重复时：

- **保留最新那版**（正式文档的**正文**），**删去旧出处**；
- 旧出处若还有导航价值，就**只留一行指针**（"见 §X"），**不复述内容**；
- **"定案记录 / 变更历史"类章节不算口径** —— 口径只在正文。这类章节要么删掉，要么只解释
  "为什么变成现在这样"，**不与正文同步**。

**判据**：同一句话在两份文档里各写一遍，改动时必然漏掉一处 —— 那就叫**重复**，不叫"冗余但无害"。

> 例：同一规则若在 A 文件的「定案记录」和 B 文件的**正文**里各写了一遍 —— **删 A、留 B**，
> A 处若还有导航价值就留一行指针。
