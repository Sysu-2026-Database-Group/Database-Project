## 1. 任务原文

> 第四周任务：ch4 连接、视图、完整性、授权
> **1. 本周目标**
> 完成多表查询、统计视图、主外键与检查约束、角色权限。
> **2. 任务**
> 1. **多表查询**：围绕订单、订单明细、商品、会员等表编写连接查询，回答完整的业务问题。
> 2. **统计查询**：使用聚合函数、`GROUP BY`、`HAVING` 和必要的子查询，统计销量、销售额、库存或会员消费情况。
> 3. **统计视图**：把会重复使用的统计查询封装为视图，并验证结果，如订单详情、商品销售统计和库存状态视图。
> 4. **完整性约束**：检查并完善主码、外码、`UNIQUE`、`CHECK`、`DEFAULT`、空值约束。
> 5. **角色权限**：依据第一周角色清单创建数据库角色，授予所需的最小权限，并测试越权操作。
> 6. **v0.1 复现**：从空数据库依次运行建库、样例数据、查询、视图、约束和权限脚本。
> **3. 本周作业**
> - `query.sql`：多表连接、聚合和子查询，具有明确业务含义。
> - `view.sql`：创建并查询不同的统计视图。
> - `constraint.sql`：创建约束，并含合法数据成功、非法数据失败的验证用例。
> - `role.sql`：创建角色、授予权限，并展示正常操作与越权失败。
> - v0.1 阶段验收清单：README、SQL 目录、结果目录、阶段报告、`ai_log` 和组内分工齐全；按 README 从空库可复现。
> **4. 提示与常见问题**
> - `INNER JOIN` 和 `LEFT JOIN` 的结果不同，应按业务问题选择并解释。
> - 完整性约束要在数据库中生效，不能只写在报告中。
> - 角色权限遵循最小权限原则，不应直接授予数据库所有权限。
> - 截图只是证据，提交内容仍要包含可重新执行的 SQL。
> - AI 生成的查询可能语法正确而业务含义错误，须用样例数据和预期结果核对。

## 3. 验收标准

**判定方式**：下表每一条都是硬性门槛，逐条判「过 / 不过」，不存在「基本满足」；
一条不过即视为不合格，不得进入下一周。
评审必须由**非本条作者的组员**执行 —— 自己评自己不算。
所有"通过"都必须有**可复核的实证**（脚本可重跑 + 保留实际输出），截图只是证据的一部分；
**每条查询与视图都要给出可复算的预期结果**（行数或关键值，取自第 3 周基线），评审能独立复算。

| # | 验收项（官方依据） | 通过标准 | 判不过的典型情形 |
|---|---|---|---|
| 1 | 交付物齐全（作业四件） | `db/query.sql` · `db/view.sql` · `db/constraint.sql` · `db/role.sql` 四件齐全、**提交进仓库**，`db/results/` 下有对应的**实际执行输出** | 只有 SQL 没有结果；结果只给截图、没有可重跑的脚本（提示 4） |
| 2 | 四件脚本可独立执行（任务 6） | 按 `db/README.md` 的顺序（第 3 周脚本 → 本周四件）在空库依次执行，**零错误**走完；**README 的执行顺序已更新到本周四件**；各脚本的 PASS 行与实际输出一致 | 需要手工插一步才过；报错被跳过还标通过；README 还停在上一版的步骤 |
| 3 | 多表查询答业务问题（任务 1） | 连接查询覆盖**订单 / 明细 / 商品 / 会员**，并至少涉及其余两类对象（预订单 · 退货）；**每条查询写明它回答什么业务问题** | 只做两表连接；查询说不出业务问题；只堆表不答题 |
| 4 | 外连接用得明白（提示 1） | 至少有一条 `LEFT JOIN` 的查询（本项目现成就有：**从未成交的商品** · **没有退货的销售单**），并说明此处**为什么不能用 `INNER JOIN`** | 整篇只有 `INNER JOIN` 也说不清差别；用了外连接但解释不出为什么 |
| 5 | 统计查询合格（任务 2） | 用聚合函数 + `GROUP BY`；**至少一条 `HAVING`**；子查询**至少出现一次**（若某处硬用反而更绕，说明理由即可）；统计口径覆盖**销量 / 销售额 / 库存 / 会员消费中的至少三类**（须含销量与销售额）；每条统计写清回答什么业务问题 | 只写 `SELECT *`；聚合没有分组语义；四类统计一个都没做；统计项说不出用途 |
| 6 | 视图被创建也被验证（任务 3） | `view.sql` 创建 **≥ 3 个统计视图**（如订单详情 / 商品销售统计 / 库存状态），**每个视图都有 SELECT 的验证结果**，且与直接查基表的结果一致 | 只 `CREATE VIEW` 不查；视图结果与基表不一致 |
| 7 | 完整性：不重复、只完善（任务 4） | 能说清本周**新增 / 完善了哪些约束、各拦什么**；**不重复创建第 3 周已建的约束**；完善走单一出处（**先改字典再改脚本**）并说明理由；**不得为了查询方便改动表结构或样例数据** | 重复创建第 3 周已有约束；悄悄改表结构 / 样例来迁就查询；只罗列约束名、不说明作用 |
| 8 | 约束真在库里生效（提示 2） | `constraint.sql` 含**合法数据成功 + 非法数据失败**两类用例，失败用例保留**实际错误码**；非法尝试全部回滚，不留脏数据 | 约束只写在报告或注释里；反例输出里看不到报错；尝试后留下脏数据 |
| 9 | 角色对齐第一周清单（任务 5） | 数据库角色与 `spec-roles.md` 的角色清单**对齐**（店长 · 收银员 · 库存管理员 · 顾客），不新增；**若判定顾客不需要库级账号，须写明理由并说明它的查询走哪条路径**；**先把"库管 / 库存管理员"两处用词统一** | 自创角色；同一岗位出现"库管 / 库存管理员"两套角色；既不建顾客角色、也不说明理由 |
| 10 | 最小权限（提示 3） | 逐角色写出"**能看 / 能改**"并在**表 / 列**级授予；**未授予 `db_owner` / `CONTROL` / `ALTER` 等超范围权限** | 直接给 `db_owner`；"几乎全库可写"；用角色绕过最小权限 |
| 11 | 越权真的失败（展示重点） | **每个角色**都有两条实证：**正常操作成功** + **越权操作失败**；越权测试在**该角色身份下**执行（`EXECUTE AS USER` 或独立登录），并保留输出 | 只在文档里写"应该失败"；在管理员身份下测越权；越权竟然成功却标通过 |
| 12 | 空库复现（任务 6） | **非作者组员**按 `db/README.md` 从空库依次执行（第 3 周脚本 + 本周四件），记录环境 / 命令 / 结果 / 问题；跑完后**第 3 周的三条账仍对得上**（在架总量 = 变动累加 · 积分余额 = 流水之和 · 现金以第 3 周基线为准，本周样例为 1430.30） | 只有作者或 AI 自己跑；跑完后基线被改乱；未实际执行就填通过 |
