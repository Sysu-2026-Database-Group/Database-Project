## 1 项目总体介绍

### 1.1 项目定位与当前完成范围

拾光书店是面向“单门店经营 + 线上预订到店自提”的数据库应用。系统围绕商品、会员、供应商、采购、销售、预订、退货以及库存、积分、资金流水组织数据，让顾客、收银员、库管和店长在各自权限内完成业务。第二阶段先用 ER 模型解释数据库，再通过函数依赖分析与迁移补强结构，最后把数据库能力封装成可操作的 Web 界面。

当前业务模型在第 5—6 周的 19 个历史经营实体上增加会员办理历史、联系方式变更历史，共 21 个经营实体。迁移记录、认证凭据、联系号码映射和请求去重记录属于技术对象，另行统计。前台提供商品浏览、预订和会员自助；后台提供收银结算、取货、退款、会员办理、商品与供应商维护、采购收货、报损、定价、资金管理、员工与经营报表。

| 使用者 | 主要功能 | 在业务链中的责任 |
| --- | --- | --- |
| 顾客 | 浏览商品、提交/查询/取消预订、会员凭证自助查询 | 发起需求，查看本人凭证与结果 |
| 收银员 | 销售清单、预览确认、取货、退款、会员办理 | 处理成交、收款与退款，不代替库管回收实物 |
| 库管 | 商品和报价维护、采购提交、收货、回收、报损与库存查询 | 处理实物和库存流水，不代替店长定价或付款 |
| 店长 | 定价、采购审批付款、注资提现、卡参数、员工和经营查询 | 决定经营参数与资金安排，查看全店经营情况 |

### 1.2 总体分层与架构图

按一次请求的处理职责，项目可分为六个逻辑层：页面交互层、路由与请求控制层、业务服务层、数据访问层、数据库业务过程层、数据存储与约束层。前四层组织 Web 应用，后两层运行在 SQL Server 内。它们是职责划分，部署时主要表现为浏览器、Flask Web 进程和 SQL Server，并不需要六台服务器。

![图 A：项目当前分层架构与主要调用方向](assets/report-structure/project-architecture.png)

图 A｜项目当前总体架构。实线表示典型写入调用链，右侧虚线表示鉴权后的部分只读请求可以直接调用 DAO。到期任务经受限身份调用数据库过程；数据库过程负责一次业务的事务，表、外码、CHECK 和索引负责数据结构与局部约束。图中各层与下表一一对应。

| 层次 | 输入、功能与输出 | 当前主要落点 |
| --- | --- | --- |
| ① 页面交互层 | 展示四类角色的页面；收集表单或 JSON 请求；展示预览、凭证、列表和可纠正错误。基础格式检查帮助用户及时修正输入 | 浏览器；`app/templates/`、`app/static/`；HTML 页面和 JSON API |
| ② 路由与请求控制层 | 按 URL 分派动作，读取可信会话身份、检查 CSRF 和请求输入，选择页面或 JSON 响应，附带请求编号 | `app/web.py`、`app/routes/` 及各功能蓝图模块 |
| ③ 业务服务层 | 组织销售、经营动作等预览与确认；验证主体、动作和签名引用；规范化输入并调用 DAO | `app/services.py`、`app/sales.py`、`app/operations.py` 等 |
| ④ 数据访问层（DAO） | 选择受限数据库连接，绑定参数，执行固定过程，转换结果和数据库错误；是请求路径唯一 SQL 出口 | `app/dao.py`、pyodbc、ODBC 驱动 |
| ⑤ 数据库业务过程层 | 再次复核岗位、状态、库存与金额；加锁、记录请求结果；将一次跨表业务放进同一事务 | `api.usp_*`；`db/*-entry.sql` 安装的业务过程与授权 |
| ⑥ 数据存储与约束层 | 保存实体、单据、历史快照和流水；用主码、外码、唯一索引、CHECK 拒绝不合法的记录 | SQL Server 业务表、认证/请求技术表、索引与约束 |

当前写路径主要遵循“路由 → 业务服务 → DAO → 存储过程 → 表”。部分只读查询在鉴权与参数检查后由路由直接调用 DAO，属于当前实现的简化。因此分层图展示的是职责与主要方向，不能据此声称所有请求都逐层经过业务服务。部署、建库和迁移 CLI 另属运维入口，其数据库操作不属于 Web 请求路径。

### 1.3 层间协作：以销售确认为例

收银员在页面选择商品后先查看预览，确认时提交 CSRF、签名引用及请求键。路由取得当前员工身份，业务服务核验预览与输入，再由 DAO 使用收银受限连接调用销售过程。过程在新事务中重新检查商品、权益和金额，写入销售单头、明细、库存、积分、资金及请求结果，成功后返回销售单号；页面跳转到凭证页。

预览期间不占用长事务，真正确认时仍需重算，防止预览之后库存、价格或配置变化。若事务中途失败，数据库回滚本次写入；若客户端重复提交，同键同内容返回原结果，同键异内容拒绝。前端禁用按钮只能改善交互，最终一致性依靠过程、事务和约束共同保证。

采购与退款采用相同分工原则，但保留业务上的不同事件：店长付款不等于库管收货，收银员退款不等于实物已经回库。资金流水、库存流水和原业务单据分别留痕，既能查询结果，也能追溯“谁在何时因哪张单改变了哪一本账”。

### 1.4 公共能力与运行组成

身份与权限贯穿页面、路由/服务和数据库：菜单按岗位展示，后端复核身份及数据范围，数据库通过 `auth`、`cashier`、`inventory`、`manager`、`guest`、`task` 六类受限连接执行固定过程。员工停用、改岗或重置口令时，会话版本变化，使旧会话失效；CSRF、请求编号、错误映射和日志由公共请求机制统一处理。

运行时除 Web 进程外，还有独立的 `app/expiry.py` 到期任务，默认每 60 秒调用到期过程；取货等入口同时即时判断到期。`run.ps1` 组织配置生成、环境检查、测试、启动、验证与停止。测试和迁移使用独立数据库副本，演示库与测试库分开；文中的历史实验结果按原验收记录引用。

## 2 第五周：ER 建模与原设计审查

### 2.1 实验目标、输入与实施方法

第五周主题是 ch6 ER 模型。实验以第一阶段已可复现的拾光书店数据库为输入，用实体、属性、标识、联系、基数和参与约束解释已有结构，并找出业务规则与数据库实际保证之间的差距。经营范围为单门店销售、线上预订到店自提、会员、采购、库存、退货与资金管理。分析以业务规定和数据字典为准，不能依据少量样例恰好没有重复而断言一对一。

输入基线包含 19 张业务表、47 条外码和 77 行旧业务数据。工作顺序是：先逐表审查“一行代表什么、主码和候选码是什么、属性为何独立保存”；再从审查结果汇总直接联系；然后核对图例、命名和外码覆盖；最后用多商品订单、会员或散客购买、库存查询三组现成证据检验表达。该顺序使图、数据字典和 SQL 结构能够互相指认。

第五周以分析与问题登记为主，未为展示 ER 而改写旧业务结构。`docs/design/design-notes-v1.0.md` 保存反推与实例论证，`er-mapping-v1.0.md` 保存逐表、逐联系和规则落点，`issues-v0.1.md` 保存问题处置。结构修正进入第六周迁移，不把修改后的结果冒充未迁移基线。

### 2.2 实体识别、属性组织与建模决策

实体判断首先看业务身份和生命周期。员工、会员、供应商具有可独立识别的身份；采购、销售、预订、退货单具有自身编号及业务生命周期；明细依附所属单据，保存一行商品或一行原销售明细的数量和价格；报价连接供应商与商品，具有自己的金额、上报人和上报时刻；库存、积分、资金流水记录已经发生的事件。

这里的“明细为依附对象”是概念角色，不表示物理主码必须包含单头编号。本项目明细使用代理主码 `id`，并以“单头外码 + 商品外码”等唯一组合约束业务身份。`book`、`toy` 各有 ISBN 或内部编码，因此具有自身标识，同时扮演商品的子类型；不能仅因其依赖商品业务而把它们当作没有标识的弱实体。

属性按当前状态、历史快照与派生值区分。`goods` 的当前售价可改变，`sale_item.unit_price` 表示成交时的价格；当前卡档配置可改变，销售单的折扣率属于成交快照。可售量由在架量减去已订量计算，未另建可售量字段；库存、积分和资金以流水保留来源，当前计数便于读取。属性是否重复，必须先判断是否描述同一业务时点。

| 建模决策 | 选择及业务理由 | 被否方案及原因 |
| --- | --- | --- |
| 商品与子类型 | `goods` 保存通用经营属性，`book`、`toy` 保存类别专属属性 | 全塞进商品表会让图书与文创专属列大量互空，类别语义不清 |
| 单头与明细 | 单头保存一次交易，明细保存多种商品及数量、成交单价 | 在单头放“商品编号列表”无法用单值外码和逐行约束清楚表达 |
| 供应商与报价 | 档案独立，报价由供应商与商品组合定位 | 把供应商名称和建档信息复制到每条报价会引入部分依赖 |
| 会员参与销售 | 销售可以没有会员，会员外码可空 | 所有销售强制关联会员将无法表达散客购买 |
| 预订人身份 | `reservation.phone` 是联系号码，未强制引用会员 | 把预订等同会员订单会排除非会员预订 |
| 历史价格 | 明细保留成交价、采购保留批次进价 | 查询历史时联接当前价格或当前报价，会随调价改变旧交易 |

### 2.3 19 张业务表的逐表归属与标识

下表列出第五周业务基线。主码本身也是候选码；“无额外候选码”只表示没有除主码之外的最小唯一标识。可空的筛选唯一列不直接等同于全表非空候选码。其他外码和完整属性以数据字典及映射清单为准。

| 表 | 一行代表的事实与主要属性 | 主码及额外候选码 |
| --- | --- | --- |
| `employee` | 一名员工；姓名、岗位、建档与修改留痕 | 主码 `phone`；无额外候选码 |
| `card_type` | 一个卡档当前参数；费用、折扣率、设置人和时刻 | 主码 `level` |
| `goods` | 一种可经营商品；类别、名称、售价、在架量、已订量及子类引用 | 主码 `id`；无额外全表业务候选码 |
| `book` | 一条图书细节；作者、出版社、页数 | 主码 `isbn` |
| `toy` | 一条文创细节；规格 | 主码 `inner_code` |
| `supplier` | 一家供应商当前档案；名称、建档留痕 | 主码 `id`；额外候选码 `name` |
| `supplier_quote` | 某供应商对某商品的当前报价；金额、上报人和时刻 | 复合主码 `(supplier_id, goods_id)` |
| `member` | 一个会员当前档案；卡档、有效期、积分余额与留痕 | 主码 `phone` |
| `purchase_request` | 一张采购单；供应商、状态和各阶段操作者 | 主码 `id`；额外候选码 `no` |
| `purchase_request_item` | 一张采购单中的一种商品；申请数量和批次进价 | 主码 `id`；额外候选码 `(request_id, goods_id)` |
| `sale` | 一张销售单；会员可选、实付与折扣快照、收银人、状态 | 主码 `id`；额外候选码 `no` |
| `sale_item` | 一张销售单中的一种商品；数量和成交单价 | 主码 `id`；额外候选码 `(sale_id, goods_id)` |
| `reservation` | 一张预订单；联系号码、预定码、创建/到期时刻、状态 | 主码 `id`；额外候选码 `code` |
| `reservation_item` | 一张预订单中的一种商品及预订数量 | 主码 `id`；额外候选码 `(reservation_id, goods_id)` |
| `goods_return` | 一次按原销售单受理的退货；总退款与经办信息 | 主码 `id`；额外候选码 `no` |
| `goods_return_item` | 本次退货中的一条原销售明细；退货数量和分摊退款 | 主码 `id`；额外候选码 `(return_id, sale_item_id)` |
| `stock_movement` | 一次库存增减事件；商品、正负数量、事由、来源 | 主码 `id`；无额外全表候选码 |
| `point_movement` | 一次积分获得、使用或回滚；会员、点数和来源 | 主码 `id`；无额外全表候选码 |
| `fund_flow` | 一次收款或付款；金额、方向、事由、前后余额与来源 | 主码 `id`；无额外全表候选码 |

四张明细表均明确选择“同一单内同一商品只保留一行，重复件数用数量表达”；退货明细对应“同一次退货内同一原销售明细只出现一次”。这是本项目的业务取舍，并由唯一约束实现，并非所有订单系统都必须遵循的通用假设。

### 2.4 主要联系、两端基数与参与约束

下表“左→右”表示每一个左侧对象能关联多少右侧对象，“右→左”反之。`0..1` 表示可选且至多一个，`1..N` 表示至少一个。业务应有基数与当前结构实际保证分别说明。

| 左侧与右侧 | 左→右；右→左 | 外码或关联表落点 | 参与约束与实现边界 |
| --- | --- | --- | --- |
| `member` → `sale` | `0..N`；`0..1` | `sale.member_phone` 可空外码 | 会员可无消费；散客销售不必有会员 |
| `supplier` → `purchase_request` | `0..N`；`1..1` | `purchase_request.supplier_id` | 每张采购单必须指定一家供应商 |
| `supplier` ↔ `goods` | `0..N`；`0..N` | `supplier_quote` 复合主码及两侧外码 | 每个报价行必须对应一家供应商及一种商品 |
| `sale` → `sale_item` | 业务 `1..N`；`1..1` | `sale_item.sale_id` 非空外码 | 外码保证明细有单头，不能保证每个单头都有明细 |
| `purchase_request` → 明细 | 完成单据业务 `1..N`；`1..1` | `purchase_request_item.request_id` | 草稿/提交条件需要流程判断，不能仅凭外码推断 |
| `reservation` → 明细 | 业务 `1..N`；`1..1` | `reservation_item.reservation_id` | 至少一行有效明细需业务入口复核 |
| `goods` → 各商品明细 | `0..N`；`1..1` | 各明细 `goods_id` | 商品可尚未发生交易；每行明细必须引用存在的商品 |
| `reservation` ↔ `sale` | `0..1`；`0..1` | `sale.reservation_id` 可空 | 第六周筛选唯一索引补足非空预订引用的最多一次 |
| `sale` → `goods_return` | `0..N`；`1..1` | `goods_return.sale_id` | 可分次退货，每次必须按一张原销售单受理 |
| `goods_return` → 退货明细 | 业务 `1..N`；`1..1` | `goods_return_item.return_id` | 至少一条退货明细需流程控制 |
| `sale_item` → 退货明细 | `0..N`；`1..1` | `goods_return_item.sale_item_id` | 原销售行可分次退；累计数量上界需跨行校验 |
| `goods` ↔ `book` / `toy` | 每类 `0..1`；业务至多对应一商品 | `goods.book_isbn`、`goods.toy_code` | 类别 CHECK 保证引用组合；第六周筛选唯一索引补上界 |
| 员工 → 单据/流水留痕 | `0..N`；依列为必选或可选 | 各 `*_by` 外码指向 `employee.phone` | 外码保证员工存在，不能证明该岗位有权执行动作 |

商品类别决定图书与文创引用互斥；外码方向从商品指向细节，因而数据库能阻止商品引用不存在的细节，却不能单靠该外码阻止孤立细节行。销售对应预订的唯一索引也仅限制最多一次，不验证取货前状态、取货后状态或库存和资金是否同步。

## 3 第六周：函数依赖、规范化、迁移与验证

### 3.1 实验目标与评价口径

第六周主题是 ch7 函数依赖与规范化。目标是在第五周模型的基础上，逐表检查候选码、关键函数依赖及插入/修改/删除异常，说明 1NF、2NF、3NF 的判断依据，再通过迁移和回归证明实际旧业务含义得到保留。需要拆分才提出拆分，合理结构则保留；不能为了展示拆表而破坏历史快照。

本项目的实际迁移以强化约束和补充留痕为主，版本从 v0.1 到 `v0.2-w6`。19 张业务表全部保留，新增 `schema_migration` 是迁移技术表。因此“迁移后 20 张物理表”与“19 个历史业务实体”不矛盾；后续 Web 增加两类会员历史经营实体后为 21 个经营实体，另有认证、请求等技术对象，不以物理表总数代替业务实体数。

### 3.2 函数依赖与范式判断方法

函数依赖 X→Y 表示在所有业务允许的同一关系状态中，X 相同必然要求 Y 相同；不是“这一份样例刚好相同”。候选码是最小唯一属性集合，主码也是候选码，主属性是属于任意候选码的属性。评估 2NF 时必须考虑全部候选码，不能因为有一个单列代理主码就直接跳过复合候选码的部分依赖检查。

1NF 要求每个属性保存本模型中的单值，不把多个商品编号或数量数组塞进一列。2NF 要求非主属性完全依赖每个候选码。3NF 要求每个非平凡依赖 X→A 中，X 是超码或 A 是主属性。由确定性金额公式、固定日期规则产生的依赖也要纳入判断，不能因其由 CHECK 维护就排除。

对时间语义的区分尤其关键。商品编号决定商品当前名称和当前售价，但不能单独决定跨历史交易的成交单价；同一卡档在调参前后可有不同折扣，销售单中的卡档不能决定所有历史折扣；采购批次价格也不能由供应商今天的报价反推。快照需要通过交易身份确定。

### 3.3 19 张表的依赖、候选码与范式结论

表中的“其余属性”指该行所属关系内的其他属性。结论限于设计文档明确识别的业务依赖。条件唯一性、跨表聚合与状态时序规则需另列，不能混成一个“全库已满足 3NF”的结论。

| 表与候选码 | 代表性函数依赖 | 判断及保留理由 |
| --- | --- | --- |
| `employee`：`phone` | `phone → name, role, 留痕` | 按员工档案依赖满足 3NF；岗位动作授权另验 |
| `card_type`：`level` | `level → card_fee, discount_rate, set_by, set_at` | 满足 3NF；跨档参数关系与历史快照另验 |
| `goods`：`id` | `id → category, name, 当前售价与库存计数, 子类引用` | 按当前状态依赖满足 3NF；流水汇总另验 |
| `book`：`isbn` | `isbn → author, publisher, page_count` | 满足 3NF，图书专属属性独立保存 |
| `toy`：`inner_code` | `inner_code → spec` | 满足 3NF，规格不作为身份 |
| `supplier`：`id`、`name` | `id → 档案属性`；`name → id, 其余属性` | 满足 3NF，名称唯一是本项目约定 |
| `supplier_quote`：`(supplier_id, goods_id)` | 组合码决定报价、上报人和时刻 | 满足 3NF；不存在单侧编号决定价格的规则 |
| `member`：`phone` | `phone → 当前卡档, 有效期, 积分余额, 留痕` | 按当前档案依赖满足 3NF；余额汇总另验 |
| `purchase_request`：`id`、`no` | 两个候选码分别决定供应商、状态和留痕 | 按已识别依赖满足 3NF；阶段推进另验 |
| `purchase_request_item`：`id`、`(request_id, goods_id)` | 两候选码分别决定数量和批次进价 | 满足 3NF；批次进价不能从当前报价重算 |
| `sale`：`id`、`no` | 码决定单头；`(小计, 折扣率, 积分抵扣额) → 实付额` | 严格不满足 3NF，有意保留 CHECK 维护的派生金额 |
| `sale_item`：`id`、`(sale_id, goods_id)` | 两候选码分别决定数量、成交单价 | 满足 3NF，保留成交价快照 |
| `reservation`：`id`、`code` | 码决定单头；`created_at → expires_at` | 严格不满足 3NF，固定三天派生到期时刻由 CHECK 维护 |
| `reservation_item`：`id`、`(reservation_id, goods_id)` | 两候选码分别决定预订数量 | 满足 3NF，已订量汇总另验 |
| `goods_return`：`id`、`no` | 两候选码分别决定原销售、总退款、经办信息 | 按已识别依赖满足 3NF；退款总额与明细跨表核对 |
| `goods_return_item`：`id`、`(return_id, sale_item_id)` | 两候选码分别决定数量与分摊退款 | 满足 3NF；原单归属及累计数量另验 |
| `stock_movement`：`id` | `id → 商品, 数量, 事由, 来源, 留痕` | 按完整事件关系满足 3NF；来源子集条件依赖另验 |
| `point_movement`：`id` | `id → 全行`；合法业务 `sale_id → member_phone` | 严格不满足 3NF；保留会员归属冗余，主动回归检查 |
| `fund_flow`：`id` | `reason_type → direction`；`(前余额, 方向, 金额) → 后余额` | 严格不满足 3NF；保留方向、余额快照并用 CHECK 维护 |

四张严格非 3NF 的表是 `sale`、`reservation`、`point_movement`、`fund_flow`。例如同一销售可有获得、使用和退货回滚等多笔积分，因此 `sale_id` 在积分表中不是超码；它却决定会员归属，构成必须分析的依赖。资金表中的事由决定收付方向、行内计算决定后余额，也不能因当前数据正确而忽略。

### 3.4 三类更新异常与具体业务例子

| 分析对象 | 插入异常 | 修改异常 | 删除异常与现有避免方式 |
| --- | --- | --- | --- |
| 假设“供应商档案混入报价” | 无商品报价时难以只保存供应商 | 同一供应商建档时刻重复多行，修改可能不一致 | 删除最后一条报价可能丢失供应商信息；实际以档案/报价分表避免 |
| 假设“订单头塞入商品列表” | 难以给每个商品分别设置外码、数量和价格 | 修改一行商品需重写整列内容 | 删除列表元素难追溯原销售行；实际以单头/明细分表避免 |
| 历史销售价与当前售价 | 旧交易不应依赖今天是否仍有同一售价 | 若改价覆盖历史，将改变已结账金额 | 商品停用也不应抹去原成交价；明细快照独立保留 |
| 供应商改名 | 可先建档后报价，没有必须伪造采购的要求 | 只改档案一行，其他表通过稳定编号引用 | 删除最后一条报价不会删除供应商档案；仍有引用时外码拒绝删档 |
| 有意保留的派生金额/时刻 | 新行必须同时满足计算式 | 基础值与派生值不同步会不一致 | 用明确 CHECK 拒绝矛盾值，并保留非 3NF 结论 |

“外码不允许删掉仍被引用的供应商”是引用保护，不是范式导致的删除异常；“员工岗位未校验”“库存汇总未同步”是权限或流程问题，也不能直接据此判某表不满足 3NF。实验把这些问题分开描述，避免用规范化替代业务一致性分析。

### 3.5 分解的无损连接、依赖保持与保留取舍

为说明什么时候应拆表，设计文档使用假设关系 U，而不是在项目中新增一张演示表：

```text
U(supplier_id, supplier_created_at, goods_id,
  quote_amount, reported_by, reported_at)
候选码：(supplier_id, goods_id)
依赖一：supplier_id → supplier_created_at
依赖二：(supplier_id, goods_id) → quote_amount, reported_by, reported_at
```

建档时刻只依赖组合码的一部分，因此 U 不满足 2NF。分解为 `S_demo(supplier_id, supplier_created_at)` 和 `Q(supplier_id, goods_id, quote_amount, reported_by, reported_at)` 后，交集为 `supplier_id`，且该交集决定 S_demo 全部属性，满足二元分解的无损连接条件。建档依赖在 S_demo 中维护，报价依赖在 Q 中维护，所列关键依赖得到保持。

这个论证只针对 U 表示的报价事实。真实供应商可以没有报价，不能由供应商与报价的内连接结果反建全部供应商档案。实际数据库已经独立保存供应商和报价，本轮选择保留该结构，是恒等保留，不虚构发生过拆表迁移。

对于确定性派生列，可以在理论上移去实付额或到期时刻，再由基础属性重算；但本轮为保持现有查询、业务快照和对账口径而保留，并用 CHECK 约束计算一致。积分会员归属可通过非空销售外码与销售表连接恢复，当前仍保留便于按会员查询；第六周对归属不一致依赖主动回归发现。保留冗余的代价、约束责任与严格非 3NF 结论均明确登记。

### 3.6 迁移前保护、实施顺序与结构变更

迁移先对来源库进行 COPY_ONLY 备份、校验及还原，再在独立新副本操作。正式验收记录的来源库为 `ShiguangBookstoreWeek3`，工作库为 `ShiguangBookstoreWeek6Final20261021220913`，另有后缀 Failure 的故障副本。库名和环境是历史执行事实，本次补稿未创建数据库或运行迁移。

执行前核对 19 张表、47 条外码、77 行旧业务事实，保存完整旧列快照和关键查询输出。`migration.sql` 要求调用者传入 DatabaseName，只允许 `ShiguangBookstoreWeek6` 前缀的专用副本；原始库或错误目标由 51040 拒绝，避免误写。成功迁移有版本标记，重复执行输出 SKIP；未完成迁移的残留状态需恢复新副本，不能盲目续跑。

| --- | --- | --- |
| 迁移元数据 | 新建 `schema_migration`，记录版本、时间、执行者和状态 | 区分是否完整执行；不作为新增经营实体 |

### 3.8 四类账的一致性与校验责任

| 账目 | 应满足的不变量 | 第六周验证与不能推导的结论 |
| --- | --- | --- |
| 库存账 | 每商品在架量 = 该商品库存流水带符号数量之和 | 固定合法截面对账一致；不保证任意直接 UPDATE 自动同步 |
| 预订占用账 | 已订量 = 按既定有效状态口径汇总的预订明细数量；可售=在架-已订 | 另列时间已到期但状态未处理的占用，不能混称自动释放 |
| 积分账 | 当前余额 = 积分流水累计；获得、使用、回滚有正确销售来源 | 来源 CHECK、类别唯一性和归属回归互补；汇总相等仍可能有错额事件 |
| 资金账 | 每行后余额符合收付公式；相邻前后余额衔接；来源单据金额相符 | 行内 CHECK 保护公式和非负，跨行连续与原单金额通过主动回归检查 |

退款、积分回滚与回收还需核对原销售归属、累计退货不超过原数量、退款总额等于明细分摊、正额退款有且仅有对应资金流水、零额退款不写零金额流水。退款并不必然等于立即回库；库存实物恢复需要对应回收事件。第六周主要验证合法截面和已经实现的约束，完整跨表原子入口在后续应用阶段补齐。

跨表不一致的 NULL 判断必须显式处理。若只用 `p.sale_id <> r.sale_id`，当 `p.sale_id` 为 NULL 时结果为 UNKNOWN，可能漏检；应组合 `IS NULL` 与不等判断。当前第六周回归补足此类来源检查，不能因为两侧都是外码就认为归属自然正确。

### 3.10 实验中的问题、修正与复核

| 现象 | 原因与修正 | 复核意义 |
| --- | --- | --- |
| 新增 `updated_by/updated_at` 后同批次报列名无效 | 静态编译时新列尚不可见；依赖新列的约束与检查使用动态 SQL 批次 | 迁移可从未改动副本执行，而非依赖手工先加列 |
| SQLCMD 变量未替换或库不存在 | 调用者显式传 DatabaseName，不在脚本内覆盖变量；执行前检查目标 | 迁移目标清楚，原始库保护能实际触发 |
| 无迁移元数据时回归停止 | 是前置状态检查生效；先正确迁移，再回归 | 不跳过缺失结构掩盖执行顺序错误 |
| 重复回滚积分反例未触发唯一性 | 最初选择无既有回滚的散客退货；改为复制已有会员退货回滚来源 | 真正命中目标索引，避免准备数据不足导致假结论 |
| 初稿把四表判断为 3NF | 忽略确定性派生列或会员归属依赖；已纠正严格范式结论 | 保留冗余可有业务理由，但必须准确说明理论代价 |
| 固定日期示例被误读为应用动作完成 | 分开列固定输入规则、静态会员记录及实际业务入口 | 公式通过不等于收费、续费、权益恢复已执行 |

复核不仅看最终 PASS，还检查是否触发预期对象、错误码是否正确、事务是否回滚、前后完整快照是否一致。采用新隔离副本重新执行实际迁移，不能仅靠已经迁移过的副本返回 SKIP 证明迁移过程可靠。

## 4 Web 设计

### 4.1 技术选型与约束

选择 Flask 3.1.3 + Jinja2 + pyodbc 5.3.0（SQL Server 17、ODBC Driver 18），不引入 ORM：项目只有 21 个实体、以存储过程承载事务，ORM 的反向建模与自动迁移会与已冻结的库结构冲突。数据库金额列用 `DECIMAL`，关键金额校核（注资、提现、卡参数）用 `Decimal`；页面金额大多为两位小数，采购单金额仍显示四位小数（待统一）。时间字段按数据库本地值展示，运行日志用 UTC，未实现跨时区转换；配置与密钥外置到 `run.*.json` 与设置目录，不写入代码。

三条禁止项：路由与业务层不得拼接 SQL；不得用字符串格式化拼参数；不得绕过 DAO 直接连接数据库。

### 4.2 总体架构

```text
浏览器（HTML 表单 / JSON API）
   │ 会话 + CSRF
Blueprint 路由（读输入、取当前身份）
   │
业务服务（预览、确认、流程编排）
   │
DAO（唯一 SQL 出口，? 参数绑定）
   │ EXEC api.usp_*
存储过程（岗位复核、锁、事务、规则）
   │
SQL Server（21 实体 / 六类受限账户）
```

调用方向单向，页面层不直接访问表；业务层不持有 SQL；事务由存储过程持有。整体是**薄应用、厚数据库**：应用负责输入、身份与流程编排，规则、锁与原子写入下沉到过程。写路径经“路由→服务→DAO”；只读查询在鉴权后直接调用 DAO，不经服务层（当前实现的已知简化）。请求处理路径的 SQL 只在 `app/dao.py`；建库、授权与升级由 `app/manage.py`、`provision_local.py`、`upgrade_guest.py` 等 CLI 脚本执行。

### 4.4 接口清单与契约

| 接口组 | 方法/路径 | 角色 | 输入 | 输出 | 主要错误 |
| --- | --- | --- | --- | --- | --- |
| 登录 | `GET/POST /auth/login`、`POST /auth/logout` | 公共/员工 | 手机号、口令、CSRF | 302 到工作台；会话 | 400/401/403 |
| 顾客目录 | `GET /shop`、`/shop/goods/<id>` | 顾客 | 关键词、分类、分页 | HTML 列表/详情 | 400/404 |
| 预订 | `POST /shop/reservations`、`POST /shop/reservations/cancel` | 顾客 | 手机号、明细、预定码 | 303 凭证；HTML | 400/404/409 |
| 预订查询 | `POST /shop/reservations/lookup` | 顾客 | 手机号+预定码 | 凭证页 | 404 |
| 销售 | `GET /sales`、`GET /sales/<no>`、`POST /sales/cart`、`/sales/preview`、`/sales` | 收银员 | 明细、会员、积分、请求键 | 预览页/凭证；303 | 400/403/409 |
| 取货 | `POST /pickups/preview`、`/pickups`、`/pickups/cancel` | 收银员 | 手机号、预定码、积分 | 预览/销售凭证 | 404/409 |
| 退货 | `POST /returns/preview`、`/returns`、`/return-recovery` | 收银员/库管 | 原单号、行、数量 | 退款凭证/回收结果 | 400/404/409 |
| 会员 | `POST /members/preview`、`/members`、`/members/contact` | 收银员 | 手机号、档位、联系方式 | 收费页/凭证 | 400/409 |
| 经营动作 | `POST /operations/<action>`、`/operations/<action>/preview`、`/operations/confirm` | 库管/店长 | 动作参数、请求键 | 303 回列表；预览 | 400/403/409 |
| JSON API | 按资源命名：`/api/sales`、`/api/sale-goods`、`/api/shop/*`、`/api/pickups/*`、`/api/operations/*` | 对应角色 | JSON + `X-CSRF-Token` | `{"error":...}` 或数据 | 同上 |

**响应约定**：销售、预订与经营动作成功后用 303 跳转结果页；登录用 302 跳工作台；会员办理成功后直接渲染凭证页（POST 返回 200）。API 成功返回数据，失败返回统一错误体；响应头带 `X-Request-ID`。写动作必须带 CSRF（表单隐藏域或 `X-CSRF-Token`）与请求键；同键同内容重放返回原结果，同键异内容返回 409。

成功响应示例（API）：

```json
{"sale_no": "W7S20261107-001", "paid_amount": "18.05", "request_id": "..."}
```

错误响应示例（API）：

```json
{"error": {"code": "insufficient_stock", "message": "可售量不足，请调整数量后重新预览。"}, "request_id": "..."}
```

HTML 页面：销售/预订/经营动作成功 303 → 结果页，会员办理成功直接渲染凭证页（200）；失败渲染错误页，显示状态码、可纠正提示与请求编号。分页要求页码 ≥1、页长不超过上限，超限统一返回 400。

### 4.5 权限与数据可见性

权限分三层：菜单按岗位隐藏；后端每个写动作独立复核身份与数据范围；数据库用 `auth`、`cashier`、`inventory`、`manager`、`guest`、`task` 六类受限连接，关键过程再查岗位。角色 × 动作矩阵见 §4.3。

| 身份 | 用途 | 不能做 |
| --- | --- | --- |
| `auth` | 登录、会话校验 | 业务写入 |
| `cashier` | 销售、取货、退货、会员 | 采购、定价、报表 |
| `inventory` | 商品、供应商、采购、库存、回收 | 销售收款、定价、盈亏 |
| `manager` | 审批付款、定价、员工、报表 | 代替收银/库管操作 |
| `guest` | 公开目录、预订、凭证查询 | 任何员工表与全店数据 |
| `task` | 到期释放 | 人工操作 |

字段级可见性示例：顾客看不到内部编码与采购价；收银员看不到批次进价与盈亏；库管看不到经营报表；店长可见经营数据，但不自动获得其他岗位的操作权。

### 4.6 认证与会话

登录用手机号+口令，口令以 Werkzeug 哈希存储；成功后写入 `actor` 与 CSRF token，会话 8 小时。每次请求校验 CSRF，写动作缺失或错误时返回 403。会话中带 `session_version`，员工改岗、停用或重置口令后版本递增，旧会话下一次请求即失效（401）。Cookie 设置 `HttpOnly`、`SameSite=Lax`，`Secure` 由环境变量控制。

### 4.7 事务、并发与幂等

预览与确认分离：预览只读、不占长事务；确认在新事务中复核身份、状态、金额与配置。一次业务由一个存储过程持有一个事务，典型包括：销售（单头+明细+库存+积分+资金）、取货（预订释放+销售+库存）、退款（退款+积分回滚）、采购付款与收货、报损、会员办理。各流程内部有固定锁顺序：销售为配置→商品（按 ID 升序）→资金；退款为原单→会员→资金；回收为退货明细→商品。跨流程不共用同一组资源，未做全局统一排序。

幂等由“可信主体 + 动作 + 请求键 + 内容摘要 + 原结果”实现：同键同内容返回原结果，同键异内容拒绝；成功记录与业务写入同事务。

### 4.8 异常处理与日志

| HTTP | 业务错误码示例 | 场景 |
| --- | --- | --- |
| 400 | `52101`、`52301`、`52501` | 参数、数量、格式、分页超限 |
| 401 | 认证 | 未登录、会话失效 |
| 403 | `52003` / CSRF | 岗位不足、CSRF 无效 |
| 404 | `52108`、`52304`、`52504` | 单据/记录不存在，或无权获知 |
| 409 | `52103`—`52107`、`52302`—`52309`、`2601/2627/547` | 库存不足、状态冲突、资金不足、预览过期、唯一/外键/CHECK |
| 503 | 连接失败 | 数据库不可用 |
| 500 | 未预期 | 未捕获异常、事务失败 |
| 405/415 | 协议层 | 方法不允许、媒体类型错误 |

用户可见信息只给“可纠正的一句话 + 请求编号”，不出现 SQL、表名、约束名、连接串、堆栈。运行日志的 8 个核心字段是 `request_id / time / action / role / status / error_code / result / duration_ms`，另附 `method / subject_type / subject`（主体用 HMAC 脱敏）；业务留痕（改价人、收货人、退款人等）落在业务表，不与运行日志混用。

### 4.9 页面交互与校验

前端做必填、格式、范围的基础校验，后端仍以服务与过程为准；按类别显示对应字段（图书/文创），不把无关字段一起提交。列表空状态给明确文案；删除、退款、取货等不可逆动作二次确认；错误提示在字段旁或页头，409 提示“重新预览”，503 提供“重试”。

### 5.2 请求处理与调用链

**查询：本人销售单**

```text
GET /sales
 → 路由读取会话 actor，校验岗位，解析分页参数
 → EmployeeDAO.sale_list(actor, page, page_size)   ← 只读查询直接调 DAO，不经服务层
 → EXEC api.usp_sale_list @employee_phone=?, @page=?, @page_size=?
 → 过程按收银员过滤并分页
 → 模板渲染列表
```

**写入：创建销售**

```text
POST /sales（CSRF + 签名引用 + 请求键）
 → SalesService.create 校验签名、主体、动作
 → EmployeeDAO.sale_create(actor, key, payload, expected)
 → EXEC api.usp_sale_create …
 → 事务由该过程持有：复核库存、权益、金额，写单头/明细/库存/积分/资金
 → 303 到 /sales/<no> 凭证
```

### 5.3 关键流程实现

**采购付款与收货。** 店长先注资；库管建草稿、提交；店长审批并付款；库管整单收货。付款只产生资金流水，收货才增加库存，两个动作各有操作人与单据来源。

**预订取货。** 顾客提交预订后生成预定码与到期时间；收银员核验后按会员折扣结算，生成销售单并把预订置为已取；取消或到期只释放已订量，不产生销售。

**退款与回收。** 收银员按原单选择行与数量，按差分公式计算退款并回滚积分；退款不直接加库存，库管确认回收后才写退货入库流水。

| 流程 | 事务边界 | 锁对象 | 幂等键 | 失败行为 |
| --- | --- | --- | --- | --- |
| 采购付款 | 一次付款一个事务 | 资金行（UPDLOCK）；采购单按状态复核 | 请求键 + 内容摘要 | 回滚，不产生半笔资金 |
| 采购收货 | 一次收货一个事务 | 商品行（UPDLOCK）；采购单按状态复核 | 请求键 | 回滚，库存不变 |
| 取货 | 预订释放+销售+库存同一事务 | 会员/配置、商品（ID 升序）、预订行 | 确认凭据 + 请求键 | 回滚，预订仍有效 |
| 退款 | 退款+积分回滚同一事务 | 原销售单（UPDLOCK）、会员、资金行 | 请求键 | 回滚，不产生半笔退款 |
| 回收 | 一次回收一个事务 | 退货明细（UPDLOCK）、商品 | 请求键 | 回滚，库存不变 |

| SQL 对账 | 实际结果 |
| --- | --- |
| 采购 2 件 × ¥5.00 | 已收货，库存 +2，资金只付一次 |
| 销售 1 件，银卡 0.95 | 原价 ¥19.00，实收 ¥18.05，库存 −1 |
| 退款 1 件 | 退回 ¥18.05，积分回滚 18；回收后库存 +1 |

**修改与删除边界。** 采购草稿与待结算清单可改；成交后走退货冲销；库存差异走收货、回收、报损，保留来源。商品仅在零库存、未上架、五张引用表均无记录时可删；删除同步清理图书/文创子类档案，编码可复用。

### 5.4 权限、会话与异常的落地

路由统一从会话取 `actor`（`g.request_actor`，`app/web.py:48`），写动作由 `services.current_actor` 复核岗位与数据范围；项目没有单独的鉴权装饰器，身份校验集中在请求前处理与服务入口。DAO 按动作选择连接身份（`cashier`/`inventory`/`manager`/`guest`/`task`），过程再校验一次。CSRF 在 `app/web.py` 的 `before_request` 统一校验；会话版本在每次请求与员工变更时比对。错误由 `AppError` 统一映射为状态码与业务码（`app/web.py` 错误处理器）；页面错误页与 JSON 错误体共用请求编号；`after_request` 写请求日志并回填 `X-Request-ID`。

### 5.5 后台任务与运行配置

`app/expiry.py` 独立进程运行（`python -m app.expiry`），默认 60 秒一轮，只连接 `task` 身份并调用到期过程；取货等入口仍即时判断到期，不依赖扫描。运行配置由 `run.example.json` 生成本地 `run.*.json`；`setup` 在 `<settings_directory>` 下生成六组连接、`settings.local.ps1` 与 `demo-credentials.local.json`。`run.ps1 start` 拉起 Web 与任务，`stop` 结束并释放端口。

### 5.6 实现顺序与返工

按 P0 基线补齐 → P1 公共基础 → P2 商品与采购 → P3 预订取货 → P4 会员 → P5 退货与经营 → P6 交付推进。返工至少三次：

1. 索引数量校验写死为 6，Web 新增第 7 个筛选唯一索引后从零建库失败，改为按索引名与启用状态校验；
2. 历史归档按字节指纹审计，Git 换行转换导致校验失败，用 `.gitattributes` 固定检出换行；
3. 删除商品只删主表，子类表残留导致同编码无法重建，改为同事务清理子类。

**常见问题**

| 现象 | 处理 |
| --- | --- |
| `setup` 报对象/索引不符 | 换新的 `database` 与 `login_prefix`，不要复用旧库 |

### 7.10 测试目标与总体思路

本项目的测试围绕业务风险组织：操作能否完成、身份能否被伪造、失败是否留下半笔数据、重试是否重复记账、并发是否破坏余额，以及换一个空环境能否复现。页面返回成功只是其中一个观察点，最终还要核对单据、库存、积分、资金和请求记录。以下方法结合现有测试代码与历史执行证据整理，本次编写没有重新运行数据库测试，也未增加已通过用例数量。

首先从 B1—B15 业务和 R 类规则提取不变量，再按风险安排测试。金额、库存、身份归属和不可逆状态优先于显示格式；先检验无库逻辑和错误契约，再以受限身份进入真实 SQL Server，最后用浏览器走完整表单及跨角色流程。每一层回答不同问题，避免只在页面层重复验证同一条正常路径。

| 关注问题 | 选择它的原因 | 主要判据 |
| --- | --- | --- |
| 规则与金额 | 折扣、积分、尾差可产生“页面看似合理、账目实际不平”的错误 | 独立复算预期值，核对分摊总额与原实付 |
| 权限与归属 | 隐藏按钮不能阻止直接构造请求 | HTTP、服务和受限 SQL 连接分别验证；本人凭证不能被其他主体读取 |
| 原子性 | 销售、收货等一次操作跨越多张表 | 后段故障后完整业务快照恢复，成功请求记录也不能残留 |
| 幂等与并发 | 双击、网络重试和资源竞争会放大记账错误 | 单据及流水笔数、同键返回值、库存和积分的最终值正确 |
| 复现与交付 | 作者旧库已存在对象时，缺安装步骤可能被掩盖 | 新副本从 setup 到 verify 成功，缺对象和多授权能被反例识别 |
| 异常恢复 | 合理拒绝后用户仍要能继续操作 | 错误不泄露内部值，重新预览或恢复连接后可继续，数据不受污染 |

### 7.11 分层策略、执行顺序与证据边界

纯单元测试用内存 DAO 或受控替身隔离数据库，适合快速检查格式、权限入口、签名、HTTP 契约和日志脱敏；它不能证明 SQL 锁、约束或真实账户权限有效。真实数据库测试使用隔离副本和受限连接，检验事务、来源、状态和并发。浏览器测试再确认用户能在页面找到入口、填表、预览、提交并看到正确结果。SQL 查询为页面结果提供账目证据，截图负责说明交互状态，两者互补。

| 顺序与层次 | 代表文件或入口 | 能证明的内容与边界 |
| --- | --- | --- |
| 1 环境与对象预检 | `run.ps1 doctor`、`tests/test_application_baseline.py` | 配置、对象与授权符合要求；环境不就绪不能把跳过记为通过 |
| 2 无库单元及 HTTP 契约 | `test_auth.py`、`test_web.py`、服务校验类 | 输入、身份、响应和脱敏逻辑；不替代真实数据库权限 |
| 3 数据库结构正反例 | `test_entry_database.py`、`db/tests/regression-negative.sql` | 外码、CHECK、唯一索引和受限身份实际生效 |
| 4 真实业务与事务 | `test_sales.py`、`test_operations.py`、`test_returns.py`、`test_members.py` | 完整业务写入与账目一致，冲突和失败不留下部分结果 |
| 5 资源竞争与重试 | `test_sales.py` 的多连接测试 | 在已构造的并发场景中不超卖、不重复扣积分或重复落单 |
| 6 浏览器与交付复现 | `scripts/browser_workflows.py`、统一入口及运行 JSON | 表单、跳转、角色入口和部署生命周期；不是大规模性能压测 |

本报告沿用正式取证口径：119 项为 49 项无库测试与 70 项真库测试；16 个浏览器节点和 22 个结构反例单列，不相加为“157 项单测”。11 月 2 日历史交付的 52 页检查、11 个表单节点和 11 月 7 日的 16 个取证节点来自不同轮次，不能合成同一轮覆盖。测试代码中的用例存在，也不能代替某次运行已执行的记录。

### 7.12 用例设计方法与代表性场景

用例按“准备数据—执行动作—观察响应—核对数据库—恢复现场”组织。正常场景确定基本业务链，等价类与边界值覆盖合法/非法输入，状态转换场景检查前置条件，主体变化场景检查身份绑定，前后快照检查副作用。金额预期尽量由原始业务输入独立推导，避免直接把被测函数返回值当成正确答案。

| 方法 | 具体场景 | 要观察的结果与现有对应 |
| --- | --- | --- |
| 等价类与非法输入 | 缺字段、重复商品行、非数字数量、可损失精度的金额、伪造员工或单价 | 及时拒绝且不进入不应调用的 DAO；销售和经营服务校验用例 |
| 边界值 | 数量 0/1、最后一件、积分上限、负积分、实付舍入为 0、会员到期当天 | 数量非法拒绝；零额不写零流水；到期日按规则包含；`test_sales.py` |
| 状态转换 | 未付款收货、审批与取消竞争、有效预订取货/取消/过期 | 拒绝非法推进或只有一个合法终态；不能重复释放占用 |
| 主体与数据范围 | 非收银员销售、他人确认引用、他人销售凭证、旧会话版本 | 拒绝跨主体调用，不暴露他人数据；认证及销售用例 |
| 前置条件改变 | 预览后改价、改卡费、库存变化或预览过期 | 新写入必须重新确认；已成功的同请求重放仍取原结果 |
| 顺序与累计结果 | 多行退款颠倒输入顺序，多次部分退货直到全退 | 分摊稳定，累计退款等于原实付，累计回滚不重复；`test_returns.py` |
| 反向验证测试判据 | 索引改名、注入错误授权、错误日期公式 | 测试必须失败且指出目标问题；不能只看到 PASS 标记就接受 |

例如尾差退款不能把“每次四舍五入”独立相加当作累计应退。本项目既有复现记录使用原实付 50.30 的三次退款，结果为 16.77、16.76、16.77，总额仍为 50.30。自动化测试还遍历原销售行逐件退回，逐次核对本次明细合计与退款单金额，最终核对原实付、原获得积分及“已全退”状态。这里验证的是一串动作完成后的整体不变量。

### 7.13 并发与幂等测试的安排

并发测试需要独立请求和数据库连接真实竞争同一资源，不能把同一连接上的顺序调用称为并发。销售测试使用线程池和 `threading.Barrier` 使多个请求在同一阶段起跑；结果既检查成功/拒绝数量，也检查数据库的最终笔数与余额。屏障提高竞争发生的机会，但不能据一次测试推断所有调度或任意压力都安全。

| 竞争场景 | 准备与执行 | 必须满足的最终判据 |
| --- | --- | --- |
| 同请求同时提交 | 同一个有效预览引用并发确认两次 | 两次返回同一结果；数据库只落一张销售单，库存只减一次 |
| 最后一件库存 | 设可售量 1，分别生成两个请求并发确认 | 恰好一个成交，另一个库存不足；最终库存 0 |
| 同会员积分 | 设余额 100，两请求均尝试使用 100 | 仅一笔成功使用，另一笔按积分规则拒绝，不透支可抵扣积分 |
| 不同商品同时销售 | 两请求占用不同商品，但追加同一本资金账 | 两笔业务可成功，资金前后余额逐笔衔接 |
| 预订与销售/取货与取消 | 两条动作争用可售量或同一预订 | 资源不双重消费，终态唯一，占用不重复释放 |

这些场景对应 `test_concurrent_same_request_creates_one_sale`、`test_concurrent_last_available_unit_only_one_sale`、`test_concurrent_member_points_cannot_be_spent_twice` 等实际用例。报告保留并发连续三轮一致的验收规则；本次未重新执行三轮，也不把规则文字当成新运行证据。更广的退款/回收竞争、长期高负载及多实例部署仍需独立验证。

幂等还要区分“同键同内容”“同键异内容”和“业务已结束后换新键”。同键同内容返回原结果；同键异内容应拒绝；换新键不能绕过单据终态。成功请求重试时，即使当下价格或余额已经变化，也不应再次扣款；相反，尚未成功的过期预览不能因为签名有效而继续写入。

### 7.14 故障注入、错误分类与恢复判定

故障选在业务中后段注入，才有机会发现“前段写入已成功，后段失败却未回滚”的问题。现有销售用例在隔离测试库创建资金写入触发器，抛出 52999，使库存和积分变更之后的资金入账失败；用例核对完整快照回到基线，移除触发器后再成功执行一次。收货也有库存变更后故障回滚测试。注入对象和临时记录仅用于测试现场，不能在演示或经营库触发。

需要校准 §7.4 的概括性异常表：它按“未预期异常兜底”列出 500，并不表示所有事务注入都返回 500。当前 `test_failure_after_stock_and_points_updates_rolls_back_everything` 明确断言 HTTP 状态 503；`test_unexpected_errors_hide_exception_values_but_log_stack_locations` 则用可控替身验证未捕获异常的 500 响应。错误发生位置、SQLSTATE 和 DAO 映射共同决定响应，应按具体用例引用，不能将两类证据互换。

| 恢复类型 | 应核对的事项 | 可接受的结论 |
| --- | --- | --- |
| 业务冲突 409 | 拒绝时无新增单据、流水或成功请求；修正输入或重新预览 | 冲突处理和可恢复操作符合已测规则 |
| 连接不可用 503 | 页面与 JSON 无连接串，恢复身份/连接后重试 | 已构造连接故障可恢复；不外推所有网络中断情况 |
| 事务后段失败 | 单头、明细、库存、积分、资金、请求结果无半笔残留 | 所测事务保持原子性；响应码按该用例实际映射记录 |
| 未捕获异常 500 | 不向用户回显异常值，日志保留定位所需堆栈位置 | 单元契约通过；仍未补真实页面 500 原始取证 |
| 迁移 DDL 失败 | 新列、索引、元数据与旧事实恢复，旧库未被写入 | 对应第六周 1913 故障副本实验，不能算作 Web 用例 |

### 7.15 测试数据、通过标准与结果归档

测试准备要明确配置、目标库、角色连接和样例前提。无报价商品不能直接拿来证明采购成功；没有既有退货回滚的散客记录也不能作为“重复回滚唯一性”的冲突来源。数据准备失败应修正夹具并重跑，不能删去断言或把预期业务拒绝归为系统故障。

测试结束后按用例设计回滚事务或清理自建单据、流水、请求记录、临时用户及触发器，恢复商品、会员和参数，并以快照比较确认没有污染基线。IDENTITY 或序列空号是事务回滚可能留下的正常现象，不以“主键必须连续”作为恢复判据；应核对业务事实是否恢复。

一次结果被记为通过，需要同时具备环境就绪、实际执行、断言符合、失败码符合预期、数据恢复及证据可追溯。`skip>0` 表示相关能力尚未在该环境执行；预期失败应记录所命中的错误，而非只记录进程非零。一次单元通过、一次浏览器成功和一份 SQL 汇总分别标注来源，不互相替代。

后续复测应保留运行时间、源码版本/工作区修正、库名、驱动、执行者、命令、退出码和限制；原始日志保留，报告摘录关键结论。当前主要入口为 `runtime-results.json`、`browser-results.json` 和 `database-checks.json`，均在 `db/results/week-7/stage-report-20261107/`。本节所列用例名可回到 `tests/` 查实现，历史运行结论则回到当轮归档查实际执行。

### 7.16 测试复盘与下一步改进

现有测试最有价值的变化，是从检查“某函数返回什么”推进到检查“一个动作前后哪些业务事实发生变化”。末件竞争验证库存互斥，重复请求验证结果与副作用一致，分次退款验证累计守恒，故障注入验证失败边界，新副本安装验证依赖完整性。几类证据叠加，才能较有把握地判断可用性。

目前仍需补充真实 500 响应与日志原片段、另机复现的原始输出、键盘操作与打印、退款/回收更广并发及更高负载。这些是后续验证计划，不计入已有通过结果。另机已获用户完成确认与“证据尚未归档”可以同时成立；协作签收也必须由本人确认，不用自动测试代替。


## 8 项目推进过程、困难与阶段复盘

### 8.1 推进方法与记录依据

项目按“先明确业务，再建立可复现基线，再解释和修正设计，最后封装应用与验证交付”推进。每次阶段完成都检查三件事：新增了什么能力，哪些旧事实必须保持，尚有哪些问题留到下一阶段。周次是课程任务顺序，审查日期是实际复核时刻，两者不强行一一对应；例如第一至四周的正式 review 都在 2026-10-06 汇总，而独立空库复现在 2026-10-05 已有记录。

本章综合 `docs/reviews/review-week-1.md` 至 `review-week-4.md`、第六周正式验收、`ER/review-v1.0.md`、`ER/review-v1.4.md`、Web 实施台账及 11 月 4—6 日复现和整改记录。第五周没有另造一份不存在的 review，使用实际 ER 审查记录。以下心得是依据问题与修复过程形成的项目复盘，不代填成员个人感言或签收。

### 8.3 第一至二周：先统一业务含义，再决定字段

初期困难是经营概念容易混用：库存既可能指当前余额，也可能指发生过的出入库；订单可能指销售，也可能指尚未成交的预订；退款与实物回收也不必同时发生。若在这些含义尚未统一时开始建表，后续外码、金额和岗位权限就会出现不同解释。

处理方式是先在场景、角色、业务规则和数据边界文档确定范围，再把对象映射到数据字典。可售量以在架减已订现算，经营盈亏按资金事由汇总，避免为了“字段齐全”重复保存所有查询结果。单据与明细分开，流水指回业务来源，使每个字段都能解释用途。

第二周 review 同时提醒了材料与设计是两项检查：当前字典和样例可以支持关系讨论，但原引用的独立样例文件缺失，不能沿用历史“通过”就声称严格提交材料齐备。这一项在推进表中继续列为待核实。体会是业务清楚、字段合理和交付文件存在需要分别证实，引用路径也应视为验收的一部分。

### 8.4 第三至四周：从脚本成功到空库可复现

DDL 阶段的困难是“在已有数据库运行成功”可能依赖残留对象或旧样例。项目增加结构校验、重复装载与冲突保护，保存 19 表、47 外码、77 行的固定基线；现金 1430.30、经营盈亏 -69.70 等结果作为可复算检查。CRUD 只操作本事务新建数据并回滚，避免演示修改污染原样例。

第四周把查询正确性和授权正确性进一步分开。销售查询采用外连接保留非会员单，商品汇总保留无销量商品；三个统计视图与基表核对差异为 0。跨档参数属于跨行规则，用补充触发器验证，而不是重复创建已有单行约束。三类店内角色各有允许操作与越权反例，越权实际返回 229。

2026-10-05 的非作者新实例、新库九步复现为脚本顺序提供了证据。第三周 review 又发现草案仍写“待独立复现”，与正式结果冲突；处理原则是以正式执行记录判断结果，并保留草案发生时状态供追溯。体会是复现不仅检查 SQL，也检查文档能否把他人带到同一结果；正式状态应有单一依据，过程记录不能任意改写成当前结论。

### 8.5 第五至六周：模型审查、理论纠偏与可靠迁移

ER 绘图最初暴露出标签压属性、双线矩形不清、说明占据图中部等可读性问题。10-11 的审查通过移动采购单区域、补真正双线框、将说明移入独立栏和补样例覆盖表逐项修正。后续又发现 C-5 仅表示当前参数的取值口径，没有物理关系落点；审查后移除该历史联系，保留空编号与参数快照规则，避免把“计算时取值”画成“存在外码”。

部分基数曾混淆业务应有上界与数据库已有保证，例如采购一次付清、预订最多取货一次。处理方式是在图中表达业务要求，在映射表写清约束、主动回归或流程各自实现到哪里。v1.4 继续修正悬浮端点、复合码和来源含义，核对 19 表137字段及 PNG 内嵌图源；10-22 的人工确认只覆盖对应正式版本，不能用旧图通过替代新图审查。

第六周还有理论与执行两类困难。理论上，初稿忽略确定计算和归属依赖，把四表判断得过于理想；复核后明确 `sale`、`reservation`、`point_movement`、`fund_flow` 严格非 3NF，保留业务冗余并说明维护代价。执行上，新增列在同一静态批次编译不可见，改用动态 SQL 批次；SQLCMD 目标由调用者显式传入并增加原库防护；反例数据必须选已有会员回滚，才会真正命中重复回滚约束。

最终以新副本、旧列快照、查询比较、22 反例、权限、1913 故障回滚和日期变异形成验收链。心得是理论分析需要接受纠正，约束通过不能替代范式证明；迁移可靠也不能只看最终表数，必须观察中途失败是否能恢复，并明确自动过期、幂等、并发入口在当时尚未实现。

### 8.6 从销售入口到四角色闭环：按依赖推进

10-23 销售入口把登录基础推进为可提交的业务：预览不写库，确认时重新复核，销售、库存、积分和资金同事务，成功请求可重放。该轮最终 48 项包括当时的登录及销售测试，不能拿这个数字代表后续采购、预订、退款已经完成。多连接和故障用例在起步阶段就验证关键不变量，避免只按页面数量衡量进度。

11-01 规划指出当时只有销售主链，安装入口还缺跨档触发器和三个视图，因此先安排 P0 基线与精确授权，再做 P1 公共布局、错误和日志，然后推进采购资金、顾客预订与到期任务、会员、退款回收、员工和经营查询，最后做 P6 交付。采购付款先有资金来源，收货再影响库存；取货复用销售规则；退款有原销售作为计算依据。这一顺序减少了后续能力建立在未稳定基础上的返工。

扩展中遇到测试夹具缺 guest/task、会员改联系号码后续费误建第二身份、取消终态缺请求区分、金额预览无有效期、移动端表格溢出及店长单据查询缺口。相应措施是补齐六身份夹具，保持会员原主键稳定并用联系映射解析，记录主体/动作/请求结果，给确认加时限和重算，修订布局及全店查询。新增会员办理、联系方式历史独立保存，21 实体模型以增量文档交付，不覆盖19实体历史成果。

另一个困难来自证据保护：给第六周受保护文档追加 Web 说明改变字节，导致历史指纹审计失败。处理为恢复历史文件原 SHA-256，把 Web 扩展放进独立文档，保留旧 manifest；Git 换行问题则通过 `.gitattributes` 明确检出规则，并在三种换行设置下审计。体会是历史可复现依赖的不只是数据库，文件字节、工具配置和证据归属也要被管理。

### 8.7 复现审查推动的整改：从可用到可交付

11-04 复现中出现一个重要反差：119 项测试通过，但全新 setup 仍被写死的“6 个索引”检查阻断。Web 已新增第 7 个筛选唯一索引，旧检查没有随依赖变化更新。整改为按索引名和启用状态校验，指出缺失/多余对象，并用索引改名反例验证判据。复现记录中先使用了本地补丁，不能据此宣称未修正源码原本就能从零安装；最终结果以合入修复后的新库验收为准。

| 问题与发现方式 | 处理措施 | 复核记录与体会 |
| --- | --- | --- |
| stop 后残留进程、运行日志未落盘 | 根据已记录进程停止并校验，增加后台启动和 `web.log` | 三次生命周期残留 0；启动成功还要能停止和排障 |
| 表单类别必填与后端不一致 | 类别切换时同步显示、禁用和 required 属性 | 图书/文创分支验证；前端与后端应使用同一业务条件 |
| 开卡成功但无自助凭证 | 事务中写凭证摘要并返回凭证 | 新开卡后可自助查询；业务完成需包含用户能继续使用的结果 |
| 三无商品不能删除及无效按钮 | 受控删除入口，服务端检查库存、上架状态及引用资格 | 合法删除与 409/403 反例；按钮资格不能代替数据库复核 |
| 删除后同编码无法重建 | 删除商品时同步清理对应 `book`/`toy` 子类行 | G-08 重建成功；不能只检查 DELETE 成功，还要检查后续可用性 |
| 金额、时间与错误页不统一 | 公共 money/rate/dt 过滤器、按状态标题、503 重试入口 | 页面复验；展示口径也影响业务结果能否正确理解 |

11-06 最终审查保留了限制：删除五类引用没有逐类完成同等实测、真实 500 缺安全取证、部分成员签收尚未补齐等。该文件结尾的概括性“全部处理”必须结合明细的“未单独构造”“仅实测报价引用”阅读，本报告采用较具体的覆盖范围。其引用日期和用语也不倒推为本次重新验收。

### 8.9 推进过程中的心得体会

第一，先确定业务语义，再选择表和接口。退款与回收分开、当前参数与历史快照分开，使数据库和页面能共同解释业务，而不是后期靠补字段修补含义。对四类角色能做与不能做的提前约定，也直接成为权限反例的来源。

第二，把“不变量”作为阶段交接条件。前期是19表、47外码和旧账，迁移时是旧事实不变，应用时是一次动作中账目同步，交付时是新环境能重建。每轮在新增能力之外检查旧基线，才有机会发现历史指纹、安装缺对象和子类残留等跨阶段问题。

第三，审查要同时检查实现和测试判据。反例若没有正确冲突数据，可能测不到目标约束；权限测试若接受任意错误，可能把 SQL 故障误判为拒绝成功。索引改名、权限注入、日期变异与故障回滚让测试本身受到检验，比只增加正常页面截图更能提高结论可信度。

第四，完成标准要覆盖用户操作的前后过程。开卡后能否取得凭证、删除后能否复用编码、服务能否停干净、错误后能否重试，都属于交付的一部分。一次按钮成功和119项通过仍不能代替独立复现与逐页使用审查。

第五，允许纠正理论与历史结论，但必须保留来源。四表范式纠偏、ER多轮修订和不同日期的测试数量变化，都反映认识与能力逐步完善。正式记录、历史草案、AI技术检查和本人签收应各有归属；未完成项清楚登记，比扩大“全部通过”的含义更有助于团队继续推进。

## 9 实验总结

本阶段把已冻结的模型落实到四类角色的 Web 操作：顾客预订与自助查询，收银销售、取货、会员与退款，库管商品、采购、收货、报损与回收，店长定价、审批、员工、卡参数与经营查询。采购付款与实物收货、退款与实物回收各自留痕，资金与库存可独立对账。

实测发现：约束保证记录形状，跨表一致性仍需业务事务；正常下单只能证明功能可用，末件竞争、重复请求与中途故障才能检验事务设计。当前销售草稿仍使用单进程内存，部分只读请求在鉴权后直接调用 DAO；另机复现已有用户确认，原始输出待补。分工：黄智亮（复核与修复，已签）、梁宇聪（已签）、林泽群（待签）。
