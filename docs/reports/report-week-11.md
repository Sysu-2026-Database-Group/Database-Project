## 2. 库存审计触发器

### 2.1 设计

库存写入统一由 `api.usp_adjust_stock` 完成：

```text
UPDATE goods.stock_total
INSERT stock_movement
```

二者处于同一事务。`stock_movement` 记录：

```text
商品、调整前后物理库存、变化量、类型、时间、操作人、来源单据
```

Web 应用角色对 `dbo` 表无直接 DML 权限，库存写入不能绕过过程。

触发器定位为**数据库层重复校验**，不承担业务写入：

```text
dbo.tr_stock_movement_guard
AFTER INSERT ON dbo.stock_movement
```

### 2.2 校验内容

| 检查 | 规则 |
|---|---|
| 行内边界 | `stock_before >= 0`、`stock_after >= 0` |
| 行内差值 | `quantity = stock_after - stock_before` |
| 当前库存一致 | 每个商品本次最后一条流水的 `stock_after = goods.stock_total` |
| 多行处理 | `inserted` 集合 + `ROW_NUMBER()`，不假设单行 |

历史流水的链式连续性由 `db/checks/verify.sql` 和 `db/regression.sql` 对账，不放入触发器；这样可以兼容测试和迁移中合法的库存截面。

### 2.3 接入

```text
db/trigger.sql
  → 样例与前后数量迁移完成后安装
  → scripts/project_runner.py 纳入 setup
  → doctor 检查 tr_stock_movement_guard 是否存在且启用
```

### 2.4 验证结果

| 验证 | 结果 |
|---|---|
| 全新库 setup | PASS |
| doctor 对象检查 | PASS |
| 正常库存调整 / CRUD 流水 | 触发器不误拒 |
| 直接插入 `stock_after ≠ goods.stock_total` | `52403` 拒绝 |
| 行内差值或边界不合法 | `52401` 或 `547` 拒绝 |
| 完整测试 | 133 通过，失败 0、错误 0、跳过 0 |
| Week6 artifact audit | PASS |

### 2.5 边界

- 触发器只覆盖 `stock_movement` 插入路径；直接 `UPDATE goods` 不触发它。
- 应用角色已受权限约束；`dbo`/`sysadmin` 仍可绕过。
- 一致性主保障仍是 `usp_adjust_stock` 的事务与唯一写入口，触发器用于重复校验。

## 3. 订单完成规则（无触发器，过程校验）

现有模型没有 `sale.status='已完成'` 状态：

```text
sale.status：已付 / 部分退款 / 已全退
reservation.status：有效 / 已取 / 已取消 / 已过期
```

### 3.0 不采用触发器的确认

黄智亮已与助教确认：本项目没有“订单状态”属性，不要求为订单完成新增状态或触发器。

订单完成以销售事务提交（或预订取货）为语义。触发器需要“状态改为已完成”或一个最终的完成事件作为挂点；当前设计中不存在这两种结构。若为了触发器新增状态或完成事件表，会引入与现有事务提交重复的语义，因此本项目不实现订单完成触发器，规则在数据库过程中校验。

### 3.1 完成前校验

`api.usp_sale_calculate` / `api.usp_sale_commit` 在写入前检查：

| 检查 | 处理 |
|---|---|
| 明细为 JSON 数组、1—50 行、字段完整 | 不满足报 `52101` |
| 商品编号/数量为整数，数量 1—1000，同一商品不重复 | 不满足报 `52101` |
| 会员格式、会员存在 | 不满足报 `52101`/`52102` |
| 商品存在、已上架、已定价 | 不满足报 `52103` |
| 可售量（含预订占用）充足 | 不满足报 `52104`；写入时 `usp_adjust_stock` 再校验并报 `52302` |
| 积分抵扣上限 | 不满足报 `52105` |
| 确认报价过期或价格/会员条件变化 | 不满足报 `52107` |
| 预订状态、到期时间 | 不满足报 `52502` |
| 单笔金额范围、折扣率、状态、会员/卡档组合 | 由过程校验及 `CK_sale_*` 约束兜底 |

### 3.2 防止重复完成

| 场景 | 机制 |
|---|---|
| 同一次提交被重试 | `api.sale_request` 主键 `(employee_phone,request_key)` + payload hash；同键同内容返回原结果，不同内容报 `52106` |
| 同一预订被重复取货 | 预订行 `UPDLOCK,HOLDLOCK` + 状态必须为“有效” + `UX_sale_reservation_id` 唯一索引 |
| 已完成订单再次完成 | 销售没有“完成”更新接口；销售创建成功即完成，不存在第二次完成同一 `sale` 的操作 |

### 3.3 边界

- 以上检查是**过程级约束**，不是数据库触发器；应用角色无法直接写 `sale`/`sale_item`，正常 Web 路径不能绕过。
- 数据库层没有“销售单必须有明细”“销售金额必须等于明细合计”的跨表约束；这两个不变量由 `usp_sale_commit` 保证，`dbo`/sysadmin 直接 DML 仍可绕过。
- 因此本项目的“订单完成规则”与库存审计一致：以单一过程入口和事务为主保障，不以触发器为主保障。

### 3.4 其他同类业务的封装与去重

订单完成不是独立机制，而是沿用同一套“过程封装 + 请求键/唯一约束”设计：

| 业务 | 写入入口 | 重复检查 |
|---|---|---|
| 预订单创建 | `usp_reservation_create` | `api.reservation_request` 请求键 + payload hash |
| 预订单取消 | `usp_reservation_cancel` | `api.reservation_cancellation` 请求键 |
| 预订取货 | `usp_pickup_create` → `usp_sale_commit` | 销售请求键 + 预订行锁/状态 + `UX_sale_reservation_id` |
| 退货创建 | `usp_return_create` | `api.operation_request` 请求键 + payload hash |
| 退货回收 | `usp_return_recover` | `api.operation_request` 请求键 + `UX_stock_return_once` |
| 采购/付款/注资/提现 | `usp_operation_write` | `api.operation_request` 请求键 |
| 会员开卡/续费/改号 | `usp_member_create` / `usp_member_contact` | `api.operation_request` 请求键 |
| 积分变动 | 销售/退货过程内部写 | `UX_point_movement_earn/use/return` 筛选唯一索引 |
| 资金变动 | 销售/退货/采购/会员/注资过程内部写 | 依赖父业务请求键；`fund_flow` 无独立请求键 |

积分和资金没有独立页面入口，也没有自己的请求键；重复检查由父业务请求键和唯一索引承担。预订过期释放由后台任务按“有效 + 到期”处理，不使用用户请求键。

## 4. 窗口查询

提交脚本：`db/window_query.sql`，包含一条排名查询、一条按订单日期累计查询和一条指定日期移动平均查询；以下说明三者的口径与页面实现。

### 4.1 排名查询（已完成）

数据对象：

```text
report.fn_product_sales_rank(@from_date, @to_date, @metric)
```

#### 4.1.1 三个排名指标

排名不是只按“卖了多少”一个维度，而是提供三个可选指标：

| 指标 | 参数值 | 计算 | 回答的业务问题 |
|---|---|---|---|
| 净销量 | `quantity` | 销售数量 − 退货数量 | 哪些商品卖出的件数最多？ |
| 净收入 | `revenue` | 整单实收按行原价分摊 − 退货退款 | 哪些商品贡献的收入最高？ |
| 净订单数 | `orders` | 总订单数 − 全部退完的订单数 | 哪些商品被最多订单真正留下？ |

默认指标为净销量，符合“畅销榜”的阅读习惯；店长可切换另外两个指标。

#### 4.1.2 三个指标的业务含义

**净销量排名**

- 衡量商品的真实出货能力，已扣退货；
- 适合回答补货优先级、货架陈列、畅销榜；
- 高排名表示周转快，但不等于利润高，因为低价商品可能销量高、收入低。

**净收入排名**

- 衡量商品对真实收入的贡献，已扣折扣、积分抵扣和退款；
- 适合回答促销资源、重点陈列、供应商谈判；
- 高排名表示收入贡献大，可能来自高单价，也可能来自高销量。

**净订单数排名**

- 衡量商品被订单选择并最终留下的广度；
- 展示时区分 `total_orders`（总订单数）和 `returned_orders`（全部退完的订单数）；
- `net_orders` 只用于排名，不单独展示，避免把中间计算量当成业务指标；
- 高排名表示商品需求覆盖面广、退货后仍被保留，适合分析连带购买和稳定需求。

三个排名可能给出不同结果：

```text
低价高销量商品：净销量排名高，净收入排名低
高价低销量商品：净收入排名高，净销量排名低
多单少量商品：净订单数排名高，净销量排名未必高
```

因此排名页保留指标切换，避免用单一指标代替经营判断。

#### 4.1.3 净口径

```text
统计日期：按 sale.sold_at，包含起止当天
退货归属：按原销售归集，退货发生在统计区间之后也冲减
退货订单：该商品在该订单中全部退完，才算 returned_orders
销售额：sale.paid_amount 已扣折扣和积分抵扣，再减 refund_amount
```

分摊方式：

```text
该行分摊实收 = sale.paid_amount × 该行原价金额 / 整单小计
该行净收入 = 该行分摊实收 − 该行退款金额
```

`fund_flow` 只用于整单收入对账，不直接用于商品排名，因为它没有 `goods_id`/`sale_item_id`。

#### 4.1.4 排名函数与并列

主排名使用：

```sql
RANK() OVER (ORDER BY 指标值 DESC)
```

`RANK` 保留并列：相同指标值同名次，下一名跳号。例如：

```text
A 100 → 第 1
B 100 → 第 1
C 90  → 第 3
```

展示顺序使用：

```sql
ROW_NUMBER() OVER (ORDER BY 指标值 DESC, goods_id)
```

`ROW_NUMBER` 只用于稳定列表顺序，`goods_id` 作为 tie-breaker，不改变业务名次。

#### 4.1.5 页面与访问

```text
/reports/product-ranking
所有角色可看净销量
店长可切换净收入/净订单数
非店长请求收入/订单时自动回退净销量并提示
默认最近 30 天
```

课程未规定排名的时间范围。本实现为排名查询增加日期参数，默认最近 30 天，用于“期间排名”；日期是页面显式筛选条件，不是写死或隐藏过滤。日期变化只改变统计窗口，不改变净销量/净收入/净订单数的指标定义。

### 4.2 累计值查询（已完成）

#### 4.2.1 两种累计模式

| 模式 | 行粒度 | 排序字段 | 累计内容 |
|---|---|---|---|
| 按日期 | 每个销售日期一行 | `sold_date` | 每日净销量/净收入；累计净销量/净收入 |
| 按商品 | 每个商品一行 | `net_revenue DESC, goods_id` | 商品净销量/净收入；按净收入降序累计 |

两个模式都同时展示两个累计量：

```text
累计净销量
累计净收入
```

净口径与排名查询一致：

```text
净销量 = 销售数量 − 退货数量
净收入 = 整单实收按行原价分摊 − 退货退款
退货按原销售归集，与退货日期无关
```

#### 4.2.2 排序字段说明

日期模式：

```sql
SUM(daily_net_quantity) OVER (
    ORDER BY sold_date
    ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
)
```

商品模式：

```sql
SUM(net_revenue) OVER (
    ORDER BY net_revenue DESC, goods_id
    ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
)
```

窗口 `ORDER BY` 决定累计顺序，最终查询也按同一字段排序；`goods_id` 只作为同收入商品的 tie-breaker。

#### 4.2.3 业务含义

- 日期累计：销售进度、月度目标完成度、累计收入/销量增长曲线；
- 商品累计：按净收入降序累计，反映头部商品的累计贡献，可用于帕累托/ABC 分析；
- 商品模式不按 `goods_id` 作为主排序，因为“按档案编号累计”没有经营意义。

#### 4.2.4 数据对象与页面

```text

report.fn_cumulative_sales_by_date(@from_date,@to_date)
report.fn_cumulative_sales_by_product(@from_date,@to_date)
```

页面：

```text

仅店长可访问；其他角色 403

```

### 4.3 移动平均查询（已完成）

#### 4.3.1 窗口与指标

采用“指定日期 + 前 2 个日历日”的 3 天窗口，不做固定“今天往前 3 天”。

```text
窗口：as_of_date - 2 至 as_of_date
排序：sale_date
无销售日期：补 0
指标：净销量、净收入
```

数据对象：

```text
report.fn_moving_average_sales(@as_of_date)
```

返回：

```text
sale_date
daily_net_quantity
daily_net_revenue
moving_avg_3d_quantity
moving_avg_3d_revenue
```

计算：

```sql
AVG(daily_net_quantity) OVER (
    ORDER BY sale_date
    ROWS BETWEEN 2 PRECEDING AND CURRENT ROW
)
```

日期序列每天一行，因此 `ROWS 2 PRECEDING` 等价于最近 3 个日历日。

#### 4.3.2 页面与权限

```text
/reports/moving-average
仅店长可访问；游客/收银/库管 403
指定日期默认今天；未来日期 400
摘要：窗口范围、3 日平均净销量、3 日平均净收入
明细：3 天的每日净销量/净收入
无销售：3 行显示 0，并提示“该窗口内没有销售数据”
```

#### 4.3.3 业务含义

- 平滑单日波动，观察指定日期之前的短期趋势；
- 辅助短期补货、排班和陈列调整；
- 与累计查询配合：累计看总量进度，移动平均看最近趋势。

#### 4.3.4 测试覆盖

```text

```
