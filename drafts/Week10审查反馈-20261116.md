### W10-F02｜折扣函数不计算“会员身份 → 折扣率”（已修复）

**级别**：已修复（2026-11-16）

**原问题**：

```sql
CREATE OR ALTER FUNCTION dbo.fn_sale_discount(
    @subtotal decimal(10,2),
    @rate decimal(3,2)
)
RETURNS TABLE
```

- 只做 `折后金额 = ROUND(subtotal * rate, 2)` 与 `优惠金额 = subtotal - 折后金额`；
- 折扣率 `@rate` 由 `usp_sale_calculate` 读取会员有效期、卡档后传入；
- 函数不接收会员手机号，不读取 `card_type`，无法体现“先查会员 → rate → 金额”。

**课程/任务原文**：

> 根据会员身份、订单金额或商品分类计算折扣率和折扣金额。折扣计算应使用函数，历史订单中的实际折扣和成交价应保存到订单或订单明细中。

**修复内容**：

1. 新增 `dbo.fn_member_discount_rate(@member_phone)`：
   - 空会员返回 `1.00`；
   - 未知会员返回 `NULL`；
   - 过期会员返回 `1.00`；
   - 有效会员按 `card_level` 读取 `card_type.discount_rate`。
2. `dbo.fn_sale_discount` 改为：

```sql
fn_sale_discount(@subtotal decimal(10,2), @member_phone varchar(11))
```

   - 内部先调用 `fn_member_discount_rate` 得到 rate，再计算折扣金额；
   - 不再把 rate 作为输入。
3. `api.usp_sale_calculate` 改为从 `fn_sale_discount(@subtotal,@member_phone)` 同时取 `discount_rate` 与 `discounted_amount`，不再直接查 `card_type` 取 rate。

**同步修改**：

- `db/function.sql`：新增会员折扣率函数，替换折扣函数签名；
- `db/sale-entry.sql`：销售计算改调新签名；

### W10-F04｜`usp_replenishment` 是授权/JSON 包装，不是重复查询

**级别**：已查证：非缺陷（包装层）

**查证结论（2026-11-16）**：

> `usp_replenishment` 不是把补货计算重写一遍。它只做三件事：校验库管身份与会话、读取商品库存字段、调用 `fn_replenishment_quantity` 取建议量，最后返回 JSON。补货计算仍只有函数一份实现。

**位置**：

- `db/procedure.sql:55-70`
- `db/results/week-10/object-contracts.md:10`

**实际对象**：

```text
api.usp_sales_statistics   销售统计
api.usp_adjust_stock       库存调整（内部共用）
api.usp_replenishment      补货查询包装
```

**课程展示重点**：

```text
销售统计过程
库存调整过程
补货量函数
销售汇总表值函数
```

**为什么需要这一层**：

| 需求 | 函数能否直接承担 | 包装过程的作用 |
|---|---|---|
| 校验库管岗位与会话版本 | 不能调用 `usp_require_employee`（UDF 不能调用存储过程） | 先执行 `usp_require_employee` |
| 返回商品名称、在架、已订、可售、目标、建议量 | 标量函数只能返回一个值 | 组装 JSON 结果集 |
| 给应用角色授权 | `function.sql` 没有对应用户的 `EXECUTE` 授权 | `procedure.sql:98` 授予 `bookstore_app_inventory` |
| 页面/DAO 统一走 `EXEC` | 函数需改写为 `SELECT` | 保持现有 DAO 调用方式 |

**结论**：

- 计算没有重复：包装过程内部仍调用 `fn_replenishment_quantity`；
- 多出的只是一个**授权 + 结果整形**的 facade；
- 如果去掉它，页面要么直接 `SELECT` 函数（需补函数授权），要么在应用层拼商品字段（破坏“页面只调用数据库对象”的约定）；
- 保留该过程是合理的，报告中标注“辅助包装，不计入核心 2 过程”即可。

**证据**：

- `db/procedure.sql:55-70`（签名、`usp_require_employee`、调用函数、JSON）
- `db/procedure.sql:98`（授予库存应用角色执行权限）
- `db/function.sql:9-17`（只有补货量计算，没有授权与商品字段）
- `db/results/week-10/object-contracts.md:9-10`

### W10-F05｜新旧两个入口指标不同，不是数据不一致

**级别**：非一致性问题（指标口径说明）

**查证结论（2026-11-16）**：

> 两者读同一数据库，但不是同一指标的两份副本：`usp_management_read('reports')` 从 `fund_flow` 汇总现金收支；`usp_sales_statistics` 从 `sale` / `sale_item` 汇总销售单与商品。指标来源、时间字段和业务含义都不同，因此数字不同不等于“数据不一致”。

**位置**：

- `db/management-entry.sql`（`@action='reports'`）
- `db/procedure.sql:72-96`
- `docs/reviews/review-week-10-baseline.md:17`

**两个入口的实际口径**：

| 入口 | 读取 | 主要指标 | 时间字段 |
|---|---|---|---|
| `usp_management_read('reports')` | `fund_flow` | 现金余额、经营收入、经营支出、经营利润 | `recorded_at`（可按日期过滤） |
| `usp_sales_statistics` | `sale`、`sale_item` | 订单数、销量、原价金额、成交实收、商品明细 | `sold_at` |

**为什么不是“两边读同一份结果”**：

- 旧报表是**现金口径**：销售收款、采购付款、退款都进入 `fund_flow`；注资/提现被排除；
- 新统计是**销售口径**：按成交单汇总，实收是成交时金额，退款不在同一指标里直接扣减；
- 同一笔销售在“成交时”进入销售统计，在“实际收付款时”进入资金流水，时间点可能不同；
- 因此两个数字**可以合法地不同**，不需要强行对齐；需要对齐时应做“销售 → 收款 → 退款”的勾稽，而不是直接比较总额。

**是否存在一致性错误**：

- 没有“同一指标被复制成两份”的问题；
- 存在的是**命名/口径风险**：两个页面都可能出现“销售金额”字样，读者容易误以为是同一指标；
- 需要在报告或对象说明中写清：一个是现金收支，一个是销售成交统计。

**为什么查询也做成过程而不是函数**：

| 原因 | 说明 |
|---|---|
| 多形态结果 | `usp_management_read` 按 `@action` 返回不同 JSON 结构；函数只能返回固定表/标量 |
| 身份校验 | 过程可调用 `usp_require_employee`；UDF 不能调用存储过程 |
| 分页/临时表/事务 | 旧报表与新统计使用分页、临时表或一致性读；函数限制更多 |
| 统一调用 | 应用 DAO 统一 `EXEC`，返回 `result_json`；改成函数要重写调用与授权 |

> 只读查询**可以**用表值函数；但不是“必须”。本项目的约定是：**计算用函数，业务查询/权限入口用过程**。`usp_replenishment` 是这一约定的另一个例子。

**证据**：

- `db/management-entry.sql`（`reports` 从 `fund_flow` 汇总）
- `db/procedure.sql:85-95`（新统计从 `sale`/`sale_item` 汇总）
- `docs/reviews/review-week-10-baseline.md:17`（旧报表保留）
- `db/results/week-10/sql-cases.txt:3-8`（新统计 45.00/42.25）

### W10-F06｜补货函数的“未知商品”没有独立错误（已修复）

**级别**：已修复（入口层错误码，2026-11-16）

**先修正记录**：

> 入口 `usp_replenishment` 并没有把“商品不存在”复用成 `52301`。实际映射是：空值/负目标 → `52301`；商品不存在 → `52304`；测试 W10-R03-id 也是 `52304`。真正的问题是：**函数 `fn_replenishment_quantity` 对未知商品只返回 `NULL`，函数本身没有独立错误**，只有经过包装过程才变成 `52304`。

**位置**：

- `db/function.sql:9-17`
- `db/procedure.sql:60-68`

**实际行为**：

| 输入 | `fn_replenishment_quantity` | `usp_replenishment` |
|---|---|---|
| 商品不存在 | `NULL` | `52304` |
| `@goods_id` 为空/≤0 | `NULL` | `52301` |
| `@target` 为空/负 | `NULL` | `52301` |
| 库存达到目标 | `0` | 返回建议量 0 |
| 库存低于目标 | 正数 | 返回正数 |

**修复前边界（2026-11-16，库管身份直调）**：

| `goods_id` | `target` | 修复前错误 |
|---:|---:|---|
| 999（不存在） | 10 | `52304` 商品不存在 |
| 999（不存在） | NULL | `52301` 参数错误 |
| 999（不存在） | -1 | `52301` 参数错误 |
| 0 | 10 | `52301` 参数错误 |

原因是原 `usp_replenishment` 把两个参数放在同一个 `IF` 里，参数错误先于商品查询：

```sql
IF @goods_id IS NULL OR @goods_id<=0 OR @target IS NULL OR @target<0
    THROW 52301, N'请提供商品编号和非负的目标可售量。', 1;
-- 之后才查询商品；查不到才 THROW 52304
```

所以修复前：**“未知商品 + 合法目标”是 52304；“未知商品 + 非法目标”会被参数错误先拦住，表现为 52301。**

**修复后（2026-11-16）**：

```sql
IF @goods_id IS NULL OR @goods_id <= 0
    THROW 52301, N'请提供有效的商品编号。', 1;
IF NOT EXISTS(SELECT 1 FROM dbo.goods WITH(HOLDLOCK) WHERE id=@goods_id)
    THROW 52304, N'商品不存在。', 1;
IF @target IS NULL OR @target < 0
    THROW 52301, N'请提供非负的目标可售量。', 1;
-- 之后才查询商品并调用 fn_replenishment_quantity
```

| `goods_id` | `target` | 修复后错误 |
|---:|---:|---|
| 999（不存在） | 10 / NULL / -1 | `52304` 商品不存在 |
| 0 | 10 | `52301` 参数错误 |
| 3（存在） | NULL / -1 | `52301` 参数错误 |
| 3（存在） | 10 | 正常返回建议量 |

**课程原文**：

> 库存已经达到目标时返回 0，商品不存在时进行明确处理，返回值不能为负数。

**修复内容**：

- `usp_replenishment` 改为三段校验：`goods_id` 语法 → 商品存在性 → `target` 合法性；
- 未知商品不再被 `target` 参数错误抢先拦截，固定返回 `52304`；
- `fn_replenishment_quantity` 保持纯计算：未知商品/空参数/负目标返回 `NULL`。标量 UDF 不能 `THROW`（SQL Server 报 443），因此错误码边界放在包装过程，而不是函数内。

**测试同步**：

`db/tests/week-10-objects.sql` 新增：

```text

W10-R03-id-null 未知商品 + target NULL → 52304

W10-R03-id-zero goods_id 0 + target 10 → 52301
W10-R03-null    商品存在 + target NULL → 52301
W10-R03-negative 商品存在 + target -1  → 52301
```
