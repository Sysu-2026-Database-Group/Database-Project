## 8 项目推进过程、困难与阶段复盘

### 8.1 推进方法与记录依据

项目按“先明确业务，再建立可复现基线，再解释和修正设计，最后封装应用与验证交付”推进。每次阶段完成都检查三件事：新增了什么能力，哪些旧事实必须保持，尚有哪些问题留到下一阶段。周次是课程任务顺序，审查日期是实际复核时刻，两者不强行一一对应；例如第一至四周的正式 review 都在 2026-10-06 汇总，而独立空库复现在 2026-10-05 已有记录。

本章综合 `docs/reviews/review-week-1.md` 至 `review-week-4.md`、第六周正式验收、`ER/review-v1.0.md`、`ER/review-v1.4.md`、Web 实施台账及 11 月 4—6 日复现和整改记录。第五周没有另造一份不存在的 review，使用实际 ER 审查记录。以下心得是依据问题与修复过程形成的项目复盘，不代填成员个人感言或签收。

### 8.3 第一至二周：先统一业务含义，再决定字段

初期困难是经营概念容易混用：库存既可能指当前余额，也可能指发生过的出入库；订单可能指销售，也可能指尚未成交的预订；退款与实物回收也不必同时发生。若在这些含义尚未统一时开始建表，后续外码、金额和岗位权限就会出现不同解释。

处理方式是先在场景、角色、业务规则和数据边界文档确定范围，再把对象映射到数据字典。可售量以在架减已订现算，经营盈亏按资金事由汇总，避免为了“字段齐全”重复保存所有查询结果。单据与明细分开，流水指回业务来源，使每个字段都能解释用途。

第二周 review 同时提醒了材料与设计是两项检查：当前字典和样例可以支持关系讨论，但原引用的独立样例文件缺失，不能沿用历史“通过”就声称严格提交材料齐备。这一项在推进表中继续列为待核实。体会是业务清楚、字段合理和交付文件存在需要分别证实，引用路径也应视为验收的一部分。

### 8.4 第三至四周：从脚本成功到空库可复现

DDL 阶段的困难是“在已有数据库运行成功”可能依赖残留对象或旧样例。项目增加结构校验、重复装载与冲突保护，保存 19 表、47 外码、77 行的固定基线；现金 1430.30、经营盈亏 -69.70 等结果作为可复算检查。CRUD 只操作本事务新建数据并回滚，避免演示修改污染原样例。

第四周把查询正确性和授权正确性进一步分开。销售查询采用外连接保留非会员单，商品汇总保留无销量商品；三个统计视图与基表核对差异为 0。跨档参数属于跨行规则，用补充触发器验证，而不是重复创建已有单行约束。三类店内角色各有允许操作与越权反例，越权实际返回 229。

2026-10-05 的非作者新实例、新库九步复现为脚本顺序提供了证据。第三周 review 又发现草案仍写“待独立复现”，与正式结果冲突；处理原则是以正式执行记录判断结果，并保留草案发生时状态供追溯。体会是复现不仅检查 SQL，也检查文档能否把他人带到同一结果；正式状态应有单一依据，过程记录不能任意改写成当前结论。

### 8.5 第五至六周：模型审查、理论纠偏与可靠迁移

ER 绘图最初暴露出标签压属性、双线矩形不清、说明占据图中部等可读性问题。10-11 的审查通过移动采购单区域、补真正双线框、将说明移入独立栏和补样例覆盖表逐项修正。后续又发现 C-5 仅表示当前参数的取值口径，没有物理关系落点；审查后移除该历史联系，保留空编号与参数快照规则，避免把“计算时取值”画成“存在外码”。

部分基数曾混淆业务应有上界与数据库已有保证，例如采购一次付清、预订最多取货一次。处理方式是在图中表达业务要求，在映射表写清约束、主动回归或流程各自实现到哪里。v1.4 继续修正悬浮端点、复合码和来源含义，核对 19 表137字段及 PNG 内嵌图源；10-22 的人工确认只覆盖对应正式版本，不能用旧图通过替代新图审查。

第六周还有理论与执行两类困难。理论上，初稿忽略确定计算和归属依赖，把四表判断得过于理想；复核后明确 `sale`、`reservation`、`point_movement`、`fund_flow` 严格非 3NF，保留业务冗余并说明维护代价。执行上，新增列在同一静态批次编译不可见，改用动态 SQL 批次；SQLCMD 目标由调用者显式传入并增加原库防护；反例数据必须选已有会员回滚，才会真正命中重复回滚约束。

最终以新副本、旧列快照、查询比较、22 反例、权限、1913 故障回滚和日期变异形成验收链。心得是理论分析需要接受纠正，约束通过不能替代范式证明；迁移可靠也不能只看最终表数，必须观察中途失败是否能恢复，并明确自动过期、幂等、并发入口在当时尚未实现。

### 8.6 从销售入口到四角色闭环：按依赖推进

10-23 销售入口把登录基础推进为可提交的业务：预览不写库，确认时重新复核，销售、库存、积分和资金同事务，成功请求可重放。该轮最终 48 项包括当时的登录及销售测试，不能拿这个数字代表后续采购、预订、退款已经完成。多连接和故障用例在起步阶段就验证关键不变量，避免只按页面数量衡量进度。

11-01 规划指出当时只有销售主链，安装入口还缺跨档触发器和三个视图，因此先安排 P0 基线与精确授权，再做 P1 公共布局、错误和日志，然后推进采购资金、顾客预订与到期任务、会员、退款回收、员工和经营查询，最后做 P6 交付。采购付款先有资金来源，收货再影响库存；取货复用销售规则；退款有原销售作为计算依据。这一顺序减少了后续能力建立在未稳定基础上的返工。

扩展中遇到测试夹具缺 guest/task、会员改联系号码后续费误建第二身份、取消终态缺请求区分、金额预览无有效期、移动端表格溢出及店长单据查询缺口。相应措施是补齐六身份夹具，保持会员原主键稳定并用联系映射解析，记录主体/动作/请求结果，给确认加时限和重算，修订布局及全店查询。新增会员办理、联系方式历史独立保存，21 实体模型以增量文档交付，不覆盖19实体历史成果。

另一个困难来自证据保护：给第六周受保护文档追加 Web 说明改变字节，导致历史指纹审计失败。处理为恢复历史文件原 SHA-256，把 Web 扩展放进独立文档，保留旧 manifest；Git 换行问题则通过 `.gitattributes` 明确检出规则，并在三种换行设置下审计。体会是历史可复现依赖的不只是数据库，文件字节、工具配置和证据归属也要被管理。

### 8.7 复现审查推动的整改：从可用到可交付

11-04 复现中出现一个重要反差：119 项测试通过，但全新 setup 仍被写死的“6 个索引”检查阻断。Web 已新增第 7 个筛选唯一索引，旧检查没有随依赖变化更新。整改为按索引名和启用状态校验，指出缺失/多余对象，并用索引改名反例验证判据。复现记录中先使用了本地补丁，不能据此宣称未修正源码原本就能从零安装；最终结果以合入修复后的新库验收为准。

| 问题与发现方式 | 处理措施 | 复核记录与体会 |
| --- | --- | --- |
| stop 后残留进程、运行日志未落盘 | 根据已记录进程停止并校验，增加后台启动和 `web.log` | 三次生命周期残留 0；启动成功还要能停止和排障 |
| 表单类别必填与后端不一致 | 类别切换时同步显示、禁用和 required 属性 | 图书/文创分支验证；前端与后端应使用同一业务条件 |
| 开卡成功但无自助凭证 | 事务中写凭证摘要并返回凭证 | 新开卡后可自助查询；业务完成需包含用户能继续使用的结果 |
| 三无商品不能删除及无效按钮 | 受控删除入口，服务端检查库存、上架状态及引用资格 | 合法删除与 409/403 反例；按钮资格不能代替数据库复核 |
| 删除后同编码无法重建 | 删除商品时同步清理对应 `book`/`toy` 子类行 | G-08 重建成功；不能只检查 DELETE 成功，还要检查后续可用性 |
| 金额、时间与错误页不统一 | 公共 money/rate/dt 过滤器、按状态标题、503 重试入口 | 页面复验；展示口径也影响业务结果能否正确理解 |

11-06 最终审查保留了限制：删除五类引用没有逐类完成同等实测、真实 500 缺安全取证、部分成员签收尚未补齐等。该文件结尾的概括性“全部处理”必须结合明细的“未单独构造”“仅实测报价引用”阅读，本报告采用较具体的覆盖范围。其引用日期和用语也不倒推为本次重新验收。

### 8.8 阶段取证与报告整理

11-07 为报告新建隔离副本，台账记录 setup 29 步、doctor 6 项、test 44 步、119 项用例零失败/错误/跳过及数据库/HTTP 验证；Edge 16 个节点和 SQL 对账分别保存在 JSON。11-05—06 的28步 setup 与这轮29步安装属于不同阶段，记录保留各自环境，不为了让表格一致而改数。演示结束后 Web 和到期任务停止，证据可回到对应运行 ID 追溯。

11-09 报告从以 Web 为主、第五六周仅列路径，演进为包含 ER、规范化、迁移和测试过程的阶段报告；随后按“总体架构—第五周—第六周—Web 成果”重新编排。本轮继续补充测试思路与推进复盘。报告编辑没有重新执行历史业务实验，测试数量和结论沿用原证据，调整前版本单独备份。

资料整理仍保留真实限制：第二周独立样例文件待核实；林泽群分工及签收待补；另机完成已有用户确认但原始输出待补；新21实体全图的组员人工签收未据此补写；更广退款/回收并发和性能验证仍为后续工作。项目推进的终点不是把所有状态改成通过，而是让完成、边界和责任都可解释、可追溯。

### 8.9 推进过程中的心得体会

第一，先确定业务语义，再选择表和接口。退款与回收分开、当前参数与历史快照分开，使数据库和页面能共同解释业务，而不是后期靠补字段修补含义。对四类角色能做与不能做的提前约定，也直接成为权限反例的来源。

第二，把“不变量”作为阶段交接条件。前期是19表、47外码和旧账，迁移时是旧事实不变，应用时是一次动作中账目同步，交付时是新环境能重建。每轮在新增能力之外检查旧基线，才有机会发现历史指纹、安装缺对象和子类残留等跨阶段问题。

第三，审查要同时检查实现和测试判据。反例若没有正确冲突数据，可能测不到目标约束；权限测试若接受任意错误，可能把 SQL 故障误判为拒绝成功。索引改名、权限注入、日期变异与故障回滚让测试本身受到检验，比只增加正常页面截图更能提高结论可信度。

第四，完成标准要覆盖用户操作的前后过程。开卡后能否取得凭证、删除后能否复用编码、服务能否停干净、错误后能否重试，都属于交付的一部分。一次按钮成功和119项通过仍不能代替独立复现与逐页使用审查。

第五，允许纠正理论与历史结论，但必须保留来源。四表范式纠偏、ER多轮修订和不同日期的测试数量变化，都反映认识与能力逐步完善。正式记录、历史草案、AI技术检查和本人签收应各有归属；未完成项清楚登记，比扩大“全部通过”的含义更有助于团队继续推进。
