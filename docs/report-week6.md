## 2. 设计思路与规范化依据

### 2.1 依赖分析的口径

对 19 张现有表逐表记录关系模式、一行代表的业务事实、主码、全部候选码、外码、关键函数依赖、三类更新异常、1NF / 2NF / 3NF 判断和保留 / 分解理由。函数依赖来自业务规则和稳定的业务标识，不能仅由当前样例中没有重复值推断。

规范化判断与跨表流程约束分开处理。例如：

- 商品编号可以决定商品当前名称和当前价格，但不能决定历史销售明细中的成交价；
- 当前会员档位参数不能覆盖历史销售中的折扣率、积分抵扣和实付金额快照；
- 采购明细的批次进价不能由供应商当前报价反推；
- 库存计数、有效预订数量、积分余额和资金余额属于跨表汇总或事件链一致性，不能单靠 3NF 判断已经自动维护。

### 2.2 保留与分解取舍

现有结构中，商品超类 `goods` 与 `book` / `toy` 子类型关系保留；销售单与销售明细、采购单与采购明细、预订单与预订明细、退货单与退货明细继续拆分，以保存一单多行和历史快照。库存、积分和资金继续采用事件流水加当前余额 / 计数的结构，因为现有业务需要快速读取当前状态，同时需要通过来源外码回溯事件。

没有为了展示范式而删除成交价、折扣、抵扣、实付或批次进价。删除这些快照会导致当前价格或当前卡档位变化后无法重建历史交易。不能直接由数据库单行约束解决的状态跃迁、累计退货、自动过期和幂等问题，在设计文档中标记为流程入口或后续应用阶段责任。

## 3. 迁移设计与执行过程

### 3.1 迁移前基线

迁移前在工作副本核对：19 张用户表、47 个外码、77 行旧业务数据；四种旧商品在架量为 `6 / 0 / 10 / 19`，商品 1 有效已订量为 `6`；旧会员积分为 `-26 / 0`；旧截面现金余额为 `1430.30`，经营盈亏为 `-69.70`。

迁移前先备份原始库，再还原为 `ShiguangBookstoreWeek6Work`。`ShiguangBookstoreWeek3` 保留为原始基线，不作为迁移写入目标。

### 3.2 `migration.sql` 六项要求

[`db/migration.sql`](../db/migration.sql) 按课程要求覆盖：

1. 创建 `schema_migration` 元数据表；
2. 为 `supplier` 增加 `updated_by` 和 `updated_at` 字段；
3. 设置主码、候选码、员工外码以及商品、销售、积分来源的唯一索引；
4. 对不需要改写的旧业务事实原地保留，仅插入一条迁移版本记录；
5. 在增加唯一约束前检查重复商品细节引用、重复预订销售、重复积分流水和负资金余额，并在提交前再次断言；
6. 不删除、不重命名、不覆盖旧业务表，并在脚本和迁移记录中说明保留策略。

脚本在事务中执行，失败时回滚。再次运行需要从迁移前的初始副本开始，不能在已经存在迁移标记和目标索引的工作副本上重复执行。

### 3.3 迁移后旧场景核对

迁移后通过 `migration-check.sql` 和后续只读回归重新核对旧商品、旧会员、旧单据、旧流水、旧资金截面及目标元数据。物理表和行数发生变化时，以业务键、来源外码和等价查询判断语义是否保留，不能只比较总行数。

## 5. 回归、反例与权限验证

### 5.1 只读回归

`regression.sql` 检查目标元数据、逐表数量、旧场景快照、新场景终态、订单金额、库存 / 有效预订、积分流水、退货分摊、销售状态和资金余额。测试后再次执行只读回归，确认临时测试没有改变合法扩充截面。

### 5.2 结构反例和权限

`regression-negative.sql` 对 22 个已经由 DDL 明确实现的约束进行独立反例测试，包括重复主码 / 业务键、重复父子组合、不存在的外码、非空、数量、来源和资金余额边界；每项都应被拒绝并回滚。

`role.sql` 验证店长、收银员和库存管理员的授权正例，以及收银员改价、库存管理员写销售、店长修改销售金额等越权失败。角色测试只证明数据库对象和列级权限边界，不等于完整岗位业务流程已经实现。

### 5.3 中途失败事务

`transaction-week-6.sql` 先写入临时销售单和合法明细，再用数量为 0 的非法明细触发 `547`。CATCH 块回滚后，临时销售单和明细没有残留，说明该测试事务的失败边界是原子的。

## 6. 实验过程中的问题与修正

第六周执行中处理过以下问题：

1. 迁移脚本首次测试时，新增字段在同一静态批次中不可见，导致 `updated_by` / `updated_at` 报列名无效；改为动态 SQL 批次执行依赖这些新列的约束和检查。
2. SQLCMD 模式下曾出现 `$(DatabaseName)` 未替换和目标数据库不存在的错误；确认脚本目标固定为 `ShiguangBookstoreWeek6Work` 后，按 SSMS SQLCMD 模式和工作库名称重新执行。
3. `schema_migration` 尚未创建时，回归脚本正确停止并提示先完成迁移；补做迁移后再运行回归。
4. 重复退货回滚积分反例最初选择了没有既有回滚记录的散客退货，无法触发唯一约束；改用已有会员销售和已有退货回滚记录作为复制来源，22 个结构反例最终全部通过。
5. 迁移、样例和回归脚本固定使用工作副本，避免误写原始 `ShiguangBookstoreWeek3`。

## 7. 未实现边界与风险说明

以下结果是当前实现边界，不应在报告中写成“功能已通过”：

- 对已取消预订再次直接执行取消 DML 会被接受，当前没有数据库级幂等保护；测试事务已回滚。
- 到期但状态仍为“有效”的预订数量为 2，结果为 `AUTO_EXPIRY_NOT_APPLIED`；当前没有自动过期作业或统一到期入口。
- 直接修改 `goods.stock_total`、库存流水或有效预订状态时，数据库不会自动同步另一侧；当前依靠业务写入约定和主动对账发现偏差。
- 并发销售 / 预订竞争、完整采购 / 取货 / 退货 / 资金统一入口以及所有状态单向推进，留待后续应用开发阶段。

这些边界已通过独立脚本或回滚测试记录，不能用静态样例覆盖。
