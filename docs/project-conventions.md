# 项目规范（物料结构与协作约定）

> 本文档规定**物料放哪儿、怎么命名、怎么流转、什么该进 `docs/`**。
> 项目速览见根目录 `README.md`；设计口径见 `docs/spec-*.md`。

---

## 1. 物料结构

```text
Database-Project/
├─ README.md       项目速览（对外展示的唯一入口）
├─ docs/           正式文档 —— 口径、周任务说明、过程留痕
├─ drafts/         草稿 —— 讨论稿 / 对照表 / 旧稿
├─ homework/       课程官方材料 —— 每周任务原文
└─ db/             建库脚本 —— 可在 SQL Server 直接执行
```

| 目录 | 装什么 | 准入标准（能不能放进去） |
|---|---|---|
| `docs/` | 正式文档 | 内容**已经被敲定**（口径），或属于本周必须留档的产出（任务说明 / 使用记录） |
| `drafts/` | 历史过程稿 | 保留必要的讨论与裁定记录；旧编号不作为实现依据 |
| `homework/` | 课程材料 | **课程官方原文件**，不做二次加工 |
| `db/` | 建库脚本 | **能直接执行**的真实 DDL |

> 「敲定」= 当前统一的判断标准，**不是冻结**；后续仍可修订 —— 修订时**直接改正文**（见 §2.1）。

---

## 2. 各目录规则

### 2.1 `docs/` —— 正式文档

**装三类东西**：

| 类型 | 命名 | 是什么 |
|---|---|---|
| **口径** | `spec-<主题>.md` | 设计口径：场景 / 角色 / 业务与规定 / 数据边界 |
| **周任务说明** | `task-week-N.md` | 保留官方任务原文，并把本组任务拆解与说明合为一节，另列交付与验收标准；实际完成情况以脚本和结果为准 |
| **过程留痕** | `ai-usage-log.md` | 官方要求留档的 AI 协助与人工修改记录（按周追加） |

**四条纪律**：

1. **命名用「前缀 + 名字」，不用编号** —— 前缀如 `spec-` / `task-`，名字要能一眼看出是什么。
   （旧的 `NN-<主题>.md` 两位编号写法**已废止**。）
2. **只留最新版** —— 修订时**直接改正文**：**不留版本记录、不写改动摘要、不保留旧说法**。
   「为什么变成现在这样」去 `drafts/` 看，过程留在那里。
3. **只放该放的东西** —— `docs/` 只放**口径本身**。
   **方法说明、走查证据表、验收对应、过程与修改记录，一律不进 `docs/`**
   （它们要么留在 `drafts/`，要么本来就属于 `task-week-N.md`）。
4. **当前有效条目连续编号** —— 业务号 `B*`、规定号 `R-*`、边界清单条号 `A*` 随正式口径调整重排；修改后须全仓搜索并修正引用。历史草稿保留其原编号，不作为实现依据。

> 这里是**唯一可以被 `db/` 脚本与测试用例引用的口径来源**。

### 2.2 `drafts/` —— 草稿

- 命名不限：`<主题>.txt` / `<主题>.md`。
- 收录：讨论稿、数据结构对照表、评审意见、原始需求摘录，以及**旧稿**。
- **双向流转**：
  - 草稿被敲定 → 迁入 `docs/`（自成一份，或并入既有正式文档）；
  - `docs/` 里的文档若需重修 → 退回 `drafts/` 逐份审查，通过后再迁回。
- 经核对仍有决策背景价值的过程稿留在 `drafts/`；与正式口径冲突的旧稿标为历史材料，可在迁移完成后删除。
- 铁律：`drafts/` 里的任何结论都**不是当前口径**，不得作为 `db/` 与测试的依据。

### 2.3 `homework/` —— 课程官方材料

- 保留课程下发的原始 DOCX；可附同名 Markdown 转写以便检索，转写与原件不一致时以原件为准。
- 文件保留原名（含"第 N 周"字样），例如 `第一周任务讲解.docx`。
- 从材料里提炼出的结论**不写在这里** —— 先落到 `drafts/`，敲定后再进 `docs/`。

### 2.4 `db/` —— 建库脚本

- **按阶段分文件**（第 3 周起）：`README.md`（执行顺序与复现说明）、`schema.sql`（建库 + 建表 + 基础约束 + 注释）、`sample-data.sql`（样例数据）、
  `crud.sql`（增删改查演示）；第 4 周再加 `query.sql`、`view.sql`、`constraint.sql`、`role.sql`。
  表之间有大量外键（当前设计 19 张表 / 47 条外键），**建表顺序必须按依赖排**。
- `schema.sql` 从空库建立结构；样例数据和 CRUD 脚本按 `db/README.md` 的顺序执行。重新复现以重新创建的空库为起点；不得对已有经营数据执行破坏性重建。
- 视图 / 触发器 / 存储过程等增量脚本**暂不拆子目录**，先平铺；数量增长后再分层。
- 早期六个单表 SQL 草稿已从 `db/` 移除；Week 3 的新脚本须按当前数据字典编写并实际验证。
- **会员卡参数的阶段落点**：Week 1 在业务与角色文档确定店长设定动作；Week 2 在边界与字典设计 `card_type` 当前配置；Week 3 建表并装入两档初始参数；Week 4 在 `role.sql` 验证只有店长能修改，且参数更新不回改历史销售快照。

## 4. 提交前自检

1. 新增内容落在**正确的目录**（未敲定 → `drafts/`；已敲定 → `docs/`；可执行 → `db/`）。
2. 改动了 `docs/` 的结论时，**直接改正文** —— 不留版本记录 / 改动摘要（见 §2.1）。
3. **写新规则前先搜一遍**：这条是不是已经在别处定过了？（见 §5）
4. **增删条目后检查连续编号及所有引用**（见 §2.1 第 4 条）。
5. `.codebuddy/`、`课堂练习/` 不进版本控制（见 `.gitignore`）。

## 5. 去重与单一出处

**同一规则只在一处定案。** 发现重复时：

- **保留最新那版**（正式文档的**正文**），**删去旧出处**；
- 旧出处若还有导航价值，就**只留一行指针**（"见 §X"），**不复述内容**；
- **"定案记录 / 变更历史"类章节不算口径** —— 口径只在正文。这类章节要么删掉，要么只解释
  "为什么变成现在这样"，**不与正文同步**。

**判据**：同一句话在两份文档里各写一遍，改动时必然漏掉一处 —— 那就叫**重复**，不叫"冗余但无害"。

> 例：同一规则若在 A 文件的「定案记录」和 B 文件的**正文**里各写了一遍 —— **删 A、留 B**，
> A 处若还有导航价值就留一行指针。

**不做规定聚合。** 规则**刻意分散**在四份口径文档里，按职责找：

| 文档 | 装哪一类规则 |
|---|---|
| `spec-scenario.md` §4 | **定性规矩**（"本店有这条规矩"，数值留到业务定） |
| `spec-roles.md` §4 | **权限视角的横切约束** |
| `spec-businesses.md` §3 | **业务口径**（`R-*`，**主表**） |
| `spec-data-boundary.md` §3 | **判据**（不是规定，是"边界为什么这样切"） |

**不建全量规则清单** —— 那会与正文漂移（"定案记录"就是这么烂掉的）。
若将来非做不可，唯一安全形态是**纯指针索引**（编号 + 一句话 + 出处，**不含正文**）。
