## §5 参数化查询与统一异常处理

### 5.1 参数化

- **唯一 SQL 出口**：运行时代码只在 `app/dao.py` 执行 SQL，路由与业务层不出现 `cursor.execute` 或 `pyodbc.connect`。
- **全部参数绑定**：所有用户输入以 `?` 占位传入；排序列、分页大小等动态部分走**白名单**，不拼接用户字符串。
- **过程调用**：写操作统一调用 `api.usp_*` 存储过程，由过程完成规则复核、加锁与原子写入；应用侧只传参数、只读结果。

复核补充：以含 `' OR 1=1 --` 的商品名称提交，服务端原样存储并正常返回，无 SQL 语法错误页。

### 5.2 统一异常

| 情形 | 状态码 | 对外表现 |
|---|---|---|
| 参数/格式/范围错误 | 400 | 指出可纠正字段，不显示数据库值 |
| 未登录、会话失效 | 401 | 提示登录；页面保留返回位置 |
| 岗位不足、CSRF 无效 | 403 | "当前岗位不能执行此操作"/页面已过期 |
| 不存在或无权获知 | 404 | 统一"记录不存在或不可访问"，避免枚举 |
| 业务规则冲突（库存不足、非法状态、重复请求） | 409 | 明确重选/刷新/回到原结果 |
| 数据库连接不可用 | 503 | "系统暂时无法完成操作" + 请求编号 |
| 未预期异常 | 500 | 统一提示，详细原因仅在后端 |

- **统一响应**：API 返回 `{"error":{"code","message"},"request_id"}`；页面复用同一错误页并显示请求编号；响应头携带 `X-Request-ID`。
- **不泄露**：前端不出现 SQL、表名、连接串、服务器路径、堆栈、驱动信息。
- **可定位**：后端日志每条含 `request_id / 时间 / 动作 / 角色 / 错误码 / 结果 / 耗时`；不记录口令、哈希、连接串、Cookie、完整预定码。

复核补充：400 / 401 / 403 / 404 / 409 / 503 均已实测；日志字段齐全且未出现口令或连接信息。

## §6 "必要的删除"如何落实

课程任务 5 要求对商品、库存、订单及明细完成"查询、增加、修改和**必要的删除**"。本项目的业务事实具有**不可变与可追溯**要求（历史单据、资金流水、积分流水必须对得上），因此**不提供物理删除**，而是把"删除"落实为四类**受控的状态迁移**：

| 对象 | 课程字面要求 | 本实现 | 界面入口 |
|---|---|---|---|
| 商品 | 删除 | **下架**（`on_shelf=0`），保留历史引用；已被单据引用的商品不可删 | 店长 → 定价与上下架 |
| 销售单 / 明细 | 删除 | 成交前可编辑/清空待结算清单；**成交后不删行、不改金额**，以**退货冲销**表达纠正 | 收银 → 销售 / 退货 |
| 采购单 | 删除 | 仅草稿可改行/移除行；**提交后冻结**，取消保留单据（状态"已取消"） | 库管 → 采购 |
| 库存流水 | 删除 | 不提供删除或直接改计数；调整一律通过采购入库、销售出库、报损、退货回收**新增流水** | 库管 → 库存与报损 |
| 会员 / 员工 | 删除 | **停用**（`enabled=0`）而非删除，历史单据与留痕保留 | 店长 → 员工账号 |

**这样做的理由**：

1. 销售金额是成交时快照，明细被外码引用；删行会让退货、积分回滚与资金链失去依据。
2. 库存计数必须等于流水累加，直接改数会与 `CK_goods_stock` 及回归断言冲突。
3. 课程"必要的删除"指向的是"业务上必须清除的情形"；在本项目中，这类情形由**下架、取消、冲销、停用**覆盖，并均有角色校验与操作留痕。

**边界说明**：若教师要求演示对 `sale` / `sale_item` 的**字面 DELETE/UPDATE**，需另行确认"未成交草稿模型"并新增结构；本项目当前不宣称已满足该字面口径（见实施规划 §5 的 D0 检查点）。
