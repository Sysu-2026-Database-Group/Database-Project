## 1. 分析约定与范围

函数依赖 `X → Y` 表示：在业务允许的同一关系状态中，X 相同的记录必须具有相同的 Y。依赖依据业务语义与码约束确定；有限样例只能说明例子或推翻依赖，不能证明依赖对所有合法数据成立。当前值与历史快照分别分析。

候选码是能够唯一标识一行的最小属性集合，**主码也是候选码**。主属性指出现在任意候选码中的属性，其余为非主属性。检查 2NF 要考虑全部候选码；检查 3NF 时，对每个非平凡依赖 `X → A`，要求 X 是超码，或 A 是主属性。

范式判断与审计、岗位授权、跨表流程、汇总余额一致性分别记录。例如缺少修改留痕应补足业务能力，但不能据此直接判定该表不满足 3NF。下文范式结论限于已识别的业务函数依赖；后续发现新依赖时需重新检查。

## 2. `supplier`：供应商档案

### 2.1 关系模式、码与引用

一行表示一家供应商的当前档案，独立于报价与采购单存在。按 A7、数据字典及 I-08，本项目保留名称唯一这一约定；这不意味着真实世界的供应商名称天然唯一。

迁移前为四列；第六周当前关系：`S(id, name, created_by, created_at, updated_by, updated_at)`。

| 属性 | 现有类型与约束 | 含义 |
|---|---|---|
| `id` | `BIGINT IDENTITY`，非空，`PK_supplier` | 稳定的供应商编号 |
| `name` | `NVARCHAR(100)`，非空、非空白，`UQ_supplier_name` | 当前名称，允许改名，但不允许重名 |
| `created_by` | `VARCHAR(11)`，非空，外码指向 `employee.phone` | 建档人 |
| `created_at` | `DATETIME2`，非空，默认当前时刻 | 建档时刻 |
| `updated_by` | `VARCHAR(11)`，可空，`FK_supplier_updated_by` → `employee.phone`；非空时为 11 位数字 | 最近一次已记录修改人 |
| `updated_at` | `DATETIME2`，可空，与 `updated_by` 同空同非空 | 最近一次已记录修改时刻 |

全部候选码为 `{id}`、`{name}`，选定主码为 `{id}`。主属性是 `id`、`name`，非主属性是 `created_by`、`created_at`、`updated_by`、`updated_at`。报价表和采购单通过 `supplier.id` 引用供应商，改名无需改写这些外码。

### 2.2 关键函数依赖

```text
id   → name, created_by, created_at, updated_by, updated_at
name → id, created_by, created_at, updated_by, updated_at
```

第一条来自编号标识一个档案；第二条依赖项目明确保留的名称唯一约束。建档人可以登记多家供应商，建档时刻也没有业务唯一约定，二者都不能单独决定供应商身份。旧三行恰由同一人建档，不会因此产生“建档人决定名称”的依赖。

以上描述一个时点的关系状态；名称可以随时间改变，`id → name` 不表示供应商永远不能改名。

### 2.3 三类异常与避免机制

| 类别 | 业务例子与分析 |
|---|---|
| 插入 | 可以先建“博文图书批发”的档案，再登记报价，无需先有商品报价或采购单。建档人必须存在是外码的引用要求，不能据此认定供应商与员工混表导致插入异常。 |
| 修改 | 修改供应商名称只需改本表一行，报价和采购单仍引用原 `id`，避免在多条业务记录中重复改名。I-09 的留痕字段已补齐，但受控入口尚不保证每次改名记录真实操作者和时刻。 |
| 删除 | 删除某家供应商的最后一条报价不会删除供应商档案。供应商仍被报价或采购单引用时，直接删除被外码拒绝，属于引用保护；删除供应商应遵守业务保留规则。 |

同名供应商无法共存是 I-08 的范围取舍，不属于上述函数依赖造成的范式异常。

### 2.4 范式判断与目标建议

| 范式 | 判断依据 | 初稿结论 |
|---|---|---|
| 1NF | 一行一个档案，属性分别保存一个编号、名称、人和时刻，没有供应商或报价列表塞入一个字段 | 满足 |
| 2NF | 两个候选码均为单属性；依据当前规则，不存在非主属性对候选码真子集的部分依赖 | 满足 |
| 3NF | 识别出的非平凡依赖由 `id` 或 `name` 决定，二者均为候选码；没有建档人或时刻决定其他非主属性的业务规则 | 满足 |

**建议保留供应商独立档案与两个候选码，不为展示规范化拆表。** 保留原关系属于恒等变换，原属性与依赖均保留，无需额外连接还原。

针对 I-09，以下字段补强已由 `migration.sql` 在工作副本实施：

```text
S_target(id, name, created_by, created_at, updated_by, updated_at)
候选码：{id}、{name}；主码：{id}
updated_by：VARCHAR(11)，可空，外码 → employee.phone
updated_at：DATETIME2，可空
两列必须同时为空或同时非空。
```

新列表示最近一次已记录的修改人和时刻，依赖完整档案标识，按相同业务假设不会引入部分依赖或不合格的传递依赖。旧记录缺乏可信的修改历史，迁移时两列应为 NULL，表示没有可用修改记录，不能用建档信息虚构修改历史，也不能把 NULL 解读为“从未改过”。该方案只保存最近一次修改；若需要全部改名历史，需另行设计历史表。

成对 CHECK 与员工外码只约束留痕值的形态和引用，不能保证每次改名都会填写留痕，也不能保证填写人就是实际执行人。字段、员工外码、手机号与成对 CHECK 已落地；改名入口、岗位校验和同步更新仍待实现，I-09 部分完成。

## 3. `supplier_quote`：某供应商对某商品的当前报价

### 3.1 关系模式、码与引用

按 A7、B1 / B2，一行表示一家供应商对一种商品的**当前报价**，新报价覆盖旧报价，不保存报价历史。采购明细另存该批实际进价，不能由当前报价反推旧采购成本。

现有关系：`Q(supplier_id, goods_id, quote_amount, reported_by, reported_at)`。

| 属性 | 现有类型与约束 | 含义 |
|---|---|---|
| `supplier_id` | `BIGINT`，非空，外码 → `supplier.id` | 哪家供应商 |
| `goods_id` | `BIGINT`，非空，外码 → `goods.id` | 哪种商品 |
| `quote_amount` | `DECIMAL(10,2)`，非空、必须大于 0 | 当前报价 |
| `reported_by` | `VARCHAR(11)`，非空，外码 → `employee.phone` | 当前报价上报人 |
| `reported_at` | `DATETIME2`，非空，默认当前时刻 | 当前报价上报时刻 |

全部候选码为 `{supplier_id, goods_id}`，亦为 `PK_supplier_quote` 选定的复合主码。没有识别出其他候选码。两列编号为主属性，另外三列为非主属性。“没有额外候选标识”不能解释成“没有候选码”。

### 3.2 关键函数依赖与复合码

```text
(supplier_id, goods_id) → quote_amount, reported_by, reported_at
```

供应商可以给多种商品报价，同一种商品也可以由多家供应商分别报价，所以两列必须共同使用。上报人、上报时刻和报价金额均没有唯一标识报价行的业务约定，也没有“供应商单独决定全部上报人或时刻”的规则。

旧脚本中的三行便于理解：

| `supplier_id` | `goods_id` | `quote_amount` |
|---:|---:|---:|
| 1 | 1 | 22.00 |
| 1 | 2 | 26.50 |
| 3 | 1 | 24.00 |

供应商 1 有两种商品、两种价格，因此 `supplier_id → quote_amount` 不成立。商品 1 有两家供应商、两种价格，因此 `goods_id → quote_amount` 不成立。整组编号才标识一条报价；复合码的成立依据是一对编号只保留一条当前报价的业务规则与主码约束。

### 3.3 三类异常与避免机制

| 类别 | 业务例子与分析 |
|---|---|
| 插入 | 供应商档案和商品档案可先独立建立，再添加报价；无需为添加一个供应商而伪造商品或报价。报价必须引用已有档案是合理的引用要求。 |
| 修改 | 更新 `(1,1)` 的当前报价只改这一行；其他商品或其他供应商的报价保持独立。当前报价改变不能改写采购明细中的历史进价。 |
| 删除 | 删除 `(1,1)` 报价不会删除供应商 1 或商品 1 的独立档案；删除最后一条报价也不应丢失主体信息。 |

覆盖旧报价是明确的当前值语义；不保留报价历史是业务边界，并不自动构成范式异常。`reported_at` 的 DEFAULT 在插入时提供缺省值，**不会因为修改金额而自动刷新**；更新报价时同步上报人与时刻的入口尚待落实。

### 3.4 范式判断与目标建议

| 范式 | 判断依据 | 初稿结论 |
|---|---|---|
| 1NF | 每行是一对供应商与商品，金额、人和时刻分别为单值，没有供应商列表或报价列表 | 满足 |
| 2NF | 三个非主属性依赖整组候选码；没有只依赖其中一列的业务规则，表中也未复制供应商档案属性 | 满足 |
| 3NF | 识别出的非平凡依赖以整组候选码为决定因素；未识别出非主属性之间的不合格依赖 | 满足 |

**建议保留 Q 的五个属性、复合主码与三条外码，不拆分、不增加报价历史表。** 恒等保留可直接保存原记录与全部关键依赖。若今后业务改为保存报价历史，必须重新分析行的含义与码，不能直接沿用当前报价的二列码。

I-02 中的上报人岗位及执行身份一致性应另行处理。现有外码仅保证员工存在，不能证明其为库管或实际操作者；本轮不把该流程缺口写成已强制。

### 3.5 迁移与回归待办

旧样例脚本定义 5 条报价，编号组合及金额为 `(1,1)/22.00`、`(1,2)/26.50`、`(2,3)/8.00`、`(2,4)/2.50`、`(3,1)/24.00`。迁移保留性检查须对比完整五列，不只比较行数或金额。

- 检查重复编号组合、三条引用和金额范围；迁移时保留全部旧报价及留痕，说明该表无需结构调整的依据。
- 验证不同供应商对同一商品报价可共存，重复组合被拒绝，不存在的供应商、商品或员工引用被拒绝，金额为 0 或负数被拒绝。
- 验证合法更新当前报价后，该行上报人和时刻同步，而旧采购明细的批次进价不变。
- 上述合法写入和反例在副本或可回滚事务中执行；临时改价不能留下并改变旧基线。

迁移及旧样例保留已通过工作副本核对；扩充后的 12 条报价也包含在样例装载和总回归中。已执行的反例回归覆盖迁移后 DDL 明确实现的约束，但本轮没有单独验证“报价更新时同步更新上报人 / 时刻”的业务入口；该入口仍待实现或专项验证。结果索引见 [`week-6-migration-check.md`](../db/results/week-6-migration-check.md) 和 [`week-6-regression-negative.md`](../db/results/week-6-regression-negative.md)。

## 4. 独立演示：什么情况才需要分解

本节使用假设关系辅助理解，不是实际目标表，也不在项目数据库建表。

假设把“供应商建档时刻”复制进每条报价：

```text
U(supplier_id, supplier_created_at, goods_id,
  quote_amount, reported_by, reported_at)

关键依赖：
supplier_id → supplier_created_at
(supplier_id, goods_id) → quote_amount, reported_by, reported_at
候选码：{supplier_id, goods_id}
```

`supplier_created_at` 没有唯一约定，是非主属性，却只依赖复合码的一部分 `supplier_id`，因此 U 不满足 2NF。同一家供应商有多条报价时，其建档时刻被重复保存；修正时可能漏改某条，删除最后一条报价会失去这家供应商在 U 中的建档信息，没有报价时也无法仅用 U 正常保存供应商资料。

可以分解为：

```text
S_demo(supplier_id, supplier_created_at)  主码：supplier_id
Q(supplier_id, goods_id, quote_amount, reported_by, reported_at)
                                       主码：(supplier_id, goods_id)
```

两个子关系的交集为 `{supplier_id}`，且 `supplier_id → S_demo`，满足二元分解的无损连接条件；供应商建档依赖由 S_demo 保持，报价依赖由 Q 保持，两者合起来保持所列关键依赖。因此对符合这些依赖的 U，投影后连接可还原 U，而不仅是恰好连接成功几个样例。

此论证范围是 U 的报价信息。真实供应商表还包含没有报价的独立档案，不能用报价连接结果重建全部供应商；真实表应继续独立保留。现有设计已经把供应商档案与报价分开，这正是本轮建议保留的原因。

## 5. `purchase_request`：采购申请单头

### 5.1 关系模式、码与引用

一行表示一张采购申请单的当前流程状态。按 A8、R-5 / R-6 / R-19 / R-26，一单只对应一家供应商，商品及批次进价由明细保存；付款和收货的操作人、时刻分别留在资金、库存流水，不在单头重复保存。

```text
P(id, no, supplier_id, status, created_by, created_at,
  submitted_by, submitted_at, approved_by, approved_at,
  cancelled_by, cancelled_at)
```

| 属性 | 现有类型与约束 | 含义 |
|---|---|---|
| `id` | `BIGINT IDENTITY`，非空，`PK_purchase_request` | 内部单据标识 |
| `no` | `VARCHAR(20)`，非空、非空白，`UQ_purchase_request_no` | 对外单号 |
| `supplier_id` | `BIGINT`，非空，外码 → `supplier.id` | 此单供应商 |
| `status` | `NVARCHAR(10)`，非空，默认草稿，五值 CHECK | 草稿 / 已提交 / 已审批 / 已收货 / 已取消 |
| `created_by` / `created_at` | `VARCHAR(11)` / `DATETIME2`，均非空；人引用 `employee.phone`，时刻默认当前时间 | 建立人和时刻 |
| `submitted_by` / `submitted_at` | `VARCHAR(11)` / `DATETIME2`，均可空，成对 CHECK；人引用 `employee.phone` | 提交人和时刻 |
| `approved_by` / `approved_at` | 同上 | 审批人和时刻 |
| `cancelled_by` / `cancelled_at` | 同上 | 取消人和时刻 |

全部候选码是 `{id}`、`{no}`，主码选择 `{id}`。两者为主属性，其余十列为非主属性。五条外码分别关联供应商以及创建、提交、审批、取消员工。

### 5.2 函数依赖与状态规则的边界

```text
id → no, supplier_id, status, created_by, created_at,
     submitted_by, submitted_at, approved_by, approved_at,
     cancelled_by, cancelled_at
no → id, supplier_id, status, created_by, created_at,
     submitted_by, submitted_at, approved_by, approved_at,
     cancelled_by, cancelled_at
```

单据编号与唯一单号各自标识整张申请。供应商可以出现在多张申请中，员工可操作多张申请，时刻没有唯一约定，均不是单据的决定因素。状态只约束某些留痕是否存在，不能决定实际人员和时刻；例如两张“已收货”单可以具有不同的提交和审批时刻。

可空留痕列表示对应动作尚未发生或不适用。这里按业务含义分析整行标识与依赖，不把 NULL 当作一种真实员工 / 时刻值，也不把“在某状态下必须为空”的条件约束推广成整张关系上的普通函数依赖。

现有阶段 CHECK 检查写入后的状态和留痕组合，时序 CHECK 检查同一行的时刻先后，均不比较修改前状态。**“已取消必须无审批人”不足以保证“审批后不可取消”**：若同时改为已取消、清空审批人和审批时刻、填写合法取消留痕，仅按本表这些 CHECK 和外码仍可能通过。这是静态约束分析，尚未实库试验；I-12 及 ER 映射 D-26 中旧“已拦住”表述已在第 25 步同步纠正，当前仍未进行实库状态跃迁测试。

### 5.3 三类异常与范式判断

| 类别 | 业务例子与避免机制 |
|---|---|
| 插入 | 单头不复制供应商名称和商品列表，供应商可独立建档，一单多商品通过多条明细表达。数据库可以先写单头再写明细；完整业务建单应在事务中形成至少一行明细，不能把库里允许零明细当成合法完整申请（I-11）。 |
| 修改 | 同一单的供应商和流程留痕只在单头保存一次，避免在每条商品行重复修改。供应商改名不影响单据引用；状态回退、清空历史留痕是流程控制缺口（I-12），不是由混存重复属性引起的范式异常。 |
| 删除 | 删除一条商品明细不会连带删除供应商档案或员工信息；删除最后一行明细留下空单头需要流程防止。单头被明细或流水引用时受外码保护，取消单据按 R-5 保留，不以物理删除替代取消。 |

| 范式 | 判断依据 | 初稿结论 |
|---|---|---|
| 1NF | 单头每个字段保存一个值，各类动作以独立属性表达，没有商品或操作人列表 | 满足 |
| 2NF | 两个候选码均为单属性，非主属性没有对码真子集的部分依赖 | 满足 |
| 3NF | 所列非平凡依赖以候选码决定整行；没有供应商、员工、状态单独决定本表其他实际业务值的规则 | 按已识别依赖满足 |

### 5.4 目标建议、迁移与回归待办

建议保留 P 的十二个属性、两候选码及五外码，不为规范化增加状态历史表。恒等保留可保存全部原属性和关键依赖。状态历史表是否需要，应按审计与流程要求另作取舍。

旧样例脚本定义 3 张已收货单：`1 / PR20260906-01 / 供应商1`、`2 / PR20260910-01 / 供应商1`、`3 / PR20260911-01 / 供应商2`，尚不覆盖草稿、已提交、已审批待收货和已取消。本轮不把脚本内容作为当前实库核验结果。

- 迁移前核对旧十二列及单号重复、五条引用、状态和留痕组合；保留原标识、单号、供应商、状态及全部留痕，不补造收货或历史状态。
- 回归重复单号、非法供应商或员工引用、非法状态、单列留痕、错误时序应被拒绝；合法新建 / 提交 / 审批 / 收货 / 取消应通过对应业务入口验证。
- I-02 的岗位与实际执行人、I-11 的至少一条明细、I-12 的前后状态和已提交后明细的修改边界、I-13 的付款及入库一致性，须明确维护入口和事务范围，不能以拆表代替流程实现。
- `verify.sql` 的 `51219` 仅对“已收货”采购单主动比较付款笔数、金额与时序，以及各已有明细的入库总量；不强制写入、不全面覆盖其他状态，也不单独保证一次收货。NULL 比较、零明细和额外入库商品的覆盖需补充回归，不能由现有查询推出完整流程通过。
- 后续安排非法回退、审批后取消（含同时清空审批信息）、终态再次操作、未审批付款 / 入库、重复付款 / 收货等用例；预期业务入口拒绝，尚未实现时如实记录待实现，不预填通过。

## 6. `purchase_request_item`：采购明细与批次进价

### 6.1 关系模式、码与依赖

一行表示某采购申请中的一种商品，数量列表达申请件数；按当前约定，一张采购单内同种商品只出现一行。现有关系：`PI(id, request_id, goods_id, request_qty, unit_cost)`。

| 属性 | 现有类型与约束 | 含义 |
|---|---|---|
| `id` | `BIGINT IDENTITY`，非空，`PK_purchase_request_item` | 明细行编号 |
| `request_id` | `BIGINT`，非空，外码 → `purchase_request.id` | 所属采购单 |
| `goods_id` | `BIGINT`，非空，外码 → `goods.id` | 商品 |
| `request_qty` | `INT`，非空，CHECK 大于 0 | 申请数量 |
| `unit_cost` | `DECIMAL(10,2)`，非空，CHECK 大于 0 | 该批进价 |

全部候选码为 `{id}`、`{request_id, goods_id}`，主码为 `{id}`，复合候选码由 `UQ_purchase_request_item_request_id_goods_id` 保证。主属性是 `id`、`request_id`、`goods_id`，非主属性是 `request_qty`、`unit_cost`。

```text
id → request_id, goods_id, request_qty, unit_cost
(request_id, goods_id) → id, request_qty, unit_cost
```

`request_id` 单独不能决定一行的商品、数量或进价，因为一张单可有多种商品；`goods_id` 单独也不能决定数量或进价，因为同一商品可出现在多个采购批次。代理键存在不免除对复合候选码的检查。

### 6.2 当前报价与历史进价

旧样例的两笔采购来自同一家供应商、同一种商品，却有不同的批次进价：

| 明细 `id` | 采购单 `request_id` | 供应商（由单头关联） | 商品 `goods_id` | 数量 | 批次进价 | 行金额 |
|---:|---:|---:|---:|---:|---:|---:|
| 1 | 1 | 1 | 1 | 5 | 22.00 | 110.00 |
| 3 | 2 | 1 | 1 | 3 | 23.50 | 70.50 |

`supplier_quote` 的 `(1,1)` 当前报价为 22.00，不意味着第二批进价也必须是 22.00。当前报价是参考参数，`unit_cost` 是该采购批次的进价，两者不具有必须相等的约束。若把旧单金额改为关联当前报价计算，第二批会从 `3 × 23.50 = 70.50` 变为 `3 × 22.00 = 66.00`，就改写了原采购事实。

因此不能为了减少看似重复的价格而删除 `unit_cost`，也不能用当前报价回填旧进价。相同“供应商＋商品”在不同采购单中可有不同成本，批次身份需要包含采购单，而不只是供应商和商品。

### 6.3 三类异常与范式判断

| 类别 | 业务例子与避免机制 |
|---|---|
| 插入 | 商品和供应商档案独立存在，明细只关联已有采购单及商品，不必重复录入档案。一张单第二种商品可正常增加一行；同种商品以数量表达，重复组合被唯一约束拒绝。 |
| 修改 | 合法编辑阶段调整该批数量或进价只影响该明细；当前报价更新不能传播到旧明细。审批 / 付款 / 收货后能否修改及如何保护相关账目须由流程另行限制，现有正数 CHECK 不保证历史冻结。 |
| 删除 | 删除明细不删除商品或供应商资料；最后一行删除导致零明细单头是 I-11 的流程问题。旧明细关联实际付款 / 入库，应保留并核对，不能以删除历史记录消除异常。 |

| 范式 | 判断依据 | 初稿结论 |
|---|---|---|
| 1NF | 每行一商品，数量与进价为单值，不在一列保存多个商品 | 满足 |
| 2NF | 数量与进价由 `id` 或整组 `(request_id, goods_id)` 决定，不依赖复合码的一部分 | 满足 |
| 3NF | 所列非平凡依赖的决定因素均为候选码；没有数量决定进价或进价决定数量的规则 | 满足 |

### 6.4 目标建议、迁移与回归待办

建议保留 PI 的五个属性、两候选码和两外码，不删除批次进价，也不增加供应商或当前报价列。恒等保留可保存原关系与关键依赖。通过 `request_id` 关联单头可得到供应商、状态和流程留痕，通过 `goods_id` 得到当前商品档案；这些查询不替代历史批次进价。

单头与明细内连接能重建已有明细对应的采购信息；由于外码保证每条明细恰好找到一张单头，不会因单头匹配产生多行。零明细单头会被内连接遗漏，核对完整单头范围应使用单头查询或左连接。这是当前查询方式说明，不宣称本轮实际进行了模式分解。

旧脚本定义 5 条明细，三张采购单行金额合计分别为 **189.50 / 70.50 / 130.00**，旧采购总额 **390.00**。这些是根据旧脚本计算的预期，实际付款与入库仍待核验。

- 迁移前检查原五列、重复 `(request_id, goods_id)`、两条引用以及数量 / 进价范围；保留原明细标识、所属单和所有旧数量、成本。
- 验证合法“一单多商品”和“同一商品多批次不同价”成功；重复 `id` 或复合候选码、不存在的单头或商品、数量或进价为 0 / 负数应被拒绝。
- 在可回滚事务或副本中更新当前报价，核对旧明细及 **189.50 / 70.50 / 130.00** 原单金额不变；同时核对采购付款、入库商品和数量，不只比较总行数。
- W6-S03 / W6-S11 已使用新单据补充采购阶段和多批次场景；旧 3 单 5 行保留。装载及总回归结果见 [`week-6-sample-data.md`](../db/results/week-6-sample-data.md) 和 [`week-6-regression-readonly.md`](../db/results/week-6-regression-readonly.md)。这些结果验证静态样例与账目截面，不代表采购状态跃迁的完整受控入口已经实现。

## 7. `sale`：销售单与成交金额快照

### 7.1 关系模式、码与依赖

一行表示一张已经形成的销售单。单头保存顾客身份、成交时的会员档位和计价结果；商品及其成交单价、数量保存在 `sale_item`。现有关系为：

`S(id, no, status, cashier_by, sold_at, card_level, member_phone, reservation_id, subtotal_amount, discount_rate, point_deduction_amount, paid_amount)`。

| 属性 | 现有类型与约束 | 含义 |
|---|---|---|
| `id` | `BIGINT IDENTITY`，非空，主键 | 内部销售单标识 |
| `no` | `VARCHAR(20)`，非空、非空白、唯一 | 顾客核对使用的销售单号 |
| `status` | `NVARCHAR(10)`，三值 CHECK | 已付 / 部分退款 / 已全退 |
| `cashier_by`、`sold_at` | 非空员工外码、非空时刻 | 收银员与成交时刻 |
| `card_level`、`member_phone` | 均可空；会员时按规则填写 | 成交时的会员身份与档位快照 |
| `reservation_id` | 可空外码 | 到店取货来源；门店直销为空 |
| `subtotal_amount` | 非空金额 | 折扣前原始总额快照 |
| `discount_rate` | 非空，`0 < 值 ≤ 1` | 成交时采用的折扣率快照 |
| `point_deduction_amount` | 非空、非负金额 | 本单积分抵扣金额 |
| `paid_amount` | 非空、非负金额 | 折扣及抵扣后的实付金额 |

候选码为 `{id}`、`{no}`，主码选择 `{id}`；`id` 与 `no` 是主属性，其余属性是非主属性。按当前约束可列出：

```text
id → no, status, cashier_by, sold_at, card_level, member_phone,
     reservation_id, subtotal_amount, discount_rate,
     point_deduction_amount, paid_amount
no → id, status, cashier_by, sold_at, card_level, member_phone,
     reservation_id, subtotal_amount, discount_rate,
     point_deduction_amount, paid_amount
```

收银员可以办理多张单，会员可以有多张历史销售，卡档位和折扣率也会随时间改变，因此不能推出 `member_phone → card_level` 或 `card_level → discount_rate`。这里的档位、折扣率、金额是成交时快照；它们不是当前 `member` 或 `card_type` 的可更新值。

### 7.2 三类异常与范式判断

| 类别 | 业务例子与避免机制 |
|---|---|
| 插入 | 非会员门店直销可以在 `member_phone`、`reservation_id` 为空时建单；会员取货再填写相应外码。商品清单不塞进单头，而由 `sale_item` 多行表达。 |
| 修改 | 调整当前商品价格、会员档位或卡档位配置不应回写旧单；成交价、折扣率、原始总额、抵扣额和实付额必须保留为历史快照。退款只改变退款累计和状态流程，不把原单金额改成当前价格。 |
| 删除 | 销售单被明细、退货、库存、资金和积分流水引用时受外码保护。已退销售仍保留原单与快照，不能通过删除单据消除退款或出库历史。 |

| 范式 | 判断依据 | 初稿结论 |
|---|---|---|
| 1NF | 每个字段保存单一值，商品列表、积分流水和退款列表分别放在明细或流水表 | 满足 |
| 2NF | 候选码均为单属性，不存在非主属性对复合码一部分的依赖 | 满足 |
| 3NF | 已识别的单行依赖均由 `id` 或 `no` 决定；会员当前档位、商品当前价格和退款汇总不作为本表内的决定因素 | 按已识别依赖满足 |

`subtotal_amount = Σ(sale_item.unit_price × quantity)`、累计退款决定 `status`、实付额对应资金流水等属于跨表聚合或流程约束，不是把单头拆成更多表就能自动获得的范式结论。`CK_sale_amount` 已检查单行金额等式和抵扣上限，但未强制实际积分余额、销售收款笔数、退款状态跃迁和库存 / 积分流水完整性。

### 7.3 目标建议、迁移与回归待办

建议保留销售单的十二个属性、两个候选码和三条外码。拆出“当前会员价格”或“当前卡档位”会破坏历史成交快照；把单头金额全部改为查询时计算也可能丢失当时的四舍五入和抵扣结果。`UX_sale_reservation_id` 已对非空预订引用强制至多关联一张销售单；取货前有效、取货后置“已取”及库存 / 收款原子联动仍需受控流程（I-16 部分完成）。

旧样例有三张销售单，状态分别为已全退、部分退款、已付；其中销售单 2 为一单两行，销售单 3 为非会员取货销售。旧金额与退货比例是迁移前事实，不能因为当前价格或卡档位改变而重算。

- 迁移前核对十二列、`id` / `no` 唯一性、三条外码、金额 CHECK 及会员 / 非会员组合，保留原状态、成交时刻和全部金额快照。
- 回归非法状态、空白单号、非会员折扣或抵扣、抵扣超过折后金额 20%、实付等式错误等拒绝用例；同时区分 CHECK 能拒绝的单行错误和必须由业务入口校验的积分余额、收款、退款、库存及状态跃迁。
- 以 `51212`、`51214`、`51217`、`51220` 为现有主动校验入口，分别核对单头与明细金额、退款状态、销售收款和库存出库；这些查询的通过只说明当前截面，不等于写入过程已被全面强制。

## 8. `sale_item`：销售明细与成交价快照

### 8.1 关系模式、码与依赖

一行表示某张销售单中的一种商品。现有关系为：`SI(id, sale_id, goods_id, quantity, unit_price)`。

| 属性 | 现有类型与约束 | 含义 |
|---|---|---|
| `id` | `BIGINT IDENTITY`，非空，主键 | 销售明细行标识 |
| `sale_id` | `BIGINT`，非空外码 → `sale.id` | 所属销售单 |
| `goods_id` | `BIGINT`，非空外码 → `goods.id` | 售出的商品 |
| `quantity` | `INT`，非空、`> 0` | 售出数量 |
| `unit_price` | `DECIMAL(10,2)`，非空、`≥ 0` | 成交时单价快照 |

候选码为 `{id}`、`{sale_id, goods_id}`，主码为 `{id}`；复合候选码由 `UQ_sale_item_sale_id_goods_id` 保证。主属性是 `id`、`sale_id`、`goods_id`，非主属性是 `quantity`、`unit_price`。依赖为：

```text
id → sale_id, goods_id, quantity, unit_price
(sale_id, goods_id) → id, quantity, unit_price
```

`sale_id` 单独不能决定商品、数量或成交价，一张单可以有多种商品；`goods_id` 单独也不能决定成交价，同一商品可在不同时间、不同会员档位或不同销售单中以不同价格成交。`unit_price` 不能用当前 `goods.price` 回填。

### 8.2 三类异常与范式判断

| 类别 | 业务例子与避免机制 |
|---|---|
| 插入 | 一张单增加第二种商品只需增加一行；商品档案和销售单头独立保存，不必复制名称、会员或金额。相同销售单中重复同一商品由复合唯一约束拒绝，用 `quantity` 表示多件。 |
| 修改 | 调整某一销售行数量或成交价只影响该历史行；当前商品售价变化不传播到旧销售行。已产生退货、资金或库存流水后能否编辑，须由业务入口限制，正数 / 非负 CHECK 本身不提供历史冻结。 |
| 删除 | 删除明细不会删除商品档案；但被退货明细或库存流水引用的销售行受外码保护。删除最后一行会形成零明细销售单，需由建单流程或主动校验防止。 |

| 范式 | 判断依据 | 初稿结论 |
|---|---|---|
| 1NF | 一行一个商品，数量和单价各为一个值，不把商品列表放进列中 | 满足 |
| 2NF | `quantity`、`unit_price` 依赖完整的 `(sale_id, goods_id)`，不依赖其一部分 | 满足 |
| 3NF | `id` 或完整复合候选码决定全部非主属性；没有商品编号决定历史成交价的规则 | 满足 |

### 8.3 目标建议、迁移与回归待办

建议保留五个属性、两个候选码和两条外码。`sale_item` 只保存成交时数量和单价；退货明细通过 `sale_item_id` 找到原商品和原单价，不重复保存 `goods_id` 或当前售价。单头的 `subtotal_amount` 与明细行金额存在跨表核对关系，不能把它误判成同一关系内的传递依赖。

- 迁移前核对原五列、重复 `(sale_id, goods_id)`、销售单和商品两条引用、数量 / 单价范围；保留原行标识、成交价和数量。
- 验证一单多商品、同一商品跨多单不同成交价、退货按原销售行定位等合法场景；重复代理键或复合候选码、不存在的销售单 / 商品、零或负数量应被拒绝。
- 保留旧样例四行（销售单 2 有两行），用 `51212` 检查行金额与单头原始总额，用 `51220` 检查卖出流水数量；退货累计数量与金额由 `51213` 主动核对。
- 新增样例已使用新销售单和销售明细覆盖非会员直销、会员折扣、积分抵扣、多商品销售及部分 / 全额退货；旧三张销售单和四条明细保留。装载及总回归结果见 [`week-6-sample-data.md`](../db/results/week-6-sample-data.md) 和 [`week-6-regression-readonly.md`](../db/results/week-6-regression-readonly.md)。回归验证数据状态及金额 / 数量对账，不等于完整销售与退货业务入口已经实现。

## 9. `reservation`：预订单与有效期快照

### 9.1 关系模式、码与依赖

一行表示一张预订单。预订只记录下单时的手机号、预定码、有效期和取消留痕，不保存金额、折扣或冻结库存。现有关系为：

`R(id, code, phone, status, created_at, expires_at, cancelled_by_employee, cancelled_at)`。

| 属性 | 现有类型与约束 | 含义 |
|---|---|---|
| `id` | `BIGINT IDENTITY`，非空，主键 | 内部预订单标识 |
| `code` | `VARCHAR(20)`，非空、非空白、唯一 | 顾客使用的预定码 |
| `phone` | `VARCHAR(11)`，非空、非空白、手机号格式 | 下单时填写的联系电话；有意不作为会员外码 |
| `status` | `NVARCHAR(10)`，四值 CHECK | 有效 / 已取 / 已过期 / 已取消 |
| `created_at`、`expires_at` | 非空；有效期 CHECK 为下单后 3 天 | 下单时刻与过期时刻 |
| `cancelled_by_employee`、`cancelled_at` | 可空；取消时的操作人和时刻成对出现 | 取消留痕；顾客自行取消可不记员工 |

候选码为 `{id}`、`{code}`，主码选择 `{id}`。当前约束表达的主要依赖为：

```text
id   → code, phone, status, created_at, expires_at,
       cancelled_by_employee, cancelled_at
code → id, phone, status, created_at, expires_at,
       cancelled_by_employee, cancelled_at
```

`phone` 不能决定会员档位或会员资料；同一手机号可以有多张历史预订单。`status` 也不能决定取消人和时刻之外的业务事实，已取、已过期、已取消是流程状态，不是拆表理由。

### 9.2 三类异常与范式判断

| 类别 | 业务例子与避免机制 |
|---|---|
| 插入 | 不依赖会员档案即可创建预订单；一张预订的多个商品行放在 `reservation_item`，不会把商品列表塞进单头。预定码重复、空白手机号或非法有效期由唯一约束与 CHECK 拒绝。 |
| 修改 | 当前会员资料、商品价格或会员档位变化不应回写预订单；有效期是下单时的 3 天规则。取消操作只补充取消留痕并按流程改变状态，CHECK 不能比较更新前状态，状态跃迁仍需流程校验。 |
| 删除 | 被销售单或明细引用的预订单不能随意删除；删除最后一条明细会造成零明细单头，属于 I-11 的流程问题。历史已取、已过期或已取消预订应保留，不能用删除代替状态归档。 |

| 范式 | 判断依据 | 初步结论 |
|---|---|---|
| 1NF | 每个字段是单值；商品集合、数量集合单独放入 `reservation_item` | 满足 |
| 2NF | 候选码均为单属性，非主属性不存在对复合码的部分依赖 | 满足 |
| 3NF | 已识别的非平凡依赖由 `id` 或 `code` 决定；`phone`、状态和时刻之间没有应保留在本表的传递依赖 | 按已识别依赖满足 |

`expires_at = DATEADD(day, 3, created_at)`、取消留痕成对出现等是列间约束；“有效预订才占用已订量”“取货后必须变为已取”“一张预订至多对应一张取货销售”属于跨表或时序流程约束，不能把它们误写成 3NF 结论。当前 `CK_reservation_cancel` 只检查写入后的状态与留痕组合，不保证审批或取货后的状态不可回退。

### 9.3 目标建议、迁移与回归待办

建议保留 8 个属性、两个候选码和 `cancelled_by_employee` 的员工外码。`phone` 保持非外码，避免把下单手机号误当成会员身份；金额、折扣、积分和库存冻结均不加入预订单。

- 迁移前核对 `id` / `code` 唯一性、手机号格式、状态枚举、有效期是否恰好三天、取消留痕成对关系，以及被 `sale.reservation_id` 引用的行；保留原状态和时刻。
- 回归有效、已取、已过期、已取消四种状态，覆盖员工代取消、顾客取消、过期计算、重复预定码和取货销售引用；分别记录 CHECK 能拦截的单行错误与必须由流程校验的状态跃迁。
- 保留旧样例的两张预订单（已取 / 有效）作为基线；`reservation = 2` 及有效预订对 `reserved_qty` 的汇总应与 `51210` 对账，不把当前一次查询结果写成强制约束已通过。

## 10. `reservation_item`：预订明细与数量快照

### 10.1 关系模式、码与依赖

一行表示某张预订单中的一种商品及预订数量。现有关系为：

`RI(id, reservation_id, goods_id, quantity)`。

| 属性 | 现有类型与约束 | 含义 |
|---|---|---|
| `id` | `BIGINT IDENTITY`，非空，主键 | 预订明细行标识 |
| `reservation_id` | `BIGINT`，非空外码 → `reservation.id` | 所属预订单 |
| `goods_id` | `BIGINT`，非空外码 → `goods.id` | 预订的商品 |
| `quantity` | `INT`，非空且大于 0 | 本预订中该商品的数量 |

候选码为 `{id}`、`(reservation_id, goods_id)`，主码选择 `{id}`。函数依赖为：

```text
id                    → reservation_id, goods_id, quantity
(reservation_id, goods_id) → id, quantity
```

单独的 `reservation_id` 不能决定商品或数量，一张预订可以有多种商品；单独的 `goods_id` 也不能决定某张预订中的数量。

### 10.2 三类异常与范式判断

| 类别 | 业务例子与避免机制 |
|---|---|
| 插入 | 同一预订增加第二种商品只需增加一行；同一预订同一商品重复出现由组合唯一约束拒绝，多件商品用 `quantity` 表达。不存在的预订或商品由外码拒绝。 |
| 修改 | 修改数量只影响该预订明细；商品档案或商品当前价格变化不应回写历史预订数量。有效预订的汇总数量、库存可用量和取货扣减属于跨表校验。 |
| 删除 | 删除明细不会删除商品；删除一张预订的最后一行会形成零明细单头，需由建单或删除流程阻止。已取预订的明细还可能被取货销售引用，不能以删除逃避历史记录。 |

| 范式 | 判断依据 | 初步结论 |
|---|---|---|
| 1NF | 一行一个商品，`quantity` 为单值正整数 | 满足 |
| 2NF | `quantity` 完整依赖复合候选码 `(reservation_id, goods_id)`，不存在只依赖其中一部分的非主属性 | 满足 |
| 3NF | `id` 或完整复合候选码决定全部非主属性；没有 `goods_id` 决定数量的规则 | 满足 |

`reservation_item` 的行数、商品数量之和与 `goods.reserved_qty` 的关系是跨表聚合；只有状态为“有效”的预订才计入汇总。该关系满足范式不等于已保证 `reservation` 至少一行明细、数量不超库存或取货后扣减完整。

### 10.3 目标建议、迁移与回归待办

建议保留 4 个属性、代理主键、组合唯一约束和两条外码；不新增商品名称、价格或预订状态列，避免复制商品档案和单头状态。

- 迁移前核对 `id` / `(reservation_id, goods_id)` 重复、数量正值、两条外码和每张预订的明细覆盖；保留两条旧样例行。
- 回归一单多商品、同商品重复、零 / 负数量、不存在的预订或商品、已取预订仍保留明细，以及有效预订汇总与 `reserved_qty` 的对账。
- 使用 `51210` 检查“有效预订明细数量 = 商品已订量”；该查询是主动校验，不能替代写入时的跨表强制约束。

## 11. `goods_return`：退货单与退款金额汇总

### 11.1 关系模式、码与依赖

一行表示一次退货受理记录。退货单只指向原销售单并记录本次退款金额、经办人和时刻；具体退哪些销售行及数量保存在 `goods_return_item`。现有关系为：

`GR(id, no, sale_id, refund_amount, handled_by, handled_at)`。

| 属性 | 现有类型与约束 | 含义 |
|---|---|---|
| `id` | `BIGINT IDENTITY`，非空，主键 | 退货单内部标识 |
| `no` | `VARCHAR(20)`，非空、非空白、唯一 | 对外退货单号 |
| `sale_id` | `BIGINT`，非空外码 → `sale.id` | 退货对应的原销售单 |
| `refund_amount` | `DECIMAL(10,2)`，非负 | 本次退货退款金额汇总 |
| `handled_by`、`handled_at` | 非空员工外码与受理时刻 | 退货经办留痕 |

候选码为 `{id}`、`{no}`，主码选择 `{id}`。在当前业务口径下的主要依赖为：

```text
id  → no, sale_id, refund_amount, handled_by, handled_at
no  → id, sale_id, refund_amount, handled_by, handled_at
```

`refund_amount` 是本次退货的金额快照与汇总，不由当前商品价格重新计算；退货单可以对应同一销售单的多次退货，因此 `sale_id` 不能决定本行的金额或时刻。

### 11.2 三类异常与范式判断

| 类别 | 业务例子与避免机制 |
|---|---|
| 插入 | 同一销售单可以分多次退货，每次建立独立退货单；具体商品行放入 `goods_return_item`，不会把多个商品塞进单头。重复退货单号、负退款金额或不存在的原销售单由唯一约束、CHECK 和外码拒绝。 |
| 修改 | 退货金额和受理时刻是该次业务的历史记录，不能因当前售价、销售单会员档位或折扣变化而回写。累计退款、销售状态、资金流水和积分回滚由跨表流程校验维护。 |
| 删除 | 退货明细、资金流水、库存流水和积分流水引用退货记录时，外码保护历史；删除退货单不能用来绕过累计退货上限或退款留痕。 |

| 范式 | 判断依据 | 初步结论 |
|---|---|---|
| 1NF | 每个字段是单值；商品和数量集合放入明细表 | 满足 |
| 2NF | 候选码均为单属性，不存在对复合码的部分依赖 | 满足 |
| 3NF | 已识别的非平凡依赖由 `id` 或 `no` 决定；原销售单的会员、金额等不复制到本表 | 按已识别依赖满足 |

`refund_amount = Σ goods_return_item.refund_amount`、累计退款不超过实付、销售状态随累计退款变化、退款资金流水恰好一笔等均是跨表聚合或流程约束。`CK_goods_return_amount` 只能保证本行非负，不能单独保证这些关系。

### 11.3 目标建议、迁移与回归待办

建议保留 6 个属性、两个候选码和 `sale_id` / `handled_by` 外码。不要在退货单中重复保存会员身份、原销售单金额或商品信息；原单价从 `sale_item` 追溯，退款金额保留本次实际处理结果。

- 迁移前核对 `id` / `no` 唯一性、原销售单外码、退款金额非负、员工外码和受理时刻；保留两张旧退货单及其金额 `17.85`、`111.15`。
- 回归同一销售单多次退货、部分退款、全额退款、零退款和超过原销售数量等场景，区分单行 CHECK 与 `51213`、`51214`、`51216`、`51218` 等主动校验。
- 旧样例 `goods_return = 2` 必须保留；单头金额与明细汇总、销售状态和退款流水的结果分别记录，不能只核对退货单行数。

## 12. `goods_return_item`：原销售明细与退货数量快照

### 12.1 关系模式、码与依赖

一行表示某次退货中针对一条原销售明细的退货数量及退款金额。现有关系为：

`GRI(id, return_id, sale_item_id, quantity, refund_amount)`。

| 属性 | 现有类型与约束 | 含义 |
|---|---|---|
| `id` | `BIGINT IDENTITY`，非空，主键 | 退货明细行标识 |
| `return_id` | `BIGINT`，非空外码 → `goods_return.id` | 所属退货单 |
| `sale_item_id` | `BIGINT`，非空外码 → `sale_item.id` | 被退的原销售明细 |
| `quantity` | `INT`，非空且大于 0 | 本次退回数量 |
| `refund_amount` | `DECIMAL(10,2)`，非负 | 本次该行退款金额快照 |

候选码为 `{id}`、`(return_id, sale_item_id)`，主码选择 `{id}`。函数依赖为：

```text
id                         → return_id, sale_item_id, quantity, refund_amount
(return_id, sale_item_id)  → id, quantity, refund_amount
```

单独的 `return_id` 可以包含多条原销售明细；单独的 `sale_item_id` 也可出现在多次退货中，因此两者均不能单独决定数量或退款金额。

### 12.2 三类异常与范式判断

| 类别 | 业务例子与避免机制 |
|---|---|
| 插入 | 一次退货可以包含多种原销售商品，每种商品一行；同一次退货重复指向同一销售明细由组合唯一约束拒绝。不存在的退货单或销售明细由外码拒绝。 |
| 修改 | 修改数量或退款金额只影响这次退货明细；当前商品价格不能回写原销售成交价或既有退款快照。累计退货量不能超过原销售行数量，需主动校验。 |
| 删除 | 删除明细会改变退货汇总、库存回补、资金退款和积分回滚，不能用删除历史行代替冲正流程；外码保护已关联的销售明细。 |

| 范式 | 判断依据 | 初步结论 |
|---|---|---|
| 1NF | 一行一个原销售明细，数量与金额均为单值 | 满足 |
| 2NF | `quantity`、`refund_amount` 完整依赖复合候选码 `(return_id, sale_item_id)`，不存在部分依赖 | 满足 |
| 3NF | `id` 或完整复合候选码决定全部非主属性；商品和原单信息由 `sale_item_id` 追溯，不复制到本表 | 满足 |

“同一次退货的明细必须属于同一原销售单”、累计数量不超过原销售数量、明细金额合计等是跨表依赖。当前唯一约束只防止同一退货单重复出现同一原销售行，不能单独完成这些业务校验。

### 12.3 目标建议、迁移与回归待办

建议保留 5 个属性、代理主键、组合唯一约束及两条外码；不新增 `goods_id`，因为商品可由 `sale_item_id` 唯一追溯，避免重复存储。

- 迁移前核对 `id` / `(return_id, sale_item_id)` 重复、数量与退款金额范围、两条外码，以及每条明细所属销售单是否等于退货单的 `sale_id`。

- 保留旧样例两条明细：退货单 1 对销售明细 3 退 1 件、退款 `17.85`；退货单 2 对销售明细 1 退 3 件、退款 `111.15`。

## 13. `stock_movement`：库存变动事件流水

### 13.1 关系模式、码与依赖

一行表示一次库存变动事件。商品、变动类别、数量符号和来源外键共同说明库存为何变化；来源根据类别在采购单、销售单或退货明细中三选一，报损时三者为空并填写原因。现有关系为：

`SM(id, goods_id, change_type, quantity, note, changed_by, changed_at, request_id, sale_id, return_item_id)`。

候选码只有 `{id}`，主码为 `{id}`。在当前约束下，`id` 决定其余全部属性。`goods_id`、`change_type`、来源外键和时刻均不能单独决定数量，因为同一商品可多次购入、卖出、退货或报损。

### 13.2 三类异常与范式判断

| 类别 | 业务例子与避免机制 |
|---|---|
| 插入 | 每次事件新增一行；四类变动由 `CK_stock_movement_source` 同时约束类别、数量符号、来源互斥和报损原因。不存在的商品、单据或员工由外码拒绝。 |
| 修改 | 库存事件是历史流水，不能用修改旧行替代冲正或补记；当前库存和已订量由 `goods` 与相关预订 / 流水汇总核对。操作岗位对应目前依赖主动校验 `51221`。 |
| 删除 | 删除流水会改变库存余额、采购入库、销售出库或退货回收入账；已有来源外码保护关联历史，冲正应新增合法事件并保留原行。 |

| 范式 | 判断依据 | 初步结论 |
|---|---|---|
| 1NF | 每行一个事件，数量、类别和来源列均为单值 | 满足 |
| 2NF | 候选码为单属性 `id`，不存在部分依赖 | 满足 |
| 3NF | 非平凡依赖均由 `id` 决定；`goods_id` 不决定数量或来源，来源外键不复制商品 / 单据属性 | 按已识别依赖满足 |

`goods.stock_total = Σ stock_movement.quantity`、销售 / 采购 / 退货数量与相应明细一致、每条业务都必须有流水，都是跨行或跨表约束。当前 CHECK 只能保证单行事件形状，不能替代这些汇总校验。

### 13.3 目标建议、迁移与回归待办

建议保留 10 个属性和四条来源外码；不要把“来源类别 + 单号”改成可自由填写的文本，也不要删除 `note`，因为报损原因是该事件必要的业务说明。

- 迁移前核对 12 行旧样例、四类事件数量符号、来源互斥、报损原因、商品 / 单据 / 员工外码和时间；保留旧库存余额 6 / 0 / 10 / 19 的可复算结果。
- 回归覆盖购入、卖出、退货、报损四类合法写入，以及缺来源、错误符号、报损无原因、跨来源同时填写等非法写入；再用 `51210`、`51219`、`51220`、`51221` 做跨表与岗位主动校验。

## 14. `point_movement`：积分变动事件流水

### 14.1 关系模式、码与依赖

一行表示某会员的一次积分获得、抵扣使用或退货回滚事件。现有关系为：

`PM(id, member_phone, change_type, points, sale_id, return_id, changed_by, changed_at)`。

候选码只有 `{id}`，主码为 `{id}`；`id` 决定其余属性。`member_phone`、`sale_id` 或 `return_id` 不作为全表候选码。第六周三个筛选唯一索引约束每销售单获得 / 抵扣各至多一笔、每退货单回滚至多一笔；这是限定类别中的条件唯一性，不推广成全表普通函数依赖。

### 14.2 三类异常与范式判断

| 类别 | 业务例子与避免机制 |
|---|---|
| 插入 | 获得、抵扣、回滚使用同一流水表，通过类别与积分正负表达方向；会员、销售单、退货单和员工由外码引用。三个按类别筛选的唯一索引已限制重复发放、抵扣和回滚，不要求应有事件一定生成。 |
| 修改 | 积分流水是历史账，不能直接改旧行来修正会员余额；积分余额应与流水合计对账，回滚必须指向原退货和原销售单。第六周类别 CHECK 已强制三类 `sale_id` 非空；历史 `verify.sql` 的 `51215` 未修改，当前 `regression.sql` 的 `51552` 显式检测 NULL、错误原单与会员，但不在写入时拦截错误跨表归属（I-18）。 |
| 删除 | 删除流水会改变会员积分余额和退货回滚结果；应通过冲正事件或受控流程处理，不能删除历史流水来“平账”。 |

| 范式 | 判断依据 | 初步结论 |
|---|---|---|
| 1NF | 每行一个积分事件，点数与来源列为单值 | 满足 |
| 2NF | 候选码为单属性 `id`，不存在部分依赖 | 满足 |
| 3NF | 非平凡依赖均由 `id` 决定；会员档位、销售金额和退货金额不复制到积分流水 | 按已识别依赖满足 |

`member.points_balance = Σ point_movement.points`、获得积分等于实付金额向下取整、抵扣点数与金额换算、回滚挂原单且一退货最多一笔，均属于跨行或跨表业务约束。范式满足不代表这些账务规则已由 DDL 强制。

### 14.3 目标建议、迁移与回归待办

已保留 8 个属性、代理主键和四条外码；`CK_point_movement_kind` 强制三类 `sale_id` 非空，仅回滚的 `return_id` 非空，其余两类退货来源为空。`UX_point_movement_earn`、`UX_point_movement_use`、`UX_point_movement_return` 分别按“消费获得 / 抵扣使用 / 退货回滚”筛选并限制事件上界。物理 `sale_id` 仍可空，合法行到销售单的实际参与为 `(1,1)`。跨表原单 / 会员归属、点数算式、余额同步仍需校验与业务事务，I-18 部分完成。

- 迁移前核对 5 行旧样例、会员余额与流水合计、三类点数符号、回滚原单和员工外码；保留旧积分余额 `-26 / 0` 的可复算结果。

## 15. `fund_flow`：资金收付事件流水

### 15.1 关系模式、码与引用

一行表示一笔已经发生或登记的收付事件，六类事由共用同一事件粒度：销售收款、采购付款、退货退款、办卡费、注资、提现。关系模式可写为：

```text
FF(id, amount, direction, reason_type, sale_id, return_id,
   request_id, member_phone, fund_before, fund_after,
   recorded_by, recorded_at)
```

当前约束下候选码只有 `{id}`，主码也选择 `{id}`。没有其他稳定的业务候选码：同一会员可以多次办理、续办或升级并产生多笔办卡费；同一销售单既可能有一笔销售收款，也可能对应多次退货退款；采购单和退货单虽然业务上各应有一笔相应流水，但数据库目前没有用唯一约束表达这个上界。`(recorded_at, id)` 只是按时间排列流水并在同刻打破平局的排序键，不是业务身份。

`id → amount, direction, reason_type, sale_id, return_id, request_id, member_phone, fund_before, fund_after, recorded_by, recorded_at` 是当前关系中需要检查的主要函数依赖。`reason_type` 与四个来源外码的互斥组合由 `CK_fund_flow_source` 约束；`direction` 与 `amount` 的加减关系由 `CK_fund_flow_balance` 约束。这些是同一行内的域 / 列间约束，不应误写成“某个来源单独决定金额”。退款金额、销售实付、采购明细合计、办卡费收费规则以及前后流水连续性都需要跨表或跨行校验。

四个来源列的含义分别是：销售收款或退款使用 `sale_id`，退款另外使用 `return_id`；采购付款使用 `request_id`；办卡费使用 `member_phone`；注资和提现四个来源列均为空。`recorded_by` 必须指向存在的员工，具体岗位是否匹配事由由 `51221` 主动检查。

### 15.2 三类异常与范式判断

| 类别 | 具体风险 | 当前防线与边界 |
|---|---|---|
| 插入异常 | 可以挂到存在但尚未满足业务条件的单据；同一采购单或退货单可以写入多笔流水；办卡费可以写成与当时卡档位不符的金额；v0.1 的负余额缺口已在第六周补上 | 外码、`CK_fund_flow_source` 和同一行余额 CHECK 能拦住来源形状与算术关系；`51216`—`51219`、`51223`、`51224` 以及 I-13、I-14、I-17、I-20 的跨表规则仍需主动校验或事务控制；`CK_fund_flow_amount` 已强制前后余额非负（I-19 已完成） |
| 修改异常 | 修改金额、方向或时刻会同时影响本行快照、后续流水链和经营盈亏；修改来源或事由可能让资金与原单脱钩 | `CK_fund_flow_balance` 只检查当前行；`51223` 按时间检查链条，不能阻止写入后再修改历史；历史流水应采用追加或受控更正策略 |
| 删除异常 | 删除一行会改变现金余额、经营盈亏和前后链条；删除被单据引用的流水还会受到外码或主动校验影响 | 当前没有“资金流水不可删除”的专门约束；迁移和应用事务应保留旧流水，并把更正记录为可追溯事件或受控操作 |

每个属性都是一个标量：金额、方向、事由、至多四个可空来源标识、前后余额、登记人和时刻，没有把多笔收付塞进一个字段，因此满足 1NF。候选码只有单属性 `{id}`，不存在复合候选码下的部分依赖，满足 2NF。按已识别的业务依赖，所有非平凡依赖的决定因素都是 `{id}`，或右侧为主属性；来源互斥、余额加减和时间连续性属于约束而不是新的非主属性传递依赖，因此按当前关系语义满足 3NF。

这里的 3NF 判断不等于“资金业务已经完整实现”。`fund_before` 与 `fund_after` 是为了保存当时的余额快照而有意保留的冗余；`fund_after` 的非负性、同一来源单据的流水上界、收付与单据金额相等、办卡费按当时档位收费、岗位匹配和并发下的链条连续性，均不是单表范式问题。

### 15.3 旧样例、目标建议与迁移回归

旧样例共有 **13 行**，覆盖六类事由。资金快照从 `0.00` 依次接到 `1430.30`；经营盈亏只计算业务自动收付，注资与提现计入现金余额但不计入经营盈亏：

```text
现金余额 = 1430.30
经营盈亏 = 349.30（销售收款）+ 100.00（办卡费）
          − 390.00（采购付款）− 129.00（退货退款）
```

建议保留一张事件流水表，不按六类事由机械拆表：所有事件都需要金额、方向、登记人、时刻和余额快照，拆表会重复维护资金链并增加跨表合并的风险。第六周已落实单行非负约束，其余增强项仍待评估：

## 16. `member`：会员档案与当前权益

### 16.1 关系模式、候选码与函数依赖

会员表一行表示一位会员的当前档案，不记录姓名；关系模式可写为：

```text
M(phone, card_level, opened_by, opened_at,
  updated_by, updated_at, expires_at, points_balance)
```

当前候选码只有 `{phone}`，主码也是 `phone`。手机号是会员的业务身份；卡档位、开卡人、开卡时刻、最近一次换卡人和时刻、到期日以及当前积分余额都由该手机号唯一决定。其他字段没有已知的业务唯一性，不能单独或组合替代手机号识别会员。

主要函数依赖为：

```text
phone → card_level, opened_by, opened_at,
         updated_by, updated_at, expires_at,
         points_balance
```

这里的 `card_level` 只表示当前档位。`card_type.card_fee` 和 `card_type.discount_rate` 是当前档位参数，不能反推出历史办卡费用或历史销售折扣；历史销售应继续使用销售单上的成交快照。`points_balance` 是当前余额快照，业务上要求它等于 `point_movement.points` 的跨行合计，但这个等式不是会员单行内部的函数依赖，也不能仅凭本表的 CHECK 约束保证。

### 16.2 三类异常与范式判断

| 类别 | 可能的异常 | 当前防线与边界 |
|---|---|---|
| 插入异常 | 只要引用存在的卡档位和员工，就可以插入会员；办卡费是否已登记、金额是否符合办理时规则、有效期是否按升级 / 重买规则计算，不能由本表单独确定 | `card_level`、员工外码、手机号格式、日期关系及成对更新留痕由 DDL 部分约束；办卡费与有效期流程需结合 `fund_flow` 和业务事务检查（I-20） |
| 修改异常 | 直接修改 `card_level`、`expires_at` 或 `points_balance`，可能与历史办卡流水、积分流水和正在生效的销售规则脱节；`updated_by/updated_at` 只留下最近一次换卡 | 会员档案外码和成对 NULL 约束只能保证引用与行内配对，不能代替历史审计、余额同步或档位状态跃迁控制（I-10、I-15） |
| 删除异常 | 删除会员会影响销售、积分流水和办卡资金流水的引用；即使外码阻止删除，也没有说明业务上是否应保留已发生交易的会员档案 | 迁移和应用事务应采用保留策略；不得用删除会员来清理测试数据，测试应使用独立副本或回滚 |

按当前已识别的依赖，`member` 满足 1NF：每个字段都是单值，积分余额是一个数值快照，不是把多笔积分塞进一个字段。它满足 2NF：唯一候选码 `phone` 是单属性，不存在部分依赖。它满足 3NF：`phone` 决定其余非主属性，`card_level` 不决定某个会员的其他档案属性；卡档参数、积分合计、有效期和收费规则属于跨表或业务流程约束，不应据此把本表判为不满足 3NF。

### 16.3 旧样例、目标建议与迁移回归

旧样例保留两位会员：`13900000001` 当前为金卡，换卡后到期日仍为 `2027-09-08`，积分余额为 `-26`；`13900000002` 当前为金卡、尚未换卡，积分余额为 `0`。迁移前按手机号核对当前档位、开卡人与时刻、最近变更人与时刻、到期日和余额，不得因增加场景而覆盖这两行或把负积分改成零。

目标结构暂建议保留会员当前档案表和 `points_balance` 快照，但把余额维护放入与 `point_movement` 同一事务的业务入口；是否采用触发器、存储过程或应用层事务锁，须在实现阶段比较并记录。`opened_by/opened_at` 与 `updated_by/updated_at` 继续表示创建及最近一次变化留痕，不把它们误写成完整审计历史。办卡、重买和升级的历史金额继续放在 `fund_flow`，不能对 `member_phone` 设置唯一约束，因为同一会员可以多次办理或升级。

迁移后的旧场景回归至少包括：

- `member.points_balance = SUM(point_movement.points)`，两位会员分别得到 `-26` 和 `0`，并保留正负积分流水；
- 到期日当天有效、次日失效；过期会员重买后恢复权益，正负积分均保留；有效期内重买顺延，银卡升级金卡按差价收费且原到期日不变；
- 办卡费、升级差价与 `fund_flow` 的会员归属和金额能够对账，历史销售折扣不因当前档位变化而改写；
- 直接改余额、引用不存在的档位或员工、填写非法日期，以及重复发放 / 回滚积分时，得到预期拒绝或主动检查结果；`51211`、`51215`、`51222` 的范围和 NULL 安全限制要单独记录，不能把静态结果写成流程已经通过。

## 17. `card_type`：会员卡档位当前参数

### 17.1 关系模式、候选码与函数依赖

会员卡档位表一行表示一个档位的当前参数，不保存每次修改的历史版本。关系模式可写为：

```text
CT(level, card_fee, discount_rate, set_by, set_at)
```

当前候选码只有 `{level}`，主码也是 `level`。`level` 的取值域限定为“银卡”和“金卡”；`card_fee`、`discount_rate`、最近设定人 `set_by` 和最近设定时刻 `set_at` 都由档位名决定。办卡费、折扣率或设定时刻不能反过来唯一识别档位，也不能组成稳定的业务候选码。

主要函数依赖为：

```text
level → card_fee, discount_rate, set_by, set_at
```

这里的依赖描述的是当前参数关系。`card_fee` 和 `discount_rate` 会随店长修改而变化，不能用它们反推历史办卡收费或历史销售折扣；历史销售单必须使用 `sale.discount_rate` 等成交快照。`set_at` 只表示最近一次设定时刻，不表示完整的参数变更历史。

### 17.2 三类异常与范式判断

| 类别 | 可能的异常 | 当前防线与边界 |
|---|---|---|
| 插入异常 | 行级 CHECK 允许插入一行合法的银卡或金卡，但不能单独保证两个档位都存在，也不能仅靠行内约束比较金卡与银卡的费用和折扣顺序 | `CK_card_type_level`、费用 / 折扣域 CHECK 保证单行取值；`dbo.tr_card_type_cross_row` 在已部署时检查两档的跨行顺序，样例数量检查由 `db/verify.sql` 完成，均不等同于“数据库永远保持恰好两行” |
| 修改异常 | 修改当前费用或折扣会影响之后的新办卡、换卡和成交；若直接改参数而没有同步有效的设定人 / 时刻，留痕会过时；办卡资金流水没有保存办理时费用快照，事后不能用当前参数可靠反算 | 历史销售折扣已经复制在 `sale`；角色脚本只给店长参数列的更新权限，但没有把 `set_by/set_at` 的同步更新入口作为完整机制，关联 I-02、I-03、I-20 |
| 删除异常 | 删除仍被 `member.card_level` 引用的档位会被外码阻止；删除未被引用的档位则可能留下只有一档的配置，破坏当前两档业务设定 | 业务角色没有删除权限，外码保护已有会员；迁移和管理流程仍应明确“银卡 / 金卡档位保留”，不能用删除代替停用或历史处理 |

按当前已识别的依赖，`card_type` 满足 1NF：每个字段都是单值，档位参数不是把多个版本或多个费用塞进一个字段。它满足 2NF：唯一候选码 `level` 是单属性，不存在部分依赖。它满足 3NF：`level` 决定其余非主属性，费用与折扣的跨行比较、档位行数、操作岗位和历史快照是约束或流程规则，不构成新的传递函数依赖。

因此，不能因为 `card_type` 只有当前值、没有历史表，就直接判定它不满足 3NF。是否需要参数历史是审计范围和业务取舍问题，对应 I-03；本阶段保留当前参数关系，并依靠成交快照复核历史销售。

### 17.3 旧样例、目标建议与迁移回归

旧样例必须保留两行：银卡 `20.00 / 0.95`、金卡 `50.00 / 0.90`，两行的设定人均为店长 `13800000001`，设定时刻为 `2026-09-01 09:00`。迁移前后核对档位集合、费用、折扣率、设定人和设定时刻；不得因为增加会员或销售场景而覆盖这两行的初始基线。

目标结构暂建议保留一张当前参数表，不按费用、折扣和设定人机械拆表：这些属性共同描述同一档位在当前时点的配置，拆开会增加同步和跨表读取成本。若后续确实需要回答“某天的档位参数”，再单独评估参数历史表或时态关系；在本周不把历史审计需求误写成现有范式缺陷。

迁移后的旧场景和新增场景至少包括：

- 验证仍只有银卡、金卡两档，金卡费用严格高于银卡，金卡折扣率不高于银卡；`51222` 与跨行触发器的检查范围分别记录；
- 在独立事务中把金卡费用合法增加或折扣合法调整，确认新值可保存，随后回滚，基线仍为 `20.00 / 0.95` 和 `50.00 / 0.90`；
- 尝试把金卡费用改为不高于银卡，或把金卡折扣改得高于银卡，预期由 `tr_card_type_cross_row` 拒绝并回滚；缺少某一档位时不能把“未触发比较”误记成顺序验证通过；
- 店长可以执行授权的参数更新，收银员不能直接修改参数；同时检查设定人 / 时刻是否随业务动作正确留痕，不能只把列级 UPDATE 权限当成完整审计保证；
- 修改档位参数后，新成交使用新折扣率，旧销售单的 `card_level`、`discount_rate`、金额和办卡资金流水不回改；办卡费和升级差价按办理时规则记录，当前参数变化不能替代历史费用快照（I-20）。

## 18. `employee`：员工档案与岗位

### 18.1 关系模式、候选码与函数依赖

员工表一行表示一名店内员工账号，当前场景只有店长、库管和收银员三类岗位；手机号同时作为账号和业务身份。关系模式可写为：

```text
E(phone, name, role, created_by, created_at,
  updated_by, updated_at)
```

候选码只有 `{phone}`，主码也是 `phone`。`phone` 是稳定的业务账号标识；姓名、岗位以及创建 / 最近更新留痕都不能单独或组合替代它。主要函数依赖为：

```text
phone → name, role, created_by, created_at,
         updated_by, updated_at
```

`created_by` 和 `updated_by` 都引用同一张 `employee` 表：前者必填，后者可空；`updated_by` 与 `updated_at` 由成对 CHECK 约束保持同空或同非空。`role` 的合法域是“库管”“收银员”“店长”，但岗位和某个业务动作之间的对应关系需要跨表判断，不能由这一行的函数依赖推出。

### 18.2 三类异常与范式判断

| 类别 | 可能的异常 | 当前防线与边界 |
|---|---|---|
| 插入异常 | 首位员工没有外部员工可作为创建人，只能让引导账号的 `created_by` 指向自己；普通账号若引用不存在的创建人则无法插入 | `created_by` 非空自引用外码保证来源账号存在，样例首位自指对应 I-01；岗位枚举和手机号格式由 CHECK 保证，但不检查创建人是否为店长 |
| 修改异常 | 修改 `role` 会改变该员工当前可执行的岗位含义；历史单据和流水中的 `_by` 仍指向同一账号，不能据此还原当时岗位；修改 `created_by` 会改变建档留痕 | 主码稳定，外码保证引用仍存在；当前表只有最近一次更新留痕，没有字段级历史，也没有把岗位变更与既有业务记录绑定 |
| 删除异常 | 被其他表留痕列或员工自引用列引用的账号不能删除；即使未被引用，删除员工也会破坏账号档案和后续审计解释 | 第六周全库 49 条外码中有 21 条引用员工（20 条来自业务表、1 条来自技术表），提供引用完整性；业务上应保留已产生经营记录的员工，停用 / 离岗策略不在本表中表达 |

按当前已识别的依赖，`employee` 满足 1NF：每个字段是单值，岗位是一个枚举值，不是把多个岗位塞进一列。它满足 2NF：唯一候选码 `phone` 是单属性，不存在部分依赖。它满足 3NF：`phone` 决定其余非主属性；`role` 不决定姓名或留痕，维护人关系是外码联系而非表内传递依赖。首账号自指、岗位授权和历史审计范围属于业务 / 流程规则，不改变该范式判断。

### 18.3 旧样例、目标建议与迁移回归

旧样例必须保留 4 行员工：店长 `13800000001`、库管 `13800000002`、收银员 `13800000003` 和 `13800000004`。首位店长的 `created_by` 继续自指；其余三行的创建人均为店长。迁移前后按手机号核对姓名、岗位、创建人、创建时刻及更新留痕，不能用新增账号覆盖或重排旧账号。

目标结构建议保留一张员工档案表，不把岗位拆成多张表：岗位是员工的一项当前属性，拆分会增加账号与角色连接的维护成本。继续保留两个自引用外码和更新成对约束；若第六周处理 I-02，再评估触发器或统一业务入口，把 `stock_movement`、`fund_flow`、销售及其他留痕列的操作人岗位与动作类别绑定，并明确触发器 / 应用层 / 主动校验各自的边界。不要因为岗位校验不足而把员工表误判为不满足 3NF。

迁移后的回归至少包括：

- 4 行旧员工仍存在，所有既有留痕外码仍能连接到对应账号，首账号自指不被迁移脚本改写；
- 插入缺失创建人、非法手机号或非法岗位时由外码 / CHECK 拒绝；只填写 `updated_by` 或只填写 `updated_at` 时由成对 CHECK 拒绝；
- 店长维护员工账号的权限和收银员 / 库管的越权行为分别记录实际结果；岗位—动作不匹配要用 `51221` 及扩展校验说明“主动发现”还是“写入时拒绝”，不能把当前仅覆盖库存和资金流水的检查写成全库强制；
- 尝试删除仍被单据、流水或其他员工引用的账号，确认外码保护；测试失败后回滚，旧员工数量和所有关联记录不变。

## 19. `goods`：商品超类与库存计数

### 19.1 关系模式、候选码与函数依赖

一行 `goods` 表示一种可销售商品及其当前展示、定价和库存状态；图书与文创的专有识别信息分别保存在 `book`、`toy` 中。关系模式可写为：

```text
G(id, category, name, book_isbn, toy_code,
  on_shelf, price, stock_total, reserved_qty,
  created_by, created_at, updated_by, updated_at)
```

`id` 是 `IDENTITY` 代理主键，当前没有其他业务候选码。`name` 允许重复；`book_isbn` 和 `toy_code` 互斥，其中一个必须为空，不能把这两列组成稳定的业务候选码。主要函数依赖为：

```text
id → category, name, book_isbn, toy_code,
     on_shelf, price, stock_total, reserved_qty,
     created_by, created_at, updated_by, updated_at
```

`category` 只决定哪一个细节引用必须存在，不决定商品名称、价格或库存；同一类别可以有多种商品。`book_isbn` / `toy_code` 是指向细节表的引用，不是当前表内独立标识。`price` 表示当前售价，不能决定或替代历史 `sale_item.unit_price`；`stock_total` 与 `reserved_qty` 表示当前库存快照，不能仅凭本行依赖推出其跨表来源。

现有 DDL 对单行形状提供了以下约束：类别与两个细节引用互斥且匹配，价格非空时必须大于 0，上架时必须已有价格，库存总量和已订量非负且已订量不超过库存总量；创建人和最近更新人引用 `employee.phone`，更新人和更新时间必须同时为空或同时非空。上述约束属于域、引用或行内一致性约束，不会自动维护跨行汇总。

### 19.2 三类异常与规范化判断

| 类别 | 可能的异常 | 当前防线与边界 |
|---|---|---|
| 插入异常 | 新增图书或文创时必须先有对应的 `book` / `toy` 细节和建档员工；若只想登记尚未定价的商品，可以保持不上架并令 `price` 为 `NULL` | 外码、类别 CHECK、员工外码和上架 CHECK 保证基本形状；细节行是否必须被商品引用一次由 I-05 另行讨论，不能由本表单独保证 |
| 修改异常 | 修改当前价格或库存计数只影响商品当前状态，不能回写历史成交价；直接改 `stock_total` / `reserved_qty` 可能与库存流水或有效预订明细脱节 | `CK_goods_stock` 只限制本行范围；I-04 的库存与预订汇总目前依靠事务入口和主动校验，尚未由单行 DDL 完整强制 |
| 删除异常 | 已被采购、销售、预订、报价或库存流水引用的商品不能删除；即使没有引用，删除商品也会使其细节、库存快照和建档留痕失去解释 | 外码提供引用保护；业务上应保留已有经营记录的商品，停用 / 下架优先于删除 |

按已识别的函数依赖，`goods` 满足 1NF：每列保存一个单值，细节编码、状态和计数没有以列表形式塞入字段。它满足 2NF：唯一候选码 `id` 是单属性，不存在部分依赖。它满足 3NF：`id` 决定所有非主属性，`category`、细节引用、当前售价和当前计数没有形成需要拆分的表内传递依赖。库存计数与库存流水、有效预订明细之间的等式属于跨表业务一致性，不应直接当作本关系的 3NF 缺陷。

### 19.3 I-04、I-05 与 I-07 的边界

- **I-04：库存计数跨表等式未由 DDL 强制。** 业务上要求 `goods.stock_total` 等于 `stock_movement.quantity` 的有效合计，并要求 `goods.reserved_qty` 等于有效 `reservation_item.quantity` 的合计。现有 CHECK 只能保证 `stock_total >= 0`、`0 <= reserved_qty <= stock_total`，不能阻止手工更新计数后遗漏流水，也不能自动处理预订取消、过期或取货后的释放。`db/verify.sql` 的相关查询属于主动校验，不等于写入时强制。本周后续应比较统一事务入口、触发器、实时派生查询或保留冗余计数并加强校验的成本；本节不预先选择实现方案。
- **I-05：细节表反向引用没有下界。** 外码方向是 `goods.book_isbn → book.isbn`、`goods.toy_code → toy.inner_code`，因此商品引用的细节必须存在，但不能保证每一行 `book` / `toy` 至少被一行 `goods` 使用，可能出现孤立细节行。这是参与约束和数据边界问题，不是 `goods` 的 1NF / 2NF / 3NF 缺陷。项目暂保留“细节行随商品建档产生”的业务约定，正常路径下可通过 `goods.created_by / created_at` 间接追溯录入人和时刻。
- **I-07：细节引用上界已补强。** 迁移前可多次引用同一细节；第六周在旧数据重复检查后已创建以下两个索引，保证同一非空编码至多被一个商品引用：

  ```sql
  CREATE UNIQUE INDEX [UX_goods_book_isbn]
  ON dbo.[goods]([book_isbn])
  WHERE [book_isbn] IS NOT NULL;

  CREATE UNIQUE INDEX [UX_goods_toy_code]
  ON dbo.[goods]([toy_code])
  WHERE [toy_code] IS NOT NULL;
  ```

  不能直接使用普通 `UNIQUE` 约束：由于每行必有一个细节列为空，SQL Server 对多个 `NULL` 的唯一性处理会使合法的同类商品插入失败。`book` 与 `toy` 两侧已同步实施，旧数据重复检查先于建索引；I-05 的参与下界仍未强制。

### 19.4 旧样例、目标结构与迁移边界

旧样例脚本中的 `goods` 必须保留以下 4 行及其留痕：

| `id` | `category` | `name` | `book_isbn` | `toy_code` | `on_shelf` | `price` | `stock_total` | `reserved_qty` |

## 20. `book`：图书识别与展示细节

### 20.1 关系模式、候选码与函数依赖

一行 `book` 表示一本图书的识别与展示信息，是 `goods` 的可选图书子类型细节。图书有自己的 ISBN，不依赖商品代理键才能被识别；图书与文创的专有属性分表保存，避免把作者、出版社和页数放入所有商品行而产生大量空值。关系模式可写为：

```text
B(isbn, author, publisher, page_count)
```

`isbn` 是主码，也是当前唯一候选码。书名不在本表中，作者、出版社和页数都可能在多本书之间重复，不能单独或组合构成稳定的业务候选码。主要函数依赖为：

```text
isbn → author, publisher, page_count
```

该依赖来自 ISBN 对一本图书的稳定识别。`author` 不决定出版社或页数，出版社也不决定作者或页数；同一作者可以有多本书，同一出版社可以出版多本书，页数也不是图书身份。`goods.book_isbn → book.isbn` 是另一张表的外码引用，不是 `book` 关系内的函数依赖。

现有 DDL 对本行提供以下约束：`isbn` 非空且长度在 10—17 之间，作者和出版社文本非空白，`page_count > 0`；`isbn` 为主键，重复 ISBN 在写入时被拒绝。当前只检查长度和非空文本，没有把 ISBN 校验为某一种纯数字或校验位格式；该格式边界不应被误写成已实现的业务校验。

### 20.2 三类异常与规范化判断

| 类别 | 可能的异常 | 当前防线与边界 |
|---|---|---|
| 插入异常 | 可以先登记一本图书的 ISBN、作者、出版社和页数，再建立对应的商品档案；由于 `book` 不引用 `goods`，也可以插入暂时没有商品引用的孤立图书 | 主键和单行 CHECK 保证 ISBN 不重复、文本非空和页数为正；细节行必须被商品引用一次属于 I-05 的反向参与约束，当前未由本表强制 |
| 修改异常 | 修改作者、出版社或页数只改变图书当前展示信息，不应回写商品名称、历史销售成交价或采购 / 销售明细；本表没有修改人和修改时刻，无法从本行回答“谁改了这本书” | `goods` 仍通过 ISBN 引用同一图书，主键稳定；I-06 的审计缺口由 `goods.created_by / created_at` 间接弥补，不能还原独立细节行的完整历史 |
| 删除异常 | 被 `goods.book_isbn` 引用的图书不能直接删除；没有商品引用的孤立图书可以删除，但删除后会失去这条图书展示信息 | 外码在 `goods` 侧提供引用保护；是否允许删除孤立细节行属于数据边界和保留策略，不是 `book` 表内范式问题 |

按当前识别的依赖，`book` 满足 1NF：每列都是一个 ISBN、作者、出版社或页数，没有把多本书或多位作者塞进一个字段。它满足 2NF：唯一候选码 `isbn` 是单属性，不存在部分依赖。它满足 3NF：`isbn` 是超码并决定全部非主属性，没有发现作者、出版社或页数之间的传递依赖。反向引用的最小 / 最大参与约束和留痕能力属于跨表建模及业务边界，不改变这一范式结论。

### 20.3 I-05、I-06 与 I-07 的联合边界

- **I-05：细节行反向引用没有下界。** 现有方向是 `goods.book_isbn → book.isbn`，数据库能保证商品引用的 ISBN 必须存在，但不能保证每条 `book` 至少被一行 `goods` 引用，因此可能存在孤立图书。项目暂保留“图书细节随商品建档一起产生”的业务约定，不为此反转外码方向；反转会削弱 ISBN 作为独立主标识的优势并扩大迁移范围。
- **I-06：本表没有独立留痕列。** `book` 没有 `created_by / created_at` 或 `updated_*`。正常建档路径下，可以通过引用它的 `goods.created_by / created_at` 间接追溯建档库管和时刻；若图书行孤立，连这条间接路径也不存在。当前建议继续把留痕集中在商品建档上，不在本轮重复增加一套可能与 `goods` 不一致的列；若未来要求细节独立维护或完整历史，再另行设计留痕 / 历史关系。
- **I-07：同一 ISBN 的商品引用上界已完成。** `book.isbn` 主键保证细节自身唯一，第六周 `UX_goods_book_isbn` 另对非空商品引用强制唯一；与文创侧同步实施。I-05 下界仍未强制。

这些问题分别属于反向参与下界、审计留痕和引用上界，不是 `book` 表需要拆分才能满足 3NF 的理由。

## 21. `toy`：文创识别与规格细节

| 核对项 | `goods`—`book` | `goods`—`toy` | 当前结论 |
|---|---|---|---|
| 商品侧基数 | 对这条具体子类型联系为 `(0,1)`；`category = 图书` 时必须有一条匹配图书细节 | 对这条具体子类型联系为 `(0,1)`；`category = 文创` 时必须有一条匹配文创细节 | `CK_goods_category` 与两个外码共同保证类别匹配、恰一个细节列非空 |
| 细节侧业务基数 | `(1,1)`：每条图书细节业务上应恰被一个商品引用 | `(1,1)`：每条文创细节业务上应恰被一个商品引用 | 外码单独不强制细节侧参与；第六周索引补上上界，下界仍未强制 |
| 当前已实现部分 | 商品引用存在性、类别互斥与图书引用上界已实现 | 商品引用存在性、类别互斥与文创引用上界已实现 | 下界未强制，仍为“部分”，不能写成完整 1:1 |
| 旧样例 | `book` 2 行分别由 `goods.id = 1 / 2` 引用 | `toy` 2 行分别由 `goods.id = 3 / 4` 引用 | 样例呈现一对一，但不能证明所有数据都满足业务基数 |

因此，“商品侧 `(0,1)`、细节侧业务 `(1,1)`”是统一口径；不能把两端都写成 `(0,1)`。商品侧 `(0,1)` 表示某个商品至多属于当前这一个子类型联系，具体类别下由 CHECK 变为必有匹配细节；细节侧 `(1,1)` 表示业务要求，当前实现的细节参与为 `(0,1)`；上界已由索引强制，下界仍需建档流程保证。

### 22.2 I-05、I-06、I-07 的边界统一

| 问题 | 同时涉及 | 统一含义 | 当前落点 |
|---|---|---|---|
| I-05 反向引用下界 | `book`、`toy`、`goods.book_isbn`、`goods.toy_code` | 外码能保证商品引用的细节行存在，不能保证每条细节行至少被一个商品引用；可能存在孤立细节行 | 保留“细节行随商品建档产生”的业务约定，不反转外码方向 |
| I-06 独立留痕缺口 | `book`、`toy`、`goods.created_by / created_at` | 细节表不能独立回答录入人和时刻；正常路径可通过商品建档留痕间接追溯，孤立行则不能 | 留痕集中在 `goods`，不在两张细节表重复添加一套未决定的审计列 |
| I-07 反向引用上界 | `goods.book_isbn`、`goods.toy_code`、`book.isbn`、`toy.inner_code` | 细节主键唯一与商品引用唯一是两层约束，第六周已补齐后者 | 两个筛选唯一索引已创建，先做重复检查，合法 NULL 排除在索引外 |

I-05 是“可以没人引用”的下界，仍保留原边界；I-07 是迁移前“可以被引用多次”的上界，已由索引修复；I-06 是留痕边界，不是范式缺陷。`book` 与 `toy` 必须同步处理，不能只给其中一侧增加索引或留痕。

### 22.3 码、依赖与目标结构的统一结论

三表的候选码和主要函数依赖互不冲突：

```text
goods.id       → goods 的其余属性
book.isbn      → book.author, book.publisher, book.page_count
toy.inner_code → toy.spec
```

`goods.book_isbn` / `goods.toy_code` 是跨表引用，不会把 ISBN 或内部编码变成 `goods` 的候选码；商品仍用代理键 `goods.id` 统一承载价格、库存、上下架和业务明细引用。当前不需要为了满足 1NF / 2NF / 3NF 拆分或合并这三张表，也不需要把出版社或规格机械拆成新的实体。

第六周实际结构为：保留三表、原外码方向及类别互斥 CHECK，新增 `UX_goods_book_isbn`、`UX_goods_toy_code`。它们提供非空引用的条件唯一性，不把可空引用列单独升级为全表候选码，不推导无条件的全表函数依赖。

### 22.4 统一回归清单与当前边界

- 分别准备孤立 `book` / `toy`、同一 ISBN / 内部编码被两个 `goods` 行引用、类别与引用列不匹配等反例，全部在独立事务中验证或回滚；

## 23. I-04：库存计数跨表一致性维护方案比较

### 23.1 当前语义与静态核对

I-04 涉及两条不同的跨表等式，不能只看 `goods` 自身的 `CHECK`：

```text
-- 对每一条商品 g 计算
g.stock_total = COALESCE((
    SELECT SUM(m.quantity)
    FROM stock_movement AS m
    WHERE m.goods_id = g.id
), 0)
g.reserved_qty = COALESCE((
    SELECT SUM(i.quantity)
    FROM reservation_item AS i
    JOIN reservation AS r ON r.id = i.reservation_id
    WHERE i.goods_id = g.id AND r.status = N'有效'
), 0)
g.stock_total - g.reserved_qty = 当前可售量
```

当前样例的业务解释如下：

| 业务事件 | `stock_total` | `reserved_qty` | 其他要求 |
|---|---:|---:|---|
| 采购入库、退货回收 | 增加事件数量 | 不变 | 必须写入来源正确的正数库存流水 |
| 普通销售、报损 | 减少事件数量 | 不变 | 销售 / 报损前不能超过可售量；报损必须填写原因 |
| 新建有效预订 | 不变 | 增加预订明细数量 | 只能占用可售量，不能侵占已订量 |
| 取消或到期 | 不变 | 减少原有效预订数量 | 不产生库存、资金或积分流水；到期不能虚构员工操作人 |
| 整单取货 | 减少销售出库数量 | 减少原有效预订数量 | 状态、销售单、出库流水和两项计数必须在同一事务完成；本项目不支持部分取货 |
| 任一事务失败 | 不变 | 不变 | 不能只留下单据、流水或其中一个计数的变化 |

因此，旧基线中 `goods.id = 1` 的在架量为 `5 - 3 + 3 - 2 + 3 = 6`，有效预订 `reservation.id = 2` 占用 6；`reservation.id = 1` 已取，其 3 件明细只保留历史，不计入 `reserved_qty`。四件旧商品的计数仍应为在架 `6 / 0 / 10 / 19`、已订 `6 / 0 / 0 / 0`。这些是脚本定义的基线预期，实际边界测试结果另在本节末尾记录。

现有实现边界也要单独记录：`schema.sql` 只有 `CK_goods_stock`，只能保证两个计数非负且 `reserved_qty <= stock_total`；没有库存或预订维护触发器。`db/verify.sql` 的 **51210** 用 `OUTER APPLY` 汇总全部库存流水和“有效”预订明细后比较两列，属于读取时主动发现；**51220** 另查销售 / 退货流水数量。`db/crud.sql` 在写入业务流水后显式 `UPDATE goods` 同步 `stock_total`，说明当前依赖事务入口和操作者纪律。任何直接改计数、改流水或改预订状态的行为，都可能在下一次校验前暂时留下不一致。

### 23.2 四种维护方案

| 方案 | 目标结构与写入边界 | 能否拦住绕过业务入口的写入 | 优点 | 代价与风险 |
|---|---|---|---|---|
| **A．统一事务入口** | 保留两个计数和两类明细；采购、销售、退货、报损、预订、取消 / 到期、取货全部通过存储过程或受控应用事务写入，并在同一事务更新对应计数；对 `goods` 行加适当锁以避免并发超卖 | 只有在撤销对表的直接写权限、所有写操作都经过入口时才有强制效果；现有 DDL 本身不能阻止手工 `UPDATE` | 最贴合现有业务语义，能把状态、流水、计数和回滚放在一个边界内；迁移范围较小，容易保留旧查询 | 入口遗漏或拥有高权限的直接 DML 仍可绕过；需要实现幂等、并发锁和到期处理；必须逐项盘点所有写入路径 |
| **B．数据库触发器** | 在 `stock_movement` 的增删改、`reservation_item` 的增删改和 `reservation.status` 的状态变化上按集合计算增量；必要时在 `goods` 上拒绝直接修改两个计数；失败即回滚整条语句 / 事务 | 在触发器未被禁用且权限未绕过时，能把手工写入纳入数据库检查或自动同步 | 直接 DML 也会触发维护；可把“流水 / 状态变化与计数同步”从应用层下沉到数据库 | 多行语句、取消 / 到期 / 取货的状态差额、历史流水不可改和并发锁都很容易写错；触发器耦合高、调试困难，可能带来递归和死锁；仍需单独设计岗位和流程规则 |
| **C．实时派生视图** | 以 `stock_movement` 和有效 `reservation_item` 为唯一来源，视图实时计算在架、已订和可售量；若保留 `goods` 两列，只能作为兼容缓存，不能再宣称问题已根治 | 视图能避免读到过期的派生值，但不能单独阻止并发销售、非法预订或错误流水写入，写入仍需事务入口 / 锁 | 没有冗余计数漂移，查询结果天然按明细重算；数据来源单一，维护逻辑直观 | 现有列、`CHECK`、查询、ER 和数据字典都要调整；每次查询都聚合，索引和性能需要重新评估；旧应用若直接读取 `goods.stock_total` / `reserved_qty` 会失效；普通视图不能代替写入授权控制 |
| **D．保留冗余计数并加强主动校验** | 保持现有结构和手动同步流程，扩大 `verify.sql` / 定时对账 / 运行前检查，必要时限制普通用户直接写表；偏差由校验发现后修复 | 不能在偏差发生的瞬间拒绝；只能在主动校验或报表读取时发现，仍属当前 v0.1 边界 | 改动最小，旧脚本和查询兼容，性能和实施风险可控；适合作为迁移期间的过渡方案 | 不满足“写入时必然一致”的硬保证；偏差可能在检查前影响可售量和业务决策；修复需要额外的冲正或人工确认，容易形成新的审计问题 |

“触发器”或“视图”不能只写成一个关键词：A / B 需要明确谁能写 `goods`、谁能改变预订状态，C 需要明确是否删除两列，D 需要明确检查频率和发现偏差后的修复流程。若只保留两列同时继续允许直接 DML，四种方案都不能声称已经解决 I-04。

### 23.3 方案选择前的验证门槛

在 `ShiguangBookstoreWeek3` 的只读基线核对和独立副本测试完成前，不选择最终方案，也不修改 `schema.sql`。本步已准备 [`db/i04-readonly-check.sql`](../db/i04-readonly-check.sql)，后续至少要分别验证：

1. 对每个 `goods` 汇总库存流水，单独汇总有效预订明细，并输出 `stock_total`、`reserved_qty`、两项重算值和可售量；不能只输出“通过 / 失败”，还要保留可定位到商品的差异行。
2. 在可回滚事务中覆盖采购入库、销售出库、退货回收、报损、有效预订、取消、到期和整单取货；每一步同时记录单据状态、流水数量、两项计数、资金 / 积分是否应变化。
3. 分别尝试直接修改 `goods.stock_total` / `reserved_qty`、修改库存流水数量、修改有效预订明细和把预订状态改为终态。A / B / C / D 的预期不同，实际结果必须标为“自动同步”“拒绝”“可写但被校验发现”或“待实现”，不能混写成同一种通过。
4. 验证失败回滚和重复请求：中途失败不得只留下销售单、预订状态、库存流水或某一个计数；同一次取消、到期或取货请求不得重复释放 / 扣减。
5. 若选 A 或 B，再增加并发下同一商品的销售 / 预订竞争测试；若选 C，先盘点所有读取两个计数的脚本和查询；若选 D，明确对账周期、修复入口和修复期间如何阻止继续销售。

本步的暂定判断是：只读核对没有发现当前截面的逐商品差异；预订侧和库存流水侧的直接写入均可在回滚事务中执行，且不会自动同步另一侧，这确认了当前“可由查询发现、写入时未强制”的边界，但不足以决定 A、B、C 或 D。I-04 仍标记为“方案已比较、实现待定”；I-10 等其他余额类跨表问题暂不在本步展开。

用户于 2026-10-17 在 `ShiguangBookstoreWeek3` 执行 [`db/i04-readonly-check.sql`](../db/i04-readonly-check.sql) 后反馈汇总列 `inconsistent_goods_count = 0`。这证明本次查询截面中没有发现逐商品库存或有效预订汇总差异；由于尚未归档结果网格中的完整商品行和截图，也不把该反馈扩写成新的行数或历史截面证据，更不能据此认定写入时已经有 DDL / 触发器强制。
