>
> 1\. 本周目标
> --------
>
> 把业务对象转成关系模式，定义属性、域、主码、候选码和外码。把上周确定的业务对象正式转成关系模式，字段定义（属性＋域）、标注主码/候选码/外码，并写真实样例元组。
> ---------------------------------------------------------------------------------
>
> 2\. 任务
> ------
>

> 3\. 本周作业
> --------
>
> *   表清单：实体及对应表，说明表中字段属性，域和码
> *   样例元组。
>

> -----------
>
> *   主码是"选出来"做标识的；候选码是其他也能唯一标识的，外码引用的是另一张表的主码，将两个 表联系起来。设计表时一定要注意表与表之间的关系。
> *   表的属性要完整，方便接下来的实验。
> *   设计时统一风格，避免多人协助时产生歧义。
> *   AI 可以用来协助提候选表和字段，但必须自己核对业务语义并能解释。

## 2. 任务拆解

官方把本周任务拆成四个子任务，每一个的实质要求是：

| # | 官方要求 | 拆解：它到底要什么 |
|---|---|---|
| 1 | 确定实体与表（表名 · 属性 · 含义） | 把"**记哪些信息**"落成"**用哪张表记**" —— 这是关系模式的第一层 |
| 2 | 定义字段（属性＋域） | 每个字段既能被存下、也能被**约束住**：七项写全，**域要能判合法** |
| 3 | 标出主码 / 候选码 / 外码 | 把表与表之间的**联系固定下来**；**外码引用的是另一张表的主码** |
| 4 | 写样例元组 | 用**真实数据检验设计** —— 数据跑不通，说明表还没设计对 |

**不可违反的硬性约束**：

1. 每个字段都要写全**七项**：字段名 · 类型 · 长度/精度 · 是否可空 · 默认值 · **域** · **含义**。
2. 每张表必须有 **PK**；**FK 必须指向另一张表的主码**。
3. 样例元组必须是**真实业务数据**，**每表 2—3 行**。
4. 表的属性要**完整**（官方原话：方便接下来的实验）—— 宁可想清楚，不要留缺口。
5. **统一风格**（官方原话：避免多人协作时产生歧义）。
6. AI 可以协助提**候选表 / 字段**，但**必须自己核对业务语义并能解释**。
7. **（上游）实体只能来自上周的边界** —— `docs/spec-data-boundary.md` 的进库清单 + 三种单据；
   边界清单里没有的实体**不进库**。
8. **（上游）本周交付的是"设计"，不是"建库"** —— 表清单 · 字段定义 · 码 · 样例元组。
   建库与 SQL 是第 3 周的事（第三周任务原文：「根据第二周的数据字典……创建表」）。

## 3. 任务说明

本周要做的事一句话概括：**把上周定下的"信息"，正式翻译成关系模式。**

下面按 §2 拆出的四个子任务，逐条说明**目的**与**要求**。

### 3.1 确定实体与表

- **目的**：把"记哪些信息"落成"用哪张表记" —— 后面所有字段、码、约束都长在这张表上。
- **要求**：
  - 实体来源**只能是** `docs/spec-data-boundary.md` 的进库清单（20 条）与三种单据，**不许凭空加实体**；
  - 每张表写清三样：**中文名 · 英文表名 · 一句话说明**（这张表装什么）；
  - **一实体一表** —— 不要把两类东西塞进同一张表（如"商品"与"库存变动"）；
  - 三种单据按**头 + 行**两级（`docs/spec-businesses.md` §1.6 已定）；
  - 表名与字段名的**风格统一**（大小写 / 单复数 / 下划线，自选一种并贯彻到底）。

### 3.2 定义字段（属性 + 域）

- **目的**：让信息既能被存下，也能被**约束住** —— 域是"这张表不接受什么"的第一道防线。
- **要求**：
  - 每个字段 **七项齐全**，其中最容易偷懒的两项是 **域** 与 **含义**；
  - **域必须可判定**：枚举要**列全**（例：卡档位只有"银卡 / 金卡"），区间要**给端点**；
  - 每个字段都要能说清它服务**哪条业务 / 哪条规定**（`R-*`）——**想不出用处的字段不要加**；
  - 数值类要想清精度：金额 · 积分 · 数量分别用什么精度、能不能为负。

### 3.3 标出码（PK / 候选码 / FK）

- **目的**：把表与表之间的**联系**固定下来 —— 这也是第 4 周做主外键与检查约束的基础。
- **要求**：
  - 每张表标出 **PK**；**候选码**要写出来，并说明**为什么不选它当 PK**；
  - **FK 一律指向另一张表的主码**（官方原话），写明"**指向哪张表哪个字段**"；
  - 每条约 FK 要能**一句话说明它在业务上意味着什么**（说不清的，多半是关系没想清楚）；
  - 引用方向要想清：如"库存变动"引用"商品"，同时引用**引起它的那张单据**。

### 3.4 写样例元组

- **目的**：用**真实数据**检验设计 —— 表设计得对不对，插几行数据就露馅了。
- **要求**：
  - 每表 **2—3 行真实业务数据**，读得出是什么生意（不接受 `test1` / `aaa` / `1,2,3`）；
  - **样例之间要对得上**：单据的行属于同一张单 · 资金流水的"事由"指向真实单据 ·
    积分余额与积分流水相符 · 已订量挂得上预订单；
  - **覆盖上周定下的关键口径**，否则设计里的坑看不出来：
    一单多行 · 部分退货 · 「订走未取」（可售量为 0）· 积分余额可为负 · 同一商品多批次不同进价。

## 4. 验收标准

**判定方式**：下表每一条都是**硬性门槛**，逐条判「过 / 不过」，**不存在「基本满足」**；
只要有一条不过，本周产出即视为不合格，不得进入下一周。
评审必须由**非本条作者的组员**执行 —— 自己评自己不算。

| # | 验收项（对应子任务） | 通过标准 | 判不过的典型情形 |
|---|---|---|---|
| 1 | 实体齐备（3.1） | 边界清单里**每条进库信息**都能落到某张表；三种单据（采购申请单 / 销售单 / 预订单）都在 | 有信息无处安放；或冒出边界清单里没有的实体 |
| 2 | 风格统一（3.1） | 表名 / 字段名的命名风格一致，一看就知道是哪类东西 | 同一概念两种写法（`member` / `Member` 混用） |
| 3 | 字段七项齐全（3.2） | 每个字段七项都填了，**含义**不为空 | "类型"只写 `varchar` 不给长度；含义写"同上" |
| 4 | 域可判定（3.2） | 每个域都能说出"什么值算合法"：枚举列全、区间有端点 | 域写成"字符串""数字"，等于没写 |
| 5 | 字段可追溯（3.2） | 每个字段能说清服务哪条业务 / 规定；**没有"以后可能要用"的字段** | 说不出用处的字段；为将来预留的空字段 |
| 6 | 码完整（3.3） | 每表有 PK；候选码写出并说明为何不当 PK；**FK 都指向另一张表的主码** | 只写 PK 不写候选码；FK 指向非主码字段 |
| 7 | 关系说得清（3.3） | 每条约 FK 都能一句话说明业务含义，且与 15 条业务对得上 | 有关系但解释不了；出现说不清的引用 |
| 8 | 样例真实（3.4） | 每表 2—3 行真实业务数据 | `test1` / `aaa` / `1,2,3` |
| 9 | 样例自洽（3.4） | 样例之间**对得上**（单与行 · 流水与事由 · 积分余额与流水） | 行的单号指向不存在的单；余额与流水不符 |
| 10 | 口径覆盖（3.4） | 样例覆盖上周的关键口径（一单多行 · 部分退货 · 订走未取 · 积分可为负 · 多批次进价） | 所有样例都只有一行一商品 |
| 11 | 语义核对（AI 使用） | 对 AI 提的候选表 / 字段**逐条核对过业务语义**，每条都解释得来历 | 直接照抄 AI 的表；解释不了某字段为什么在 |
