## 1. 任务原文

> **数据库系统实验课程** —— **第二阶段（第 5—9 周）**：数据设计、重构与应用开发。
>
> 阶段目标：回头审查第一阶段的表是否合理 —— 用 ER 模型和规范化解释设计，用迁移脚本修正问题，并把数据库封装成可操作的应用界面。
>
> **第六周任务：ch7 函数依赖与规范化**
>
> **1. 本周目标**
>
> 识别更新异常与函数依赖，完成规范化、反规范化取舍和迁移设计。在 v0.1 的副本上运行 `migration.sql`，验证迁移前后业务含义一致，为第 7—9 周的应用开发准备数据库结构。
>
> **2. 任务**
>
> 1. **确认分析对象与基线**：根据第五周 ER 图，列出实体对应的表、表中字段、主码、候选码和外码，检查 ER 图与现有表结构是否一致。保存 v0.1 数据副本，以及订单明细、商品销售统计、库存查询的迁移前结果，作为后续对比基准。
> 2. **分析函数依赖与更新异常**：说明字段之间的决定关系，对每个核心表列出主要的函数依赖关系，说明决定因素。例如商品编号决定当前商品名称，但通常不能决定历史订单中的成交价。检查表结构是否出现更新异常，分别讨论插入、修改、删除异常，并给出数据例子；如果没有则说明设计如何避免的。
> 3. **判断范式并设计分解**：检查是否一个字段保存多个值（1NF），非主属性是否部分依赖某个候选码（2NF）、是否存在不符合 3NF 的传递依赖。逐表给出判断依据；对问题关系提出拆分、合并或保留方案，列出新关系的属性和码。
> 4. **解释分解与冗余取舍**：说明分解后如何还原业务信息，是否保持关键依赖。若商品表重复存储类别名称，可依据商品编号决定类别编号、类别编号决定类别名称进行分析。
> 5. **实施数据迁移**：编写 `migration.sql`，应包含：新表创建；字段调整；主码、候选码和外码设置；必要的数据迁移；重复数据检查；旧表处理或保留说明。
> 6. **完成迁移测试并同步文档**：编写 `regression.sql`，测试关键标识、关系映射、订单金额、商品销量、库存和角色权限是否正确。解释拆表导致的合理行数变化；分别验证合法写入、非法外码或数量被拒绝、越权操作失败。保存预期值和实际值，更新 ER 图、数据字典及 README。
>
> **3. 本周作业**
>
> - **依赖与范式分析**：逐表记录候选码、关键函数依赖、插入 / 修改 / 删除异常、范式判断及依据；已经满足要求的表说明保留理由。
> - **重构方案**：提交目标关系模式、更新后的 ER 图和数据字典，说明拆分 / 合并 / 保留的理由、无损连接与依赖保持分析，以及冗余维护方式。
> - **migration.sql**：提供从 v0.1 到目标结构的迁移脚本，保留基线数据，写明执行顺序、数据冲突处理、运行前提和失败恢复方法。
> - **regression.sql 与结果**：包含订单明细、销售统计、库存查询、完整性与权限验证；逐项记录迁移前基准、预期、迁移后结果及差异解释，不能只提交成功截图。
> - **README、报告素材与 ai_log**：报告素材先包含设计思路、实验过程和实验总结，再重点说明函数依赖、分解依据、迁移步骤和回归结论；记录 AI 辅助过程与人工验证。上述材料并入第二阶段 v1.0 作业。
>
> **4. 提示与常见问题**
>
> - 函数依赖来自业务规则。样例中没有重复值不能证明依赖成立；增加一个自增主键，也不意味着其他属性之间的依赖和冗余已经消失。
> - 规范化并非表越多越好。检查 2NF 要考虑所有候选码；判断 3NF 不能只看主键，应分析非平凡函数依赖的决定因素和被决定属性。
> - 如果现有结构合理，可保留并给出分析证据。用独立演示关系说明异常与分解，不要为展示规范化而破坏原项目；迁移脚本仍应明确检查基线和记录无需变更的结论。
> - 无损连接和依赖保持要结合函数依赖说明，不能只凭有限样例验证。样例回归用于发现迁移错误，不代替设计层面的论证。
> - 先备份或复制数据库，再迁移。删库重建会丢失已有数据，不能代替迁移；脚本不要求可重复执行，但要写清再次运行所需的初始状态。

### 2.4 依赖分析、重构与既有问题

每张表必须记录：

1. 关系模式、一行代表什么、主码及全部候选码。
2. 关键函数依赖 `X → Y`、决定因素、业务依据及适用时点。
3. 插入、修改、删除异常的例子；无异常时说明如何避免。
4. 1NF、2NF、3NF 判断及依据。
5. 保留 / 拆分 / 合并方案；新关系的属性、码、引用和旧新标识映射。
6. 无损连接、依赖保持的论证，以及冗余维护方式。
7. 对应问题编号、迁移步骤和回归证据。

检查 2NF 时考虑全部候选码；判断 3NF 时，对每个非平凡依赖核对决定因素是否为超码，或被决定属性是否为主属性。代理键和样例无重复值都不能代替依赖分析。

### 2.5 迁移、旧场景保留与执行边界

- **备份并在副本操作**：保留原 v0.1 复现入口；不得用删库重建代替从已有数据迁移。

新增资金流水按时序接续已有余额；正积分必须有获得来源，库存必须有入库来源。未来时点或会改变参数的操作在独立测试副本或事务中执行，不污染扩充基线。

### 2.7 回归测试与实现范围

回归至少包含订单明细、销售统计、库存查询、标识映射、金额、权限及以下检查：

| 检查类别 | 必测内容 |
|---|---|
| 合法操作与完整性 | 合法写入成功；重复主码 / 单号 / “父单 + 商品”、不存在的外码、非法数量被拒绝 |
| 库存与来源 | 超可售量、侵占已订量、报损无原因；在架等于流水累加，已订等于有效预订明细汇总 |
| 采购与预订状态 | 未审批付款 / 收货、审批后取消、状态回退、收货数量不符；部分取货、终态再次操作 |
| 积分与退货 | 超余额或抵扣上限、跨原单 / 超数量退货；余额等于积分流水，退款分摊及多次退货累计正确 |
| 资金 | 流水前后余额连续，采购付款 / 销售收款 / 退款有正确来源，现金与经营盈亏分别计算 |
| 权限 | 授权角色合法操作成功；收银员改卡参数、库管收款 / 退款、无权角色查询资金失败 |
| 重复请求与事务 | 同次收货 / 取货 / 退款 / 取消不重复记账；中途失败整笔回滚，无残留单据或部分流水 |
| 迁移与扩充数量 | 区分原记录、迁移生成、新增样例和临时测试；拆表后的合理行数变化有解释 |

每项记录初始状态、步骤、预期、实际、差异及失败后的状态。使用独立事务或可重置副本，不能只提交成功截图。

实施时明确本周已实现的流程范围。自动过期、重复请求等尚未实现时，必须保留用例和待实现记录；静态样例存在只能证明数据覆盖，不能判定该操作通过。延期不能替代课程要求的合法写入、非法外码 / 数量拒绝、权限验证及迁移回归。
