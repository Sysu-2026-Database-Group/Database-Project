## 2. 经营规则（业务约束）

### 2.1 商品

- 图书以 ISBN 作为业务唯一标识；同一 ISBN 在不同批次可能有不同进价。
- 文创商品没有 ISBN，使用内部编码 `goods_code`。
- 图书与文创共享「商品」这一概念：都能采购、销售、退货、拥有库存。
- 不做二手书；不做商品规格变体（例如不同颜色、不同尺寸）。

#### 2.1.1 商品状态机

**先明确主语**：这里的「商品」指的是**商品种类（SKU）**，不是单册 ——
一个种类在 `Product` 里是一行，单册没有独立记录（R7）。

**可销售条件（唯一的判定依据）**

```text
可销售条件 ⟺ (在库量 − 预定量 − 损坏量) > 0
            ⟺  physical_qty − reserved_qty − damaged_qty > 0
            ⟺  stock_qty > 0
```

> **三种写法为什么是同一件事**：`physical_qty = stock_qty + reserved_qty + damaged_qty`，
> 而 `reserved_qty` 与 `damaged_qty` 在「在库量」里加了一次、又在「占用量」里减了一次，
> 自动抵消。**占用池无论有几个，结论都塌缩成 `stock_qty > 0`。**
> 因此将来新增任何占用口径（在途锁定、质检保留……）都**不需要改动状态机**。
>
> `damaged_qty` 是**预留的占位项** —— 本项目**不落这个池**（见 R8）：
> 报损走 `DAMAGE_OUT` 流水即时扣减 `stock_qty`，所以它的当前取值恒为 0。
> 公式里保留它，是为了让「占用」这个概念在文档层面完整。

**状态集合**：共 **4 个状态**，分**自动区**与**人工区**两层，**没有草稿态**。

| 层 | 状态 | 含义 | 由谁决定 |
|---|---|---|---|
| 自动区 | `ON_SALE` | 在售（可售余量 > 0） | 触发器，按 `stock_qty` 自动 |
| 自动区 | `OUT_OF_STOCK` | 缺货（可售余量 = 0） | 触发器，按 `stock_qty` 自动 |
| 人工区 | `OFF_SHELF` | 已下架（暂不卖，保留商品） | 管理员 / 库管 |
| 人工区 | `DISCONTINUED` | 停售（终态，不可逆） | 管理员 |

**判定函数（一元）**

```text
stock_qty > 0 → ON_SALE
stock_qty = 0 → OUT_OF_STOCK
若当前状态 ∈ (OFF_SHELF, DISCONTINUED)，触发器不动它
```

建议抽成标量函数 `fn_ProductStatus(@stock_qty)`，挂在库存流水触发器上。

**「缺货」的四种成因被统一归入 `OUT_OF_STOCK`**

| 情形 | `stock_qty` | `reserved_qty` | 状态 | 语义 |
|---|---|---|---|---|
| 全部卖光 | 0 | 0 | `OUT_OF_STOCK` | 货架真空 |
| **全部被订走（架上还有货）** | 0 | > 0 | `OUT_OF_STOCK` | 货有主，无货可卖 |
| 从未进过货 | 0 | 0 | `OUT_OF_STOCK` | 立档即缺货 |
| 有货可卖 | > 0 | 任意 | `ON_SALE` | 正常 |

> **为什么「全被订走」不单列一个状态**：
> 它与「全部卖光」允许和禁止的**动作完全一致** ——
> 都不能卖、都不能再预订、都不能报损（见下方关键约定）。
> 一个不禁止任何新动作的状态值，只是另一个状态值的别名，却要付出
> 「二元判定 + 触发器多一个关注点 + 多一条不变式」的代价。
>
> 这层区分改由**查询视图的计数**表达：商品列表页并列展示
> `stock_qty`（可售量）/ `reserved_qty`（预定量）/ `physical_qty`（在库量）/ `status`（状态）**四项**，
> 人一眼看得出「两个 0」与「0 和 20」的差别。**系统只呈现事实，不替人做判断** ——
> 要不要补货属于库管的意愿（见 §7 / R10）。

**迁移关系**

| 起始状态 | 触发事件 | 目标状态 | 触发方 |
|---|---|---|---|
| （新建） | 建档事务提交 | `OUT_OF_STOCK` | 库管，初始态（按函数判定，见下） |
| `ON_SALE` | `stock_qty` 归零（卖出 / 预占 / 报损） | `OUT_OF_STOCK` | 触发器，**自动** |
| `OUT_OF_STOCK` | `stock_qty` 回补至大于 0（采购入库 / 释放预占 / 退货 / 盘盈） | `ON_SALE` | 触发器，**自动** |
| `ON_SALE` / `OUT_OF_STOCK` | 人工下架 | `OFF_SHELF` | 管理员 / 库管 |
| `OFF_SHELF` | 人工重新上架，立即重跑 `fn_ProductStatus` | `ON_SALE` 或 `OUT_OF_STOCK` | 管理员 / 库管 |
| 除 `DISCONTINUED` 外任一态 | 人工停售（绝版） | `DISCONTINUED` | 管理员 |
| `DISCONTINUED` | 无 | —— | 终态，**不可逆** |

> **建档为什么落在 `OUT_OF_STOCK`**：商品状态是 `stock_qty` 的投影，
> 而建档时 `stock_qty = 0`，按函数判定只能是 `OUT_OF_STOCK`。
> 若把建档初始值写成 `ON_SALE`，每一行新商品都会立即与
> 「自动区状态必须等于按可售余量判定的结果」这条自洽性冲突。
> 商品**进第一批货后自动转 `ON_SALE`**，所以「建档 → 采购入库 → 上架」
> 这条链路全程无需人工干预，也不需要「确认上架」这一步。
>
> 若某商品建档后**本就不打算卖**（样书、内部资料），由人工置为 `OFF_SHELF` 表达。

**触发器职责划分（v7 定案）**

`stock_qty`、`reserved_qty`、`status` 三个派生字段由**两个触发器**分管，
划分清楚是为了避免同一字段被两处扣减（线上预订流程尤其容易踩这个坑 ——
那条 `RESERVE` 流水与业务代码很容易把 `stock_qty` 扣两遍）：

| 触发器 | 挂载对象 | 负责字段 | 做什么 |
|---|---|---|---|
| 库存流水触发器 | `InventoryMovement` 的 `INSERT` | `stock_qty`、`status` | `stock_qty += qty_delta`，**对所有 `movement_type` 一视同仁**；随后重跑 `fn_ProductStatus(stock_qty)` 维护 `status` |
| 预订单触发器 | `Reservation` 状态变更 + `ReservationItem` 增删 | `reserved_qty` | 进入 `RESERVED` 时 `+qty`，离开 `RESERVED` 时 `−qty`。**不碰 `stock_qty`，不碰 `status`** |

> 这样划分之后，「`stock_qty = SUM(InventoryMovement.qty_delta)`」这条对账关系
> 与单据的字段变化**天然自洽**：
> `stock_qty` 只有一个写入口（流水），`reserved_qty` 只有一个写入口（预订）。
> 预订流程中 `stock_qty` 的下降**来自那条 `RESERVE` 流水**，
> 业务代码**不得**再手工 `UPDATE stock_qty`。

**关键约定**

- **自动区两态由 `stock_qty` 一个量唯一决定**；人工区两态由人决定，
  触发器**不碰**，也**不允许人工直接设置**自动区两态 —— 它们只是库存的一个投影。
- **`reserved_qty` 不参与状态判定。** 它只是「已有主的货」这个计数，
  供查询与展示使用。商品的「能不能卖」只由可售余量决定。
- 商品被预订时：`stock_qty −qty`、`reserved_qty +qty`，随后重跑一次
  `fn_ProductStatus`。只要还有可售余量，商品**保持 `ON_SALE`**。
- **「全部在库商品均被预定」= `stock_qty = 0` 且 `reserved_qty > 0` = `OUT_OF_STOCK`。**
  它不需要单列状态，三条禁令由 `stock_qty = 0` 自动落实：
  - 不能销售 —— 收银台取不到可售量
  - 不能预订 —— 下单校验直接失败
  - 不能报损 —— 报损的 `qty <= stock_qty` 校验直接失败

  这些禁令是**推论**，不是额外规则。
- **状态说「缺货」与账面说「有货」并不矛盾** —— 它们回答的是两个不同的问题。
  这类商品仍在货架上，计 `physical_qty`，也是盘点的账面基准（见 §2.4）。
- **「20 册里被订走 1 册」绝不改变商品状态**：`stock_qty = 19 > 0`，
  商品保持 `ON_SALE`，其余 19 册正常销售。这是计数级粒度的核心保证。
- 销售单与预订单**只能**包含 `ON_SALE` 的商品。

### 2.2 采购

- 一张采购单只对应一个供应商，可包含多个商品。
- 采购单状态机：`DRAFT → SUBMITTED → RECEIVED`，另有 `CANCELLED`。
  （注意：这里的 `DRAFT` 是**采购单**的草稿态，与商品状态无关。）
- **只有进入 `RECEIVED` 时才产生入库流水**，并记录实际收货数量。
- 采用**货到付款**：收货确认的同一事务内，写入一笔采购支出。
- 进价按批次记录。

> ⚠️ **采购审批环节：本阶段 block，留待后续讨论**（登记在 §6.1 待商议项）。
> 目前**不设**审批状态、不设审批人字段；`SUBMITTED` 之后即可直接收货。
> 「店长审批采购单」这一权限也一并收回，等该环节解冻后再议。
> 相应地，采购单状态机里**没有** `APPROVED`、**没有** `CLOSED`。

### 2.3 销售

- 渠道两种：`STORE`（门店直接销售）、`ONLINE`（线上预订后到店自提）。
- **销售订单只在「钱货两清」时生成**：门店单在结算时生成，线上单在自提核销时生成。
  线上预订阶段**没有**销售订单，只有预订单（见 §2.6）。
- 销售订单状态机：

| 起始状态 | 触发事件 | 目标状态 | 触发方 |
|---|---|---|---|
| （新建） | 门店结算 / 线上自提核销，收款成功 | `PAID` | 收银员 |
| `PAID` | 部分订单行退货 | `PARTIAL_REFUND` | 收银员 |
| `PAID` / `PARTIAL_REFUND` | 全部订单行退货完毕 | `REFUNDED` | 收银员（可自动判定） |

- **订单行必须快照**成交时的 `unit_price`、`discount_rate`、`line_amount`；
  订单头快照 `member_level_id`、`discount_rate`。

**计价规则（已拍板：先扣积分，再打折）**

设某一订单：

| 符号 | 含义 |
|---|---|
| `M` | 订单行小计 = `unit_price × qty` |
| `S` | 订单小计 `subtotal` = Σ`M` |
| `D` | 积分抵扣金额 = 使用积分 ÷ 100 |
| `r` | 会员折扣率（普通 1.00 / 银卡 0.95 / 金卡 0.90） |
| `T` | 实付金额 `total_amount` |

计算顺序固定为：

```text
1. S = Σ(unit_price × qty)
2. D = min(使用积分 ÷ 100, S × 20%)      -- 抵扣上限为小计的 20%
3. 折后基数 B = S − D
4. 实付 T = ROUND(B × r, 2)
5. 获得积分 = FLOOR(T × points_rate)
```

> **注意一个数学后果**：积分在打折之前被减掉，因此积分也一并被折扣缩水。
> 例如售价 89 元、用 500 积分、银卡 9.5 折：
> `(89 − 5) × 0.95 = 79.80`，积分实际价值只有 `5 × 0.95 = 4.75` 元。
> 会员折扣越高，积分越不值钱。这是本方案的既定语义，文档与代码需保持一致。

### 2.4 库存

- 所有库存变化只能通过「库存流水」发生，**禁止直接修改库存数量**。
- 流水原因取值：

| 代号 | 含义 | 方向 |
|---|---|---|
| `PURCHASE_IN` | 采购入库 | + |
| `SALE_OUT` | 销售出库 | − |
| `RESERVE` | 预订预占 | − |
| `RELEASE` | 释放预占 | + |
| `RETURN_IN` | 退货入库 | + |
| `DAMAGE_OUT` | 报损出库 | − |
| `INVENTORY_GAIN` | 盘盈调整 | + |
| `INVENTORY_LOSS` | 盘亏调整 | − |

- 账面库存 = 全部流水之和；同时维护汇总字段 `stock_qty`（由触发器同步）。
- 任何时刻两者必须相等，可用一条对账视图随时验证。
- **`stock_qty` 的语义不是「进了多少货还没卖」，而是「扣掉一切占用之后还能卖的余量」** ——
  它由 §2.1.1 的可销售条件定义：`stock_qty = 在库量 − 预定量 − 损坏量`。

> **关于预占的简化约定**
> 本系统把「预占」直接视为库存扣减（`RESERVE` 记负值）。
> 预订超时或取消则写一条 `RELEASE` 回补。
> **写入侧只有一套真源**（库存流水），不存在「实物账 / 可售账」双写的问题。
>
> 读取侧区分三个口径，它们描述的是**两组互不重叠的货**：
>
> | 口径 | 含义 | 来源 |
> |---|---|---|
> | `stock_qty` | **可售量**：还没有主的货 | `Product` 字段，库存流水触发器维护 |
> | `reserved_qty` | **已订量**：已被订走、待自提的货 | `Product` 字段，预订单触发器维护 |
> | `physical_qty` | 架上真实总量 | `stock_qty + reserved_qty` |
>
> **线上预订的库存变化发生在「下单预占」时刻，而不是「到店自提」时刻**；
> 自提阶段只做收入确认、积分结算与状态流转，**不再写任何库存流水**。
>
> 顾客下单后，这本书在语义上相当于「**已售出、待取货**」——
> 其他顾客既不能再买走也不能再预订。但它**仍在货架上**，因此**计入在库**：
> 盘点的账面基准取 `physical_qty`，而不是 `stock_qty`。
> 当**可售量归零**（`stock_qty = 0`）时，商品状态转为 `OUT_OF_STOCK`
> （判定规则见 §2.1.1）—— 注意此时**架上是满的**，状态与账面并不矛盾。
>
> **关于报损**：`DAMAGE_OUT` 流水**即时扣减 `stock_qty`**，不设独立的「待损池」。
> 因此可销售条件里的 `damaged_qty` 恒为 0（见 R8）。若将来需要「破损待处理区」，
> 只需新增一个占用池，**状态机无需改动** —— 这正是 §2.1.1 那条塌缩性质的价值。

### 2.5 会员

等级与权益如下：

| 等级 | 升级门槛（累计消费） | 折扣 | 积分倍率（乘数） |
|---|---|---|---|
| 普通 | 注册即得 | 无 | 1× |
| 银卡 | ≥ 1000 元 | 9.5 折 | 1.5× |
| 金卡 | ≥ 5000 元 | 9 折 | 2× |

- **积分获取**：`获得积分 = FLOOR(实付金额 × 倍率)` —— **最后一步才取整**。
  例：实付 79.80、银卡倍率 1.5 → `FLOOR(119.70) = 119`。
  ⚠️ 不是「先把消费额取整、再乘倍率」（那会得到 118）—— 口径以 §2.3 的公式为准。
- 积分使用：**100 积分抵 1 元，单笔最多抵订单小计的 20%**。
- 计价顺序见 §2.3：先扣积分，再打折。
- **等级只升不降**（已拍板）：一旦达到某等级，永久保留。
  退货导致 `total_spent` 下降时，等级**不下调**。
- 退货时同步回滚积分与累计消费额。
- 不做储值，不做余额账户。

> **设计说明**：取消降级后，`Member.total_spent` 与 `Member.level_id`
> 之间不再是严格函数关系 —— 可能出现「累计消费 900 元但仍是银卡」的情况。
> 这是**保级**语义，属正常现象，对账时不可误判为数据错误。

### 2.6 线上预订

这是本项目的**第三套状态机** —— 前两套是商品状态机（§2.1.1）与销售订单状态机（§2.3），
三套之间**完全解耦**。

#### 2.6.1 为什么还要单独建实体

「已预定」在 v6 里**只是一条计数**（`Product.reserved_qty`），不占商品状态位（见 §2.1.1）。
但**预订这件事本身仍然需要单据记录**，理由有三条：

1. **`reserved_qty` 算不出来。** 这个计数必须由「哪些预订还活着」聚合得到。
   没有预订单，它就没有来源 —— 商品列表页也就展示不出「预定量」这一列。
2. **有效期是单据的属性。** 保留 48 小时、取货码、到期时刻，这些都属于一笔具体的预订，
   不属于商品，也不属于销售订单。
3. **销售订单不能承担未成交的预订。** 预订有三种归宿（成功自提 / 超时过期 / 主动取消），
   其中两种全程**没有钱**发生。若把预订塞进销售订单，会长期躺着大量
   「永远不会付款」的僵尸行，污染所有销售统计（营收、销量、客单价）。

因此分工是明确的，而且**分属两个不同层级的问题**：

| 层级 | 表达什么 | 载体 | 取值 |
|---|---|---|---|
| 商品层 | 能不能卖 | `Product.status` | 自动区 `ON_SALE` / `OUT_OF_STOCK` |
| 商品层 | 被占了多少 | `Product.reserved_qty` | 计数，**不参与状态判定** |
| 单据层 | 这一笔预订还作不作数 | `Reservation.status` | `RESERVED` / `PICKED_UP` / `EXPIRED` / `CANCELLED` |

> ⚠️ **命名提醒（v6 已消除歧义）**：`Product.status` 与 `Reservation.status`
> 在 v4 时都含 `RESERVED`，极易混淆。
> **v6 起 `Product.status` 不再有 `RESERVED`**，该词只出现在 `Reservation.status` 里。

预订单先诞生，**自提成功才生成销售订单**。

#### 2.6.2 实体与字段（概念层，完整字段见 04 数据字典）

`Reservation`（预订单，头）：

| 字段 | 说明 |
|---|---|
| `reservation_id` | 主键 |
| `reservation_no` | 业务单号，唯一 |
| `member_id` | 下单会员（**必须登录会员**） |
| `reserved_at` | 下单时刻 |
| `expire_at` | 保留截止时刻 = `reserved_at + 48 小时` |
| `pickup_code` | 取货码，`RESERVED` 期内唯一 |
| `status` | 见下方状态机 |
| `order_id` | 自提成功后指向生成的销售订单，其余状态为 `NULL` |
| `staff_id` / `picked_up_at` | 核销人与核销时刻，仅 `PICKED_UP` 时有值 |

`ReservationItem`（预订单，行）：`reservation_item_id` + `reservation_id` +
`product_id` + `qty`。**只有这几件事，没有任何金额字段。**

> **预订单为什么不持有任何金额与折扣（v7 定案）**：
> 线上预订**不冻结**价格、折扣与积分 —— 一律**以线下自提当时为准**。
> 因此 `Reservation` 上没有 `member_level_id` / `discount_rate` / `subtotal` /
> `total_amount`，`ReservationItem` 上也没有 `unit_price` / `line_amount`。
> 预订单的职责被收窄成一句话：**锁住 qty 个商品，别让别人买走。**
> 金额、折扣、积分的快照**只在销售订单上发生**（成交即快照，见 §2.3）。

#### 2.6.3 预订单状态机

**状态集合**：4 个状态，其中 `RESERVED` 为唯一活动态，其余三个均为终态。

| 状态 | 含义 | 货是否已锁走 | 是否为终态 |
|---|---|---|---|
| `RESERVED` | 预订有效，等待到店自提 | 是 | 否 |
| `PICKED_UP` | 已自提，钱货两清 | 是（已离店） | 是 |
| `EXPIRED` | 超过保留期未取 | 已归还 | 是 |
| `CANCELLED` | 顾客主动取消 | 已归还 | 是 |

**迁移关系**：

| 起始状态 | 触发事件 | 目标状态 | 触发方 |
|---|---|---|---|
| （新建） | 会员下单，且库存预占成功 | `RESERVED` | 会员 |
| `RESERVED` | 到店报取货码，收款完成 | `PICKED_UP` | 收银员 |
| `RESERVED` | 超过保留期（48 小时）未取 | `EXPIRED` | 定时作业，**自动** |
| `RESERVED` | 顾客主动取消 | `CANCELLED` | 会员 / 收银员 |
| `PICKED_UP` / `EXPIRED` / `CANCELLED` | 无 | —— | 终态，**不可逆** |

**每次迁移的副作用**（这是与库存、资金、订单、商品状态四处耦合的点）：

| 迁移 | 库存流水 | 可售量 / 已订量 | 商品状态 | 资金流水 | 销售订单 | 积分 |
|---|---|---|---|---|---|---|
| → `RESERVED` | `RESERVE`（−qty） | `stock_qty −qty`（库存流水触发器）、`reserved_qty +qty`（预订单触发器） | 重跑 `fn_ProductStatus`；**可售量归零才转 `OUT_OF_STOCK`** | 无 | 不生成 | **不动** |
| `RESERVED` → `PICKED_UP` | **无**（预订时已扣，不重复） | `stock_qty` 不变、`reserved_qty −qty` | **不变**（`stock_qty` 未变，函数结果必然相同） | `SALE_IN`（+实付） | **生成** `PAID` 订单 —— **此刻才快照金额、折扣、积分** | 扣使用、加获得 |
| `RESERVED` → `EXPIRED` | `RELEASE`（+qty） | `stock_qty +qty`、`reserved_qty −qty` | 重跑 `fn_ProductStatus`，通常回 `ON_SALE` | 无 | 不生成 | 不动 |
| `RESERVED` → `CANCELLED` | `RELEASE`（+qty） | `stock_qty +qty`、`reserved_qty −qty` | 重跑 `fn_ProductStatus`，通常回 `ON_SALE` | 无 | 不生成 | 不动 |

> **金额在哪儿定（v7 定案）**：预订全程**不记金额、不冻结折扣、不动积分**。
> `PICKED_UP` 时按**自提当时的售价、当时的会员等级折扣、当时可用的积分**重新计算，
> 再快照进新建的销售订单。
> 所以上表「资金流水」列的 `+实付` 指的是**重算后的金额**，
> 而不是任何下单时的预估 —— 下单时压根没有预估。
>
> **副作用**：若小林的等级在保留期内从银卡升到金卡，自提时按**金卡 9 折**成交；
> 若期间书店调价，按**新价**成交。这是「以自提时为准」的必然结果，属于既定语义。

> **只有「会写库存流水」的迁移才需要重估商品状态**（R14）：
>
> | 迁移 | 写流水？ | 谁重估 |
> |---|---|---|
> | `→ RESERVED` | 写 `RESERVE` | 库存流水触发器 |
> | `→ EXPIRED` / `→ CANCELLED` | 写 `RELEASE` | 库存流水触发器 |
> | `→ PICKED_UP` | **不写** | **无人重估，也不需要** |
>
> `PICKED_UP` 不写库存流水，所以没有触发器被激活；而且**也不需要** ——
> `stock_qty` 一点没变，一元函数的结果必然相同。
>
> 一句话收口：**状态是库存的投影；库存没动，状态就不用动。**
>
> 预订单触发器按 R14 只维护 `reserved_qty`、**不碰 `status`**；
> **`reserved_qty` 的变化本身不影响状态判定**，它只改变商品列表页上那个数字。
>
> 重估的效果只有两种走向：
> - 下单把可售量划空（`stock_qty = 0`）→ 商品转 `OUT_OF_STOCK`，
>   尽管架上还压着一批已订走的货；
> - 释放预占把货归还可售量（`stock_qty > 0`）→ 商品回到 `ON_SALE`。

#### 2.6.4 约束

「只有自提成功才有订单」这条业务规则，用一条 `CHECK` 写成数据库约束：

```sql
CONSTRAINT ck_reservation_order_link CHECK (
    (status =  'PICKED_UP' AND order_id IS NOT NULL)
 OR (status <> 'PICKED_UP' AND order_id IS NULL)
)
```

> 这条约束把「预订与订单的耦合关系」变成了**不可违反的数据库事实**：
> 任何试图让 `EXPIRED` 的预订挂上订单、或让 `PICKED_UP` 的预订没有订单的
> 写入，都会被数据库直接拒绝。这是本项目「业务规则下沉到数据库」原则的范例。

#### 2.6.5 超时释放的实现（注意 Express 限制）

SQL Server **Express 版不含 SQL Server Agent**，因此不能依赖数据库内置的定时作业。
本项目采用：

- 存储过程 `usp_ExpireReservations`：把 `RESERVED` 且 `expire_at < GETDATE()`
  的预订批量置为 `EXPIRED` 并写 `RELEASE` 流水，**单事务**完成。
- 调用时机两处兜底：
  1. 应用层定时任务（或 Windows 任务计划程序 / `sqlcmd`）周期调用；
  2. 收银员打开核销页面、以及库管开始盘点**之前**各调用一次，
     保证展示口径与盘点口径都是最新的。

> 这样即便定时任务没跑，业务动作前的即时调用也能保证不会出现
> 「已经超时却仍占着货」的脏读口径。

### 2.7 资金与财务

书店的「钱」单独成一条线，与「货」并行记录。

**资金流水类型**（`CashFlow.flow_type`）：

| 代号 | 含义 | 方向 | 触发点 |
|---|---|---|---|
| `CAPITAL_IN` | 店长注资（投钱） | + | 店长操作 |
| `CAPITAL_OUT` | 店长提现（放钱） | − | 店长操作 |
| `PURCHASE_OUT` | 采购付款 | − | 采购收货确认 |
| `SALE_IN` | 销售收款 | + | 门店结算 / 线上自提核销 |
| `REFUND_OUT` | 退货退款 | − | 退货确认 |
| `OPERATING_EXPENSE` | 日常费用（水电、房租等） | − | 店长或管理员登记 |

> 注意：线上**下单预占阶段不产生任何资金流水**（顾客还没付钱），
> 只有 `PICKED_UP` 时才写 `SALE_IN`。预订超时或取消同样不产生资金流水。

**口径声明（v7 拆成两个指标）**：本项目的钱采用**收付实现制**，
但**不再用一个数去混淆两件不同的事**：

```text
经营盈亏 = SALE_IN − PURCHASE_OUT − REFUND_OUT − OPERATING_EXPENSE
现金余额 = SUM(CashFlow.amount_delta)          -- 含注资 / 提现
```

| 指标 | 回答什么 | 是否含注资 / 提现 |
|---|---|---|
| **经营盈亏** | 书店**做生意**赚了还是亏了 | **不含** |
| **现金余额** | 账上现在**有多少钱** | 含 |

> **为什么必须拆开**：`CAPITAL_IN` / `CAPITAL_OUT` 是**老板与书店之间的资金往来**，
> 不是经营成果。若不剔除，会出现两个荒谬结果：
> ① 一家刚开张、一本书都没卖的书店报出 5 万元「利润」；
> ② 两个指标恒等（同一个公式），报表并列显示毫无意义。
> 剔除之后，创店当期的**经营盈亏为 0、现金余额为 50,000** —— 这才是可解释的口径。

> **另一个有意保留的简化**：收付实现制不区分「采购支出」与「销售成本」，
> 因此**库存积压不会体现在经营盈亏里**。
> 若要算会计口径的毛利，需要引入移动加权平均成本（`Product.avg_cost`），
> 本项目将其列为 **M3 阶段的可选深化项**，不进 M1 / M2 范围。

## 5. 两条自洽轨迹（模型验证用的叙事）

### 5.1 门店销售（§2.3 计价规则的验收）

> 3 月 12 日，银卡会员小林（累计消费 1,280 元）到店，想买《数据库系统概念》。
> 这本书 2 月从「华南图书批发」进货 20 册，进价 58 元，定价 89 元。
>
> 收银员扫码，系统取到当前售价 89 元；识别出银卡会员，折扣 9.5 折；
> 小林用 500 积分抵 5 元。
>
> **计价（先扣积分，再打折）**：
> `89 − 5 = 84`，`84 × 0.95 = 79.80`，实付 **79.80 元**。
>
> 系统把 89、0.95、79.80 三个数字**快照**进订单行，
> 写入一条 `−1` 的库存流水，库存由 20 变为 19；
> 若库存由此归零，触发器会把商品状态改为 `OUT_OF_STOCK`。
>
> 同时：写一笔 `SALE_IN` 资金流水 79.80 元；
> 写两条积分流水（−500 使用、**+119 获得**），
> 其中 `FLOOR(79.80 × 1.5) = FLOOR(119.7) = 119`；
> 小林累计消费变为 1,359.80 元，积分余额由 500 变为 **119**。
>
> 5 月，这本书定价调整为 99 元。
> 小林回看 3 月的订单，金额依旧是 79.80 元 —— 因为价格被冻结在了订单行里。

### 5.2 线上预订（§2.6 与 §2.1.1 状态重估的验收）

本节分两个场景，各自验证一条设计承诺：

- **场景一 · 库存充足** → 验「**订走 1 册不会锁死整个种类**」
- **场景二 · 只剩最后 1 册** → 验「**全部被订走时状态归为缺货**」

#### 场景一 · 库存充足（20 册）

> 4 月 8 日 10:00，小林在手机上预订《数据库系统概念》1 册。
> 该书当前 `stock_qty = 19`、`reserved_qty = 0`、`status = ON_SALE`。
>
> **下单事务**：写 `Reservation(status='RESERVED', expire_at=4/10 10:00)`，
> 预订单行只记 `product_id = 该书`、`qty = 1` —— **不记金额、不记折扣、不动积分**；
> 写一条 `RESERVE(−1)` 流水。
> 结果：`stock_qty = 18`、`reserved_qty = 1`、`physical_qty = 19`。
> 重跑 `fn_ProductStatus(18)` → `ON_SALE`，**商品状态不变**。
> **此时没有资金流水、没有销售订单，也没有任何价格承诺。**
>
> 同一时刻店里来了位散客想买这本书 —— 商品列表页显示「可售 18 / 已订 1 / 在库 19」，
> 他正常买走一本。被预订的那 1 册从未参与销售，因为它已经不在可售的那一批里了。
>
> **这是本设计最要紧的一步**：只有 1 册被订走，商品**照旧是 `ON_SALE`**。
> 若因为「有人订了 1 册」就把整个种类锁死，就会出现「1 本预订锁死 19 本」的业务事故。
>
> **分支 A（4 月 9 日 15:00，到店自提）**：
> 小林报出取货码，收银员核销。事务内：
> ① **按自提当时的售价、等级与积分重新计价** —— 售价仍 89、小林仍是银卡，
>    故 `T = ROUND(89 × 0.95, 2) = 84.55`，**此刻才把金额快照进销售订单**；
> ② 生成 `SalesOrder(channel='ONLINE', status='PAID')` 与订单行；
> ③ `Reservation.status = 'PICKED_UP'`，`order_id` 指向新订单；
> ④ 写 `CashFlow(SALE_IN, +84.55)`；⑤ 扣使用积分、加获得积分。
> **不写任何库存流水** —— `stock_qty` 保持 18，`reserved_qty` 降为 0，
> `physical_qty` 由 19 降为 18（书真的离店了）。
> **商品状态不变**：`stock_qty` 未变，无需重估（见 §2.6.3）。
>
> 注意计价发生在①而不是下单时：若书店这期间把售价调到 99，或小林已升为金卡，
> 成交价就按新价 / 新折扣走 —— **一切以自提时为准**。
>
> **分支 B（4 月 10 日 10:00 之后一直没来）**：
> `usp_ExpireReservations` 把预订置为 `EXPIRED` 并写 `RELEASE(+1)`。
> 结果：`stock_qty` 回到 19，`reserved_qty` 降为 0，`physical_qty` 保持 19
> （书从未离店）。重跑 `fn_ProductStatus(19)` → `ON_SALE`。
> 全程没有资金流水、没有销售订单、没有积分变动。

#### 场景二 · 只剩最后 1 册

> 换一个前提：这本书**只剩最后 1 册**，并且被小林订走。
> `stock_qty = 0`、`reserved_qty = 1`，重跑 `fn_ProductStatus(0)` → `OUT_OF_STOCK`。
>
> 商品转为**缺货**：门店不能再卖、不能再被预订、也不能报损 ——
> 三条禁令都由 `stock_qty = 0` 自动落实，不需要额外规则。
> 但它**仍计入在库** —— `physical_qty = 1`，那本书还躺在货架上，只是已经有主了。
> 列表页会显示「可售 0 / 已订 1 / 在库 1」，库管一眼就能看出
> 这不是「货架空了」，而是「全被订走了」—— 但**系统不会提示他补货**，
> 要不要补是他的判断。
>
> **分支 C（4 月 10 日 10:00 之后一直没来）**：
> `usp_ExpireReservations` 写 `RELEASE(+1)`，`stock_qty` 由 0 回到 1，
> 商品状态由 `OUT_OF_STOCK` 回到 `ON_SALE` ——
> 这是 `OUT_OF_STOCK → ON_SALE` 这条自动迁移的验收点。

这两段叙事是**验收工具**：任何一步做不到，说明模型有漏洞。

## 6. 已拍板的业务规则

| 编号 | 规则 | 定案 |
|---|---|---|
| R1 | 折扣与积分是否叠加、以何顺序 | **可叠加，先扣积分再打折** |
| R2 | 是否允许部分退货 | **允许，按订单行退货** |
| R3 | 会员是否降级 | **不降级，等级只升不降** |
| R4 | 积分随折扣缩水是否可接受 | **接受**，这是 R1 的必然结果，非缺陷 |
| R5 | 「能不能卖」怎么判定 | **判商品种类，不判单册**。可销售条件 = `(在库量 − 预定量 − 损坏量) > 0`，**恒等于 `stock_qty > 0`**。`reserved_qty` 只是计数，**不参与状态判定** |
| R6 | 价格 / 折扣 / 积分的**快照时点** | **只在成交时快照**（门店结算、线上自提核销）。此后不因调价或等级变化而回改。**线上预订不产生快照** —— 见 R11 |
| R7 | 商品种类与具体商品的区分粒度 | **只区分到「计数」级**。种类 = `Product` 一行；单册**无独立记录**，只体现为 `stock_qty` / `reserved_qty` 两个计数。**不做副本表**；代价是盘亏无法定位到具体哪一册、批次成本只能近似 |
| R8 | 报损是否落独立的「待损池」 | **不落**。`DAMAGE_OUT` 流水即时扣减 `stock_qty`，可销售条件里的 `damaged_qty` 恒为 0。若将来需要「破损待处理区」，新增一个占用池即可，**状态机无需改动** |
| R9 | 商品状态机的层次 | **4 态，分两层**：自动区 `ON_SALE` / `OUT_OF_STOCK` 两态由 `stock_qty` **一元判定**；人工区 `OFF_SHELF` / `DISCONTINUED` 两态由人决定，触发器不碰 |
| R10 | 「全部在库商品均被预定」怎么表达 | **归入 `OUT_OF_STOCK`**，不单列状态。该事实由 `stock_qty = 0` 且 `reserved_qty > 0` 表达，并在查询视图展示计数；**是否补货取决于库管意愿，系统不做提示、不做判断** |
| R11 | 线上预订是否冻结金额 / 折扣 / 积分 | **一律不冻结**。预订单只负责锁住 `qty` 个商品；金额、折扣、积分**以线下自提当时为准**。因此 `Reservation` / `ReservationItem` **不含任何金额字段** |
| R12 | 盈亏口径 | **拆成两个指标**：经营盈亏 = `SALE_IN − PURCHASE_OUT − REFUND_OUT − OPERATING_EXPENSE`；现金余额 = `SUM(CashFlow.amount_delta)`。**注资 / 提现不进经营盈亏** |
| R13 | 建档时商品的初始状态 | 建档即按 `fn_ProductStatus` 判定 —— 此时 `stock_qty = 0`，故为 **`OUT_OF_STOCK`**；进第一批货后由触发器自动转 `ON_SALE` |
| R14 | 派生字段的触发器职责划分 | **库存流水触发器**维护 `stock_qty`（对所有 `movement_type`）并重跑 `fn_ProductStatus` 维护 `status`；**预订单触发器**只维护 `reserved_qty`，不碰前两者 |

## 7. 已定案的边界约定

| 项 | 定案 |
|---|---|
| 商品状态机的状态数 | **4 态**：自动区 `ON_SALE` / `OUT_OF_STOCK`，人工区 `OFF_SHELF` / `DISCONTINUED` |
| 自动区的判定基准 | **只看 `stock_qty` 一个量**（可售余量 > 0 即在售）。`reserved_qty` 不参与判定 |
| 建档时商品的初始状态 | **`OUT_OF_STOCK`** —— 建档即按 `fn_ProductStatus` 判定，`stock_qty = 0` 故为缺货；进第一批货后自动转 `ON_SALE`（R13） |
| 「已预定」的表达层 | **计量层，不占状态位**。它只体现为 `Product.reserved_qty` 这个计数；`Product.status` 里**没有** `RESERVED` |
| 「全部在库商品均被预定」 | **状态 = `OUT_OF_STOCK`**（等价于 `stock_qty = 0` 且 `reserved_qty > 0`）。不单列状态 |
| 全被订走时是否要补货 | **系统不提示、不判断**，由库管看计数自行决定（R10） |
| 派生字段由谁维护 | 库存流水触发器维护 `stock_qty` 与 `status`；预订单触发器只维护 `reserved_qty`（R14） |
| 商品种类与具体商品的粒度 | **只到计数级**：种类 = `Product` 一行；单册无独立记录，体现为 `stock_qty` / `reserved_qty` 两个计数 |
| 商品列表页必须展示什么 | `stock_qty`（可售量）、`reserved_qty`（预定量）、`physical_qty`（在库量）、`status`（状态）**四项并列**，不做派生标签、不给补货建议 |
| 线上预订库存扣减时点 | **下单预占时扣减**；自提阶段不动库存，只做收入确认与积分结算 |
| 线上预订是否冻结金额 / 折扣 / 积分 | **一律不冻结**。预订单只锁 `qty` 个商品；`Reservation` / `ReservationItem` **不含任何金额字段**（R11） |
| 线上预订的成交计价时点 | **自提核销时**按当时的售价、当时的会员等级、当时可用的积分重新计算，并快照进销售订单 |
| 线上预订积分结算时点 | **自提时**扣使用积分、加获得积分；**下单不动积分** |
| 线上预订资金流水时点 | **自提时**写 `SALE_IN`；下单、过期、取消均不产生资金流水 |
| 价格 / 折扣快照的产生时点 | **只在成交时**（门店结算、线上自提核销）。此后不因调价或等级变化而回改（R6） |
| 经营盈亏与现金余额 | **两个指标，不可混用**。经营盈亏不含注资 / 提现（R12） |
| 预占商品在语义上是什么 | **已售出、待取货**。其他顾客不能再买走或再预订 |
| 预占商品是否计入在库 | **计入**。它仍在货架上，计 `physical_qty`；**盘点账面基准 = `physical_qty`** |
| 预占商品的库存表达 | 两个计数：`stock_qty`（可售量）/ `reserved_qty`（已订量）；`physical_qty` 为两者之和 |
| 预占商品能否被销售 / 再预订 | **不能** —— `stock_qty = 0`，销售与预订都在校验阶段被拒 |
| 预占商品能否报损 | **不能** —— 报损只从可售量扣，`stock_qty = 0` 时校验 `qty <= stock_qty` 直接失败 |
| 报损是否设独立待损池 | **不设**。`DAMAGE_OUT` 即时扣减 `stock_qty`（R8） |
| 退货时预订单是否回滚 | **不回滚**。预订已终态（`PICKED_UP`），退货是订单级事件，只动订单与积分 |
| 报损是否需要审批 | 不需要，但必须填写文字原因 |
| 盘点是否需要店长确认 | 需要（记入 `confirmed_by`），确认后不可修改 —— **具体落库方式待商议（Q5）** |
| 采购审批 | **本阶段 block**，状态机无 `APPROVED` / `CLOSED`。详情见 Q1 |
